# Деплой тестового сервера: Vercel + Railway (для новачка)

> Покрокова інструкція, як підняти гілку **develop** на публічному тестовому сервері.
> Розрахована на людину, яка **ніколи цього не робила**. Кожен крок — з поясненням
> «навіщо» і командами, які можна копіювати як є.

---

## 0. Загальна картина: чому два різні сервіси

Наш застосунок складається з **трьох частин**, і вони не можуть жити на одному хостингу:

```
   ┌─────────────────────────┐        ┌─────────────────────────┐
   │  store-client (вітрина)  │        │  store-admin (адмінка)   │
   │        Next.js           │        │        Next.js           │
   │        VERCEL            │        │        VERCEL            │
   └───────────┬─────────────┘        └───────────┬─────────────┘
               │  HTTPS запити до API             │
               └──────────────┬──────────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │   store-api (бекенд)     │
                 │        NestJS            │
                 │        RAILWAY           │
                 └───┬──────────────┬───────┘
                     ▼              ▼
              ┌───────────┐   ┌───────────┐
              │ PostgreSQL│   │   Redis   │   (обидва — плагіни Railway)
              └───────────┘   └───────────┘
```

**Чому не все на Vercel?** Vercel чудово тримає Next.js-фронтенди, але **не вміє
запускати NestJS-бекенд**: це «живий» сервер, якому потрібні постійне з'єднання з
Postgres і Redis, фонові cron-задачі та зберігання завантажених файлів на диску. Тому:

- **Vercel** → `store-client` (вітрина) і `store-admin` (адмінка), два окремі проєкти.
- **Railway** → `store-api` + керовані **PostgreSQL** і **Redis** (натискаєш кнопку —
  вони самі створюються, адмініструвати сервер не треба).

**Скільки це коштує?** Railway і Vercel мають безкоштовні/пробні тарифи, яких для
тестового сервера вистачає. Єдина рекомендована платна дрібниця — **власний домен**
(~5–12 $/рік). Навіщо він потрібен — пояснено у кроці 1.

## 1. Найважливіше, що треба зрозуміти ДО початку

Тут два «підводні камені». Якщо їх не врахувати — сайт зовні відкриється, але
**вхід у кабінет і кошик гостя працювати не будуть**. Прочитайте цей розділ уважно.

### 1.1. Домен: чому «голі» адреси Vercel і Railway не дружать (авторизація)

Наш бекенд ставить авторизаційні дані в **cookie** з політикою `SameSite=Strict`
(див. `apps/store-api/src/auth/auth.controller.ts` і `src/csrf/csrf.service.ts`). Ця
політика означає: браузер віддає такий cookie лише коли **сайт і API — це один і той
самий домен** (точніше — один «registrable domain», напр. `example.com`).

Безкоштовні адреси `щось.vercel.app` і `щось.railway.app` — це **різні** домени, тому
браузер cookie між ними **не передасть**. Наслідок:

| Що робить користувач                  | Голі _.vercel.app + _.railway.app                         |
| ------------------------------------- | --------------------------------------------------------- |
| Дивиться каталог, товар, блог, статті | ✅ Працює                                                 |
| Логіниться в кабінет / адмінку        | ⚠️ Входить, але «вилітає» після перезавантаження сторінки |
| Кошик гостя (без реєстрації)          | ❌ Не працює (CSRF/cookie)                                |

**Правильне рішення (рекомендоване, БЕЗ змін коду):** узяти один домен і посадити всі
три частини на його **піддомени** — тоді для браузера це «один сайт» і cookie ходять як
задумано. Саме так спроєктований застосунок (у Docker-версії Caddy робить те саме):

```
shop.ВАШ-ДОМЕН.com    → store-client (Vercel)
admin.ВАШ-ДОМЕН.com   → store-admin  (Vercel)
api.ВАШ-ДОМЕН.com     → store-api    (Railway)
```

> 💡 Домен можна купити на будь-якому реєстраторі (Namecheap, Cloudflare, GoDaddy,
> hostiq.ua тощо). Далі в інструкції показано, які DNS-записи додати — Vercel і Railway
> дають готові значення для копіювання.

**Альтернатива без домену (не рекомендовано):** можна залишити голі адреси, якщо вам
достатньо показати **лише вітрину-каталог** без входу в кабінет і без гостьового кошика.
Тоді кроки з доменом просто пропускаєте. Щоб авторизація запрацювала на різних доменах,
довелося б міняти код (перевести cookie на `SameSite=None; Secure` і переробити
CSRF-механізм) — це окрема задача, у цю інструкцію вона не входить.

### 1.2. `swagger.json`: як фронтенд отримує контракт API

Фронтенди не пишуть запити до API руками — вони генерують типізовані хуки з
OpenAPI-специфікації (інструмент Orval). Щоб **не комітити** цей згенерований файл у git
(він навмисно в `.gitignore`), бекенд віддає специфікацію по HTTP у **будь-якому**
середовищі за адресою `GET /api/docs-json` (інтерактивний Swagger UI лишається лише в
`development`). Збірка фронтенду на Vercel просто **завантажує свіжу спеку з живого
Railway-API** під час білду (`curl … -o apps/store-api/swagger.json`) — файл ніде не
зберігається в репозиторії й завжди синхронний із розгорнутим API. Команди — у кроках 4–5.

> ⚠️ Наслідок: збірка фронтенду **залежить від того, що Railway-API вже піднятий і
> публічно доступний**. Тому порядок такий: спершу бекенд (крок 3), потім фронтенди.
>
> 🔒 `/api/docs-json` відкриває публічно **форму** ендпоінтів (не дані — усі захищені
> роути далі вимагають авторизації). Для тестового сервера це прийнятно. Для справжнього
> продакшну варто закрити цей ендпоінт (напр. токеном) або повернутися до кодогенерації в CI.

## 3. Крок за кроком: бекенд на Railway (робимо ПЕРШИМ)

Бекенд піднімаємо першим, бо фронтендам потрібна його публічна адреса.

**3.1. Створити проєкт і бази:**

1. Зайдіть на `railway.app` → **New Project**.
2. **+ New → Database → Add PostgreSQL**. Railway створить керований Postgres.
3. Ще раз **+ New → Database → Add Redis**. Redis у нас **обов'язковий** у продакшн-режимі
   (кеш + обмеження частоти запитів).

**3.2. Додати сам застосунок:**

1. **+ New → GitHub Repo** → виберіть ваш репозиторій.
2. У налаштуваннях сервісу: **Settings → Source → Branch = `develop`**.
3. **Settings → Root Directory = `apps/store-api`**. Railway сам знайде
   `apps/store-api/Dockerfile` і збиратиме з нього (образ уже вміє прогнати
   `prisma db push` при старті — окрема команда міграції не потрібна).

**3.3. Прописати змінні оточення** (**Variables** у сервісі store-api). Значення беріть
за зразком з [`.env.production.example`](../../.env.production.example):

| Змінна                | Що вписати                                                                   |
| --------------------- | ---------------------------------------------------------------------------- |
| `NODE_ENV`            | `production`                                                                 |
| `DATABASE_URL`        | посилання на Postgres-плагін: `${{Postgres.DATABASE_URL}}`                   |
| `REDIS_HOST`          | `${{Redis.RAILWAY_PRIVATE_DOMAIN}}` (внутрішній хост Redis)                  |
| `REDIS_PORT`          | `6379`                                                                       |
| `REDIS_PASSWORD`      | `${{Redis.REDIS_PASSWORD}}`                                                  |
| `JWT_SECRET`          | згенерувати (див. нижче), ≥ 32 символи                                       |
| `JWT_REFRESH_SECRET`  | інший, окремий, ≥ 32 символи                                                 |
| `CSRF_SECRET`         | ще один, ≥ 32 символи                                                        |
| `PUBLIC_BASE_URL`     | публічна адреса API (заповнити після 3.4, напр. `https://api.ВАШ-ДОМЕН.com`) |
| `CORS_ORIGINS`        | адреси вітрини й адмінки через кому (заповнити у кроці 5)                    |
| `STORE_CLIENT_URL`    | адреса вітрини (заповнити у кроці 5)                                         |
| `ADMIN_SEED_EMAIL`    | `admin@store.com` (або свій)                                                 |
| `ADMIN_SEED_PASSWORD` | пароль головного адміна                                                      |

Meilisearch/SMTP/Sentry/Nova Poshta — **необов'язкові**, залиште порожніми: пошук
автоматично відкотиться на Postgres, пошта/аналітика просто вимкнуться.

Згенерувати секрет:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**3.4. Отримати публічну адресу API:**

- **Settings → Networking → Generate Domain** — Railway видасть адресу
  `store-api-xxxx.up.railway.app`.
- (Рекомендовано) Додайте свій піддомен: **Custom Domain → `api.ВАШ-ДОМЕН.com`** і
  створіть у реєстратора CNAME-запис на значення, яке підкаже Railway.
- Впишіть цю адресу у змінну `PUBLIC_BASE_URL` і збережіть (сервіс перезапуститься).

**3.5. Наповнити базу демо-даними (seed):**
Після першого успішного деплою запустіть seed **один раз** через Railway CLI:

```bash
railway run --service store-api npm run db:seed -w apps/store-api
```

**Нюанс із адресою бази:** `railway run` виконує команду на вашому ноуті, а внутрішній
`postgres.railway.internal` ззовні не резолвиться. Якщо побачите «connection refused» —
підставте публічний URL бази (Postgres → **Connect → Public Network**, або змінна
`DATABASE_PUBLIC_URL`):

```bash
railway run --service store-api \
  bash -c 'DATABASE_URL="<DATABASE_PUBLIC_URL>" npm run db:seed -w apps/store-api'
```

Створить усі демо-дані: 2 адміни, покупці, вкладені категорії з iPhone, замовлення в усіх
статусах, знижки, тех-сторінки, статті тощо (див. [`seed-guide.md`](../seed-guide.md)).

**3.6. Перевірити, що бекенд живий:**
Відкрийте в браузері `https://api.ВАШ-ДОМЕН.com/health` → має відповісти `ok`.

> ℹ️ Інтерактивний Swagger **UI** (`/api/docs`) у проді навмисно вимкнено (лише в
> `development`). А ось **JSON-спека** `/api/docs-json` доступна завжди — саме її тягне
> білд фронтенду. Перевірте: `https://api.ВАШ-ДОМЕН.com/api/docs-json` має віддати JSON.

## 4. Крок за кроком: вітрина `store-client` на Vercel

> ✅ Перед цим кроком **Railway-API має бути живий** (крок 3) — збірка тягне з нього
> OpenAPI-спеку по HTTP. Комітити нічого не треба.

1. На `vercel.com` → **Add New → Project** → імпортуйте той самий GitHub-репозиторій.
2. **Root Directory → `apps/store-client`** (кнопка _Edit_ біля Root Directory).
   Увімкніть **«Include files outside of the Root Directory»** — збірка записує спеку в
   сусідню теку `apps/store-api/`, тож їй потрібен доступ за межі Root Directory.
3. **Framework Preset** визначиться як _Next.js_ автоматично.
4. **Build Command** (розкрийте _Build & Output Settings_ → _Override_):
   ```
   curl -sf "$NEXT_PUBLIC_API_URL/api/docs-json" -o ../store-api/swagger.json && npm run generate:api && npm run build
   ```
   Спершу з живого API завантажується OpenAPI-спека, з неї Orval генерує типізовані
   API-хуки, потім — звичайна збірка Next. Прапорець `-sf` робить `curl` «тихим» і
   повертає помилку, якщо API недоступний, щоб білд одразу впав зі зрозумілою причиною.
   (Команди без `-w`, бо Root Directory уже вказує на застосунок — усе виконується
   всередині `apps/store-client`.)
5. **Environment Variables:**

   | Змінна                 | Значення                                                                |
   | ---------------------- | ----------------------------------------------------------------------- |
   | `NEXT_PUBLIC_API_URL`  | адреса Railway-API, **без слеша в кінці** (`https://api.ВАШ-ДОМЕН.com`) |
   | `NEXT_PUBLIC_APP_URL`  | майбутня адреса вітрини (`https://shop.ВАШ-ДОМЕН.com`)                  |
   | `NEXT_PUBLIC_SITE_URL` | те саме, що `NEXT_PUBLIC_APP_URL` (для SEO/sitemap)                     |
   | `NEXT_PUBLIC_CURRENCY` | `UAH`                                                                   |

   > ⚠️ Усі `NEXT_PUBLIC_*` «запікаються» у збірку. Якщо зміните їх пізніше — треба
   > зробити **Redeploy**, простого перезапуску замало. `NEXT_PUBLIC_API_URL` заодно
   > дозволяє показ картинок з API-домену (`next/image`), тож задайте його правильно
   > **до** першої збірки.

6. **Deploy**. Після збірки Vercel дасть адресу `store-client-xxxx.vercel.app`.
7. (Рекомендовано) **Settings → Domains → Add** → `shop.ВАШ-ДОМЕН.com`, і додайте у
   реєстратора CNAME-запис за підказкою Vercel.

## 5. Крок за кроком: адмінка `store-admin` + «зшивання» всього разом

**5.1. Задеплоїти адмінку** — так само, як крок 4, з відмінностями:

- **Root Directory → `apps/store-admin`** (+ увімкнути «Include files outside Root Directory»).
- **Build Command:**
  ```
  curl -sf "$NEXT_PUBLIC_API_URL/api/docs-json" -o ../store-api/swagger.json && npm run generate:api && npm run build
  ```
- Змінні:

  | Змінна                  | Значення                                       |
  | ----------------------- | ---------------------------------------------- |
  | `NEXT_PUBLIC_API_URL`   | адреса Railway-API (та сама)                   |
  | `NEXT_PUBLIC_ADMIN_URL` | адреса адмінки (`https://admin.ВАШ-ДОМЕН.com`) |
  | `NEXT_PUBLIC_APP_URL`   | адреса вітрини (`https://shop.ВАШ-ДОМЕН.com`)  |

- Додайте домен `admin.ВАШ-ДОМЕН.com`.

**5.2. Повернутися на Railway і замкнути коло** (це критичний крок — без нього браузер
блокуватиме запити):

- У змінних store-api задайте:
  - `CORS_ORIGINS` = `https://shop.ВАШ-ДОМЕН.com,https://admin.ВАШ-ДОМЕН.com` (обидві
    адреси через кому, без пробілів, без слеша в кінці).
  - `STORE_CLIENT_URL` = `https://shop.ВАШ-ДОМЕН.com`.
- Збережіть → Railway перезапустить бекенд.

Після цього фронтенди (Vercel) і бекенд (Railway) знаходяться на піддоменах одного
домену → cookie ходять правильно, CORS дозволено, картинки показуються.

## 6. Перевірка (smoke test)

Пройдіть цей чеклист у браузері:

- [ ] `https://shop.ВАШ-ДОМЕН.com` — відкривається головна, видно банери й товари.
- [ ] Каталог → картка товару → фото вантажаться, ціна є.
- [ ] Категорія **Смартфони → iPhone** відкривається (перевірка вкладених категорій).
- [ ] Блог і тех-сторінки (Про нас, Доставка, Гарантія) відкриваються.
- [ ] **Реєстрація/вхід**: залогінтесь, **перезавантажте сторінку** — ви й далі
      залогінені (перевірка cookie/домену з кроку 1.1).
- [ ] Кошик гостя: додайте товар без входу — він зберігається.
- [ ] `https://admin.ВАШ-ДОМЕН.com` — вхід під `admin@store.com`; у списку замовлень
      видно демо-замовлення в різних статусах; є черга відгуків на модерацію та
      повідомлення з форми контактів.

### Таблиця типових проблем

| Симптом                                                 | Причина / що робити                                                                                                                                              |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| У консолі браузера **CORS error**                       | `CORS_ORIGINS` на Railway не містить точної адреси фронтенду (перевірте кому/слеш/https).                                                                        |
| Логінюсь, але **«вилітає» після перезавантаження**      | Фронтенд і API на **різних** доменах — зробіть піддомени одного домену (крок 1.1).                                                                               |
| **Кошик гостя не працює**, помилка 403/CSRF             | Те саме — потрібні спільний домен/піддомени.                                                                                                                     |
| **Картинки товарів не вантажаться**                     | `NEXT_PUBLIC_API_URL` виставлений неправильно або не зроблено Redeploy після зміни.                                                                              |
| Збірка Vercel падає на **`curl … /api/docs-json`**      | Railway-API не піднятий/недоступний, або `NEXT_PUBLIC_API_URL` вказує не туди. Перевірте, що `https://api.ВАШ-ДОМЕН.com/api/docs-json` відкривається у браузері. |
| Збірка падає на **`generate:api`** («cannot find spec») | `curl` не записав файл (див. рядок вище), або вимкнено «Include files outside Root Directory».                                                                   |
| **500** з API / бекенд не стартує                       | Перевірте змінні на Railway (`DATABASE_URL`, `REDIS_*`, три секрети ≥32 символів).                                                                               |

## 7. Оновлення після змін коду

- **Фронтенди (Vercel):** кожен `git push` у `develop` автоматично запускає новий
  деплой обох проєктів. Якщо змінили `NEXT_PUBLIC_*` — зробіть **Redeploy** вручну
  (Deployments → ⋯ → Redeploy), бо ці змінні запікаються у збірку.
- **Бекенд (Railway):** пуш у `develop` теж тригерить редеплой; вручну —
  **Deployments → Redeploy**.
- **Змінили API-контракт** (ендпоінти/DTO): нічого комітити не треба — після редеплою
  бекенду просто зробіть **Redeploy** фронтендів; їхній білд сам завантажить свіжу
  OpenAPI-спеку з живого API.
- **Змінили схему БД:** образ бекенду сам прогонить `prisma db push` при старті. Якщо
  додали нові демо-дані — за потреби перезапустіть seed (крок 3.5).
