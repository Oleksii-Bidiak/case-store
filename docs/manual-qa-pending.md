## Крок 0. Підготовка стенду (обов'язково перед усім)

Потрібно 4 вікна терміналу (кожна команда працює постійно). Виконуй з кореня репозиторію.

1. **Інфраструктура:** `docker compose up -d`
   → Postgres (5432), Redis (6379), Meilisearch (7700) запущені. Перевір: `docker ps` — контейнери `Up`.
2. **Міграції + дані:** `npm run db:migrate`, потім `npm run db:seed`
   → у консолі підсумок сіда без помилок (`✓ Users: admin=…, customer=…` + лічильники
   товарів/категорій; точні числа з часом змінюються — орієнтуйся на відсутність помилок).
3. **API:** `npm run start:dev -w apps/store-api` → `http://localhost:3001`,
   Swagger: `http://localhost:3001/api/docs` (404 на голому `/api` — норма).
4. **Вітрина:** `npm run dev -w apps/store-client` → `http://localhost:3000`.
5. **Адмінка:** `npm run dev -w apps/store-admin` → `http://localhost:3002`.
6. **Перевір `NEXT_PUBLIC_API_URL`** в `apps/store-client/.env.local` і `apps/store-admin/.env.local`:
   має бути `http://localhost:3001` **без** `/api` в кінці (деталі — master §Крок 1).
7. **Пошук:** в `apps/store-api/.env` мають бути `MEILI_HOST=http://localhost:7700` і
   `MEILI_MASTER_KEY=…` (той самий, що в `docker-compose.yml`). Після зміни `.env` перезапусти API.
8. **Ревалідація контенту** (потрібна для LG-8 і частини чеків Частини III; без цих змінних
   ISR-очистка мовчки no-op — не помилка, але зміни підтягуються лише за ~годину): у store-api
   `PUBLISHING_CRON` (деф. `* * * * *`), `STOREFRONT_REVALIDATE_URL`
   (напр. `http://localhost:3000/api/revalidate`), `REVALIDATE_SECRET`; у store-client той
   самий `REVALIDATE_SECRET`.
9. **Зовнішні ключі** (NP, SMTP, Sentry, Umami, Google OAuth, IndexNow) — див. **Частину IV**.
   Для фінального прогону Частини I вони **обов'язкові** (LG-4 і LG-6 без ключів не проходяться).

**Акаунти (з сіда, для dev-стенду):**

- Адмін: `admin@store.com` / `Admin123!` (адмінка на :3002)
- Покупець A: `customer@store.com` / `Customer123!`
- Покупець B: зареєструй сам на вітрині (наприклад `customerb@store.com` / `Customer123!`) —
  потрібен для перевірок бану і злиття кошиків.

> ⚠️ Ці паролі опубліковані в репозиторії (`docs/seed-guide.md`). На проді вони мають бути
> **ротовані** — це окремий чек у LG-7.

**Темна тема для візуальних перевірок:** DevTools (F12) → `Ctrl+Shift+P` → набери
«Rendering» → **Emulate CSS media feature prefers-color-scheme** → `dark`. Сайт слідує
системній темі, окремого перемикача немає.

**Де проходити:** чорновий прогін LG-1/LG-2/LG-5/LG-8 можливий локально; **фінальний** прогін
Частини I — на staging/прод-стенді з реальними ключами (LG-9 — саме про деплой).

### LG-1 — Гість: каталог → пошук → PDP → кошик

Мета: гість знаходить товар за 2 хвилини і доносить його до чекаута (подорож Г1–Г3).

- [ ] **Головна + регресія навігації.** **Зроби:** відкрий головну, проклацай хедер/футер,
      банери, категорії; повтори у темній темі. **Має бути:** верстка ціла в обох темах,
      жодне посилання не веде в 404, банери/слоти головної рендеряться.
- [ ] **Мега-меню «Каталог» (десктоп).** **Зроби:** відкрий «Каталог», проведи мишкою по
      кореневих категоріях; пройди Tab-ом; `ArrowRight`/`ArrowLeft`; `Escape`. **Має бути:**
      права панель миттєво показує підкатегорії без мерехтіння; стрілки переносять фокус;
      Escape закриває і повертає фокус на кнопку; клік по категорії/підкатегорії веде на
      `/categories/<slug>`.
- [ ] **Мобільне меню — акордеон.** **Зроби:** на вузькому в'юпорті відкрий бічне меню; тапни
      шеврон біля категорії з дітьми; тапни назву категорії. **Має бути:** шеврон розгортає
      підкатегорії на місці без навігації; назва навігує і закриває меню; дві категорії можуть
      бути розгорнуті одночасно.
- [ ] **Пошук з одруками (потрібен Meilisearch).** **Зроби:** пошукай «айфон», «афйон»,
      `ihpone`. **Має бути:** всі три знаходять iPhone-товари (підказки + `/search`).
- [ ] **Rollup кореневої категорії.** **Зроби:** у каталозі клікни чіп кореневої категорії,
      товари якої лежать у підкатегоріях. **Має бути:** сітка показує товари всіх підкатегорій;
      під активним чіпом — другий рядок чіпів прямих підкатегорій.
- [ ] **Посадкова `/categories/[slug]`.** **Зроби:** відкрий сторінку кореневої та вкладеної
      категорії. **Має бути:** H1 з назвою, опис, хлібні крихти «Головна → [батько →]
      категорія», чіпи підкатегорій, грид товарів з усім піддеревом; фільтри/сортування/
      пагінація працюють поверх slug; «Скинути фільтри» не скидає категорію.
- [ ] **Перелінковка категорій.** **Зроби:** пройди по лінках категорій: мега-меню, мобільне
      меню, плитки головної, хаб `/categories`, крихта на PDP. **Має бути:** всі ведуть на
      `/categories/<slug>`.
- [ ] **Фільтр «Виробник».** **Зроби:** у каталозі обери виробника. **Має бути:** сітка
      звужується, `?brandId=` в URL, комбінується з категорією/ціною/пошуком; знімний чіп
      «Виробник: X»; «Очистити все» прибирає і бренд.
- [ ] **«Популярні бренди».** **Зроби:** відкрий `/categories`. **Має бути:** стрічка показує
      реальні активні бренди (не стаб), кожен веде на `/products?brandId=…`.
- [ ] **Бренд на PDP.** **Зроби:** відкрий товар із брендом. **Має бути:** назва бренду над
      заголовком, веде на `/products?brandId=…`.
- [ ] **ModelPicker на головній.** **Зроби:** обери бренд → модель → «Підібрати». **Має
      бути:** селект моделі заблокований до вибору бренду; сабміт веде на
      `/products?deviceModelId=<id>` і сітка фільтрується.
- [ ] **Фільтр «Сумісний пристрій» у каталозі.** **Зроби:** у сайдбарі обери бренд→модель,
      поєднай з категорією/ціною. **Має бути:** URL несе `?deviceModelId=`; чіп «Пристрій: X»
      знімається.
- [ ] **PDP cross-sell «Сумісні аксесуари».** **Зроби:** відкрий товар із заданою сумісністю.
      **Має бути:** секція з іншими товарами під ту саму модель (поточний виключений); без
      compat — секції немає.
- [ ] **PDP: вкладка «Характеристики» + highlights.** **Зроби:** відкрий товар зі збереженими
      характеристиками. **Має бути:** рядки ключ/значення (BOOLEAN → «Так/Ні», одиниці
      додаються); стрічка «Коротко про товар»; без специфікацій — empty-state.
- [ ] **Фасети `?specs=` у каталозі.** **Зроби:** обери категорію з фільтрованими
      специфікаціями, обери значення у блоці «Характеристики». **Має бути:** URL отримує
      `?specs=key:value`, сітка звужується, чіп фасета знімається.
- [ ] **Вкладка «Хіти продажів».** **Зроби:** на головній відкрий таб «Хіти продажів» (потрібні
      PAID-замовлення в БД). **Має бути:** товари за проданою кількістю; порожня БД замовлень
      не валить секцію.
- [ ] **`/promo` — живі знижки.** **Зроби:** відкрий `/promo`. **Має бути:** сітка «Знижки» —
      лише товари зі знижкою (server `onSale`), «Промокоди» — з реального
      `/api/discounts/active`, не хардкод.
- [ ] **Контакт-форма + анти-спам.** **Зроби:** на `/contact` надішли форму; потім швидко
      надішли 6 разів поспіль. **Має бути:** справжній сабміт з екраном успіху; 6-й → 429 з
      дружнім повідомленням; в адмінці `/messages` звернення видно, лічильник непрочитаних
      росте (стик LG-5).
- [ ] 🔒 **(до TASK-331) Муляж на `/cart` знято.** **Зроби:** наповни кошик гостем, відкрий
      `/cart`. **Має бути:** НЕМАЄ radiogroup «Оплата онлайн» (сьогодні він default-checked!)
      і мертвих селектів міста/способу доставки, які нічого не роблять
      (`cart-delivery-payment.tsx` — presentational-only, стан 🎭). Поки TASK-331 не
      виконаний — цей пункт ❌ за замовчуванням.
- [ ] 🔒 **(до TASK-338) Гостьовий чекаут.** **Зроби:** гостем (розлогінений) натисни
      «Оформити замовлення». **Має бути:** гість оформлює замовлення БЕЗ акаунта (контакти +
      НП + спосіб оплати), після покупки — пропозиція створити акаунт; гість бачить статус
      замовлення за лінком з листа (E-17). Сьогодні гостя редіректить на
      `/login?redirect=/checkout` (стан ⬜, Г1.7) — до TASK-338 пункт ❌ за замовчуванням.

### LG-2 — Покупець: реєстрація → чекаут → підтвердження → скасування

Мета: зареєстрований покупець проходить повний цикл грошей без оператора (подорож П1).

- [ ] **Реєстрація + злиття гостьового кошика (E-05).** **Зроби:** гостем додай 2 товари в
      кошик і 1 у «Обране»; зареєструй Покупця B (нормальний пароль; слабкий — LG-7) або
      увійди Покупцем A. **Має бути:** товари гостя в кошику/обраному одразу після входу,
      без дублікатів; F5 нічого не губить.
- [ ] **Чекаут наскрізно.** **Зроби:** `/checkout` → 2 кроки (Доставка → Підтвердження):
      місто/відділення НП (з ключем — автопідказки, LG-4), телефон з маскою `+380…` →
      «Підтвердити». **Має бути:** редірект на `/orders/{id}/confirmation`; адреса/товари/суми
      збігаються; порожній кошик → `/checkout` редіректить геть.
- [ ] **Купон + акційна ціна (E-08).** **Зроби:** застосуй валідний промокод до кошика з
      акційним товаром (compareAtPrice). **Має бути:** знижка рахується від поточних (уже
      акційних) цін і не робить суму від'ємною. Подвійна знижка — **дозволений** стан
      (рішення у звіті §10); фіксуй лише арифметичні помилки.
- [ ] **ГОЛОВНЕ (money-path): знижка НЕ діє на послуги.** **Зроби:** застосуй промокод і
      познач додаткову послугу; оформи замовлення. **Має бути:** знижка порахована ЛИШЕ від
      суми товарів; `total = subtotal + доставка + послуги − знижка` — різниця сум до/після
      позначення послуги дорівнює повній ціні послуги.
- [ ] **Сток скінчився під час чекауту (E-01).** **Зроби:** в адмінці постав товару з кошика
      `stock` менший за кількість у кошику; спробуй оформити. **Має бути:** сервер відхиляє
      з повідомленням про недостатній залишок; замовлення не створюється; степер кошика
      обмежує кількість до `maxQty`.
- [ ] **Купон вичерпано між `/cart` і чекаутом (E-15).** **Зроби:** створи купон з
      `maxRedemptions=1`, погаси його іншим акаунтом, потім оформи замовлення з ним у
      першому. **Має бути:** чекаут відхиляє вичерпаний купон зрозумілим повідомленням;
      ліміт не пробивається.
- [ ] **Категорію деактивовано, товар у кошику (E-14).** **Зроби:** додай товар у кошик,
      потім в адмінці деактивуй його категорію; спробуй збільшити кількість і оформити
      замовлення. **Має бути:** рядок помічений неактивним; збільшення/чекаут відхиляються
      (400), замовлення не створюється, склад не списується.
- [ ] **Статуси і скасування покупцем (E-18).** **Зроби:** відкрий `/orders`: скасуй свіже
      PENDING-замовлення; потім знайди замовлення у статусі CONFIRMED+ (постав в адмінці).
      **Має бути:** статуси українською; скасування PENDING працює без F5 і повертає склад
      (перевір в адмінці); у не-PENDING замовлення кнопки скасування **немає** (це свідоме
      обмеження — далі телефоном оператору).

### LG-3 — Оплата: повний цикл з провайдером 🔒 ЗАБЛОКОВАНО до TASK-330

> **Онлайн-оплати сьогодні не існує взагалі** (жодного провайдера/webhook; статус ставить
> адмін руками) — це 🔴 блокер запуску за рішенням власника №1. Сценарій нижче — каркас
> живої перевірки епіка TASK-330 (+ TASK-331 муляж, TASK-332 машина станів); він
> деталізується у плані 163 після вибору провайдера (порівняння — звіт §9). До виконання

- [ ] **Вибір оплати на чекауті.** **Зроби:** пройди чекаут до кроку оплати. **Має бути:**

### TASK-337 — жива Нова Пошта: ключ, keyless і вартість ≠ 0.00

**Контекст рішення.** `estimateShipping` більше не повертає тихо `0.00`, коли немає
`NP_API_KEY`. Межа проведена так:

| ключ є                               | реальні виклики                              | реальні виклики                |

| ключ є, НП лежить                    | `0.00` + лог `warn` (замовлення не блокуємо) | те саме                        |

`getDocumentDeliveryDate` — усі відповідають із порожнім `apiKey`. Контроль:
`Counterparty/getCounterparties` → `"User is undefined"`, тобто акаунт-скоуповані
