Системних архітектурних дірок немає: напрямок імпортів FSD не порушений ніде в обох
фронтендах, сирих `fetch`/`axios` поза алоулистом немає, усі `$queryRaw` параметризовані,

## CRITICAL

### C1. Відкритий редирект: санітайзер блокує CR і LF, але не TAB

`apps/store-client/src/features/auth/lib/sanitize-redirect-target.ts:26-32` і його дзеркало
`apps/store-api/src/auth/oauth/sanitize-redirect-target.ts:22`.

Функція має рівно три правила: не починається з `/` → на головну; починається з `//` або
`/\` → на головну; містить `\r` або `\n` → на головну. TAB у цьому переліку немає, а
WHATWG-парсер URL викидає TAB/LF/CR **до** розбору. Перевірено на цій машині:

```
new URL('/\t/evil.com', 'https://shop.example').href   →  https://evil.com/
```

Тобто `?redirect=/%09/evil.com` проходить усі три перевірки як «звичайний шлях, що починається
з `/`», а браузер читає його як протокол-відносний `//evil.com`.

Що з цього виходить: `login-form.tsx:117` робить `router.replace(redirectTarget)` **на маунті**,
якщо відвідувач уже авторизований — жертву викидає на чужий сайт без жодного вводу.
Неавторизований вводить справжні креденшли на нашій сторінці і опиняється на сторінці
атакувальника (`login-form.tsx:137`). Класична пост-логін передача на фішинг, тим переконливіша,
що починається на справжньому домені.

Окремо важливо: **TASK-527** (та сама дірка в адмінці, 🔴) заведено з планом «перенести сюди
`sanitize-redirect-target.ts`». У нинішньому вигляді перенесення перенесе й дірку.

**Фікс:** застосовувати перевірки до значення, з якого вже видалено те, що видалить браузер:

```ts
const stripped = raw.replace(/[\t\n\r]/g, "");
if (!stripped.startsWith("/")) return "/";
if (stripped.startsWith("//") || stripped.startsWith("/\\")) return "/";
return stripped;
```

В обох дзеркалах, з тест-кейсом `/%09/evil.com` у кожному.

### C2. Скасування замовлення повертає стік, але ніколи не звільняє погашення промокоду

`apps/store-api/src/order/order.repository.ts:1028-1094`, `payment/payment-reconcile.worker.ts:194`.

`cancelAndRestock` інкрементує `product.stock` і пише історію статусів, але не чіпає ні
`Discount.redeemedCount`, ні рядок `DiscountRedemption`. Підтверджено пошуком: у всьому `src/`
`redeemedCount` мутується рівно в одному місці (`discount.repository.ts:215`, тільки інкремент),
а `discountRedemption` має лише `create`/`count`/`findMany` — жодного `delete` чи `decrement`.

Сценарій: код із `perUserLimit = 1`, клієнт застосовує його, обирає картку, кидає платіж. Через
30 хв `expireStaleReservations` сам скасовує замовлення — товар повертається на склад, погашення
лишається. Клієнт більше **ніколи** не застосує цей код (409 `USER_LIMIT_REACHED`), і зняти
погашення з адмінки нічим: інтерфейсу для цього не існує. Те саме з `maxRedemptions: 100` —
сотня покинутих оплат зʼїдає всю акцію без жодного продажу.

**Фікс:** у ту саму транзакцію `cancelAndRestock`, симетрично до інкременту стоку, додати
`tx.discountRedemption.deleteMany({ where: { orderId } })` і `decrement` лічильника, якщо рядок
було видалено. Парний крок — повторне заявлення слота в `reviveAndReserve`
(`order.repository.ts:1099+`), інакше CANCELLED→PROCESSING дасть замовлення зі знижкою без
погашення.

### C3. Email ніде не зводиться до нижнього регістру — одна людина отримує два акаунти

`apps/store-api/src/auth/auth.repository.ts:62,78`, `auth.service.ts:167,294,436`; DTO —
`dto/register.dto.ts:11`, `dto/login.dto.ts:8`, `dto/request-password-reset.dto.ts:8`.

Жоден шар не нормалізує email: у DTO лише `@IsEmail()`, у сервісі й репозиторії — нічого.
`prisma/schema.prisma:190` — `email String @unique` на звичайному `text`; ні `citext`, ні
функціонального індексу в міграціях немає. При цьому `contact.service.ts:101`,
`newsletter.service.ts:109` і `order.service.ts:635` роблять `.trim().toLowerCase()` — правило в
проєкті існує, auth його не дотримує.

Три наслідки, від прикрого до незворотного:

1. Реєстрація як `Oleksii@Gmail.com`, вхід як `oleksii@gmail.com` → `findByEmail` не знаходить
   рядок → «Invalid credentials». Підказати нічого, бо повідомлення навмисно загальне.
2. «Забули пароль?» на іншому регістрі — мовчазний no-op (`auth.service.ts:439`), що виглядає як
   зламана пошта.
3. **Головне:** вхід через Google. Google віддає `oleksii@gmail.com`, `loginWithGoogleProfile`
   збігу не знаходить і йде в `createUserFromOAuth`. Unique-індекс регістрозалежний, тож вставка
   **проходить**. Одна людина = два акаунти, два кошики, дві історії замовлень; перший назавжди
   недосяжний через Google.

**Фікс:** `@Transform(({ value }) => typeof value === "string" ? value.trim().toLowerCase() : value)`
на всі чотири email-поля DTO (за зразком `normalizePhone` з TASK-466) + міграція-бекфіл наявних
рядків. Хвіст: `RegisterDto.email` — єдине текстове поле auth без `@MaxLength`.

### C6. Один клас у спільному тулбарі поставив 24 списки адмінки в колонку

### Auth і конфігурація

**W14. `maxAge` refresh-куки захардкоджено проти конфігурованої тривалості токена.**

## Що перевірено й підтверджено як коректне

Щоб було видно межі ревʼю, а не лише список проблем.

- **FSD** — нуль імпортів «вгору» в обох фронтендах; нуль імпортів `@/app/*` з нижніх шарів;
  крос-віджетні імпорти йдуть через публічні `index.ts`; історичний цикл
  `product-detail ⇄ product-quick-view` стереже регрес-тест.
- **Сирих `fetch`/`axios` немає** — жодного літерального виклику поза `shared/api/server-fetch.ts`
  і санкціонованим axios-мутатором; ESLint-гард `no-restricted-syntax` на місці.
- **Безпека кошика й замовлень** — IDOR немає: кожна операція скоупиться через
  `resolveCart(identity)`; CSRF накриває refresh/cart/wishlist; атрибути `set`/`clear`
  refresh-куки збігаються повністю, тож кука чиститься.
- **Атомарність погашення знижки чиста** — `tryIncrementRedeemed` робить умовний `updateMany` з
  порівнянням колонок, це єдиний шлях погашення, і є int-тести на реальному Postgres із чотирма
  гоночними сценаріями. (Дірка не в атомарності, а у звільненні — C2.)
- **Межі грошей у знижках чисті** — відсоток округлюється до цента, сума клампиться
  `Math.min(rawCents, subtotalCents)`, відʼємний підсумок неможливий; база знижки однаково
  рахується в кошику й замовленні.
- **Пастка boolean-DTO не відтворюється** — перевірені query-DTO читають `obj[key]` у
  `@Transform`, з тестами.
- **`@IsUUID(4)` з плану 179 більше не існує** — 85 входжень у `store-api` вже `'loose'`;
  лишився один без режиму (S2) і чотири `ParseUUIDPipe`, які так і задокументовані.
- **Мертвих модулів і невикористаних npm-залежностей немає** — евристика по 2226 файлах дала нуль
  справжніх спрацювань; усі підозрілі пакети мають вжиток; скрипти `package.json` не биті.
- **Форматери дат в адмінці консолідовані**, і це стереже тест-гард; жодного `en-US` у
  `apps/*/src` не лишилось.
- **Ключі прав** — жодного сирого рядка поза тестами; звірка каталогу бекенда з
  `@RequirePermission` дала порожні обидві різниці.
- **Інвалідація кешу React Query** — ключів із неповними параметрами не знайдено в жодній апці;
  `exact: true` не вживається, тож префіксні ключі накривають фільтровані сторінки.
- **Форми** — правила `docs/conventions/forms.md` витримані: усі `useState`, засіяні асинхронним
  пропом, мають guard; `useDebouncedCallback` скрізь імпортується прямо, не з бареля.
- **Парольна політика синхронна** в трьох копіях байт у байт; `console.log` у проді — лише в
  CLI-скриптах; `any` — 13 на весь монорепо поза тестами й генератом.
- **`.claude/` у синхроні з `CLAUDE.md`** — 7 агентів, 8 команд, 10 скілів, зайвих немає.

## Чого це ревʼю не покриває

- Не пентест: інвентар захисту складено в плані 179 і не перевірявся заново.
- Не перевірялися наживо ні LiqPay, ні Нова Пошта, ні пошта — лише код.
- Модулі поза пʼятіркою (`search`, `catalog-import`, `media`, `payment`, `publishing`, `staff`…)
  дивилися лише там, куди вів слід із ревʼюваних; окремого проходу по них не було.
- Продуктивність і навантаження — не предмет (це TASK-392 / `docs/deploy/10-capacity.md`).
