## 5. Розриви процесу замовлення

Наскрізний процес «замовлення → гроші → доставка → закриття» має розриви на кожній ланці:

1. **Немає серверної машини станів** — `admin-order.controller.ts:183`: бекенд записує
   будь-який запитаний статус «як є»; адмін-UI
   (`features/order-status-update/model/transitions.ts`) пропонує всі статуси крім поточного.
   7 статусів замовлення + 4 платіжні — без жодного графа переходів. Наслідки: скасування
   після відправки без наслідків для стоку/грошей (E-07), засмічена історія при конкурентному
   редагуванні (E-11, last-write-wins), і головне — **webhook оплати не має на що лягти**
   (TASK-330 залежить від TASK-332). → **TASK-332 🔴**
2. **Refund — лейбл** (E-12): REFUNDED не рухає гроші (провайдера немає) і не повертає сток
   (авто-restock свідомо лише з PRE_SHIPMENT: PENDING/CONFIRMED/PROCESSING, захист
   `restockedAt` від подвійного повернення). → **TASK-330-C 🔴** + процес повернення
   (RMA-мінімум) → TASK-340 🟡
3. **Листи: лише 3 шаблони** (order-confirmation, password-reset, account-locked) через
   MailOutbox (cron щохвилини, ретраї). Немає «Відправлено + ТТН» — причому **поля ТТН немає
   навіть у схемі `Order`** (жодного `trackingNumber` — знахідка подорожей, user-stories
   §5.2): TASK-335 має включати міграцію + поле у формі адмінки, а не лише шаблон листа.
   Скасування/зміна статусу теж не сповіщає покупця (user-stories §5.8 — переглянути при
   TASK-335, той самий outbox). → **TASK-335 🟡**
4. **Оператор не може знайти замовлення** за номером/email/телефоном («де моє замовлення?» —
   найчастіший дзвінок): у `/orders` лише вкладки-фільтри. Внутрішніх нотаток оператора
   немає (`Order.notes` — це коментар покупця з чекаута). → **TASK-336 🟡**
5. **Телефонні замовлення** — оператор не може ані створити замовлення з адмінки, ані
   відредагувати позиції/адресу (обхід: скасувати + клієнт оформлює заново). → TASK-341 🟢
6. **Гостьові замовлення неможливі на рівні БД**: `Order.userId` обовʼязковий із
   `onDelete: Restrict` (`schema.prisma:334-341`) — TASK-338 включає міграцію (nullable
   `userId` + контакти гостя + токен доступу до статусу, Г1.9/E-17), а не лише зняття guard.
   → **TASK-338 🔴**

Що при цьому **справне** (перевірено кодом, живі перевірки — LG-2/LG-5): декремент стоку при
створенні, `CHECK stock >= 0`, race-safe купони (maxRedemptions/perUserLimit), транзакційне

## 7. Безпека

**Що міцне** (ревʼю 2026-07-13 + аудит TASK-313, статично): жодного IDOR (усі `:id`
скоупляться по userId), детекція повторного використання refresh-токена, Argon2, підписаний

Pino-redaction. Це не перевірялось наживо → LG-7.

**Блокерне і передзапускове:**

1. **TASK-314 — 2FA/lockout відсутні + Gmail-обхід** (у блокерному списку §1). Найгостріше —
   обхід: `loginWithGoogleProfile` віддає токен **із наявною роллю рядка**, тож адмін із

   з огляду на мітигейт — блокерним є пакет: lockout після N спроб + верифікація мітигейту

   бана/деактивації — для ADMIN/MANAGER розглянути звірку в межах TASK-314.

   `scripts/create-admin.ts`; зміни власного пароля, зміни ролі, скидання чужого пароля —
