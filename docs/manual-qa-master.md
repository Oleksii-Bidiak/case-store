# Ручне QA-тестування — головний чекліст (від А до Я)

> **Для кого цей документ:** для людини, яка **не знається на QA**. Тут кожна перевірка
> розписана покроково: що зробити і що має статися. Іди зверху вниз, не перестрибуй.
>
> **Що ми перевіряємо:** весь застосунок одразу — вітрину для покупців (`store-client`),
> адмін-панель (`store-admin`) і сервер/API (`store-api`). Автотести вже зелені, але живий
> застосунок у браузері майже не перевіряли руками. Саме це ми й робимо.
>
> **📋 Трекер прогресу:** короткий «титульний аркуш» зі станом усіх розділів —
> [`manual-qa-progress.md`](./manual-qa-progress.md). Відмічай там розділи в міру проходження.

## 🧭 Як користуватися цим документом (прочитай перед стартом)

**Що означають позначки:**

- `- [ ]` — перевірка ще не зроблена. Постав `x` між дужок → `- [x]`, коли пройшла успішно.
- ✅ — перевірка пройшла, все як треба.
- ❌ — щось не так. **Не виправляй сам.** Просто напиши прямо в рядку, що сталося, наприклад:
  `❌ кнопка "Купити" не натискається, у консолі помилка`. Потім ці ❌ стануть задачами в `BACKLOG.md`.

**Формат кожної перевірки:**

> **Зроби:** конкретна дія (куди клікнути, що ввести).
> **Має бути:** що очікувати на екрані/в логах.
> Якщо побачив інше → постав ❌ і коротко опиши.

**Міні-глосарій (терміни, що зустрінуться):**

- **Стек** — усі частини застосунку, запущені разом (база, сервер, два сайти).
- **DevTools** — панель розробника в браузері. Відкривається клавішею **F12** (або
  ПКМ → «Переглянути код» / «Inspect»).
- **Console (Консоль)** — вкладка в DevTools, де видно помилки JavaScript. Червоний текст = погано.
- **Network (Мережа)** — вкладка в DevTools, де видно всі запити сайту до сервера (адреса,
  статус-код 200/404/401 тощо).
- **Cookie** — маленький файл, який браузер зберігає для сайту (наприклад, щоб пам'ятати,
  що ти залогінений). Дивитися: DevTools → вкладка **Application** → **Cookies**.
- **Swagger** — веб-сторінка зі списком усіх запитів API, де їх можна викликати вручну.
  Відкривається за адресою `http://localhost:3001/api`.
- **Статус-код** — число-відповідь сервера: `200` = успіх, `201` = створено, `400/401/403/404/409` = різні
  помилки, `429` = «забагато запитів». Бачиш їх у вкладці Network.

## Крок 0. Автотести (запусти найперше, браузер не потрібен)

> Це швидка перевірка, що код узагалі робочий. Виконуй команди в терміналі **з кореня
> репозиторію** (папка `store-ai`). Якщо хоч одна впаде — спершу розберись із нею, далі не йди.

- [✅] **Зроби:** `npm run typecheck` → **Має бути:** без помилок (3 робочі простори: api, client, admin).
- [✅] **Зроби:** `npm run lint` → **Має бути:** без помилок.
- [✅] **Зроби:** `npm run test` → **Має бути:** усі тести зелені (store-api ~323, store-client ~16).
- [✅] **Зроби:** `npm run test:e2e` → **Має бути:** ~170 e2e-тестів зелені.
- [✅] **Зроби:** `npm run build` → **Має бути:** усі три застосунки збираються без помилок.

> ⚠️ Ці тести перевіряють логіку, але **не** перевіряють: реальну поведінку в браузері,

## Крок 1. Підготовка: запусти весь стек

> Тобі знадобиться **чотири окремі вікна терміналу** (бо кожна команда працює постійно й не
> завершується). Виконуй по черзі.

- [✅] **Термінал 1 — база даних (Docker):** `docker compose up -d`
  → **Має бути:** піднялися PostgreSQL (порт 5432) і Redis (порт 6379), без помилок.
- [✅] **Застосуй міграції:** `npm run db:migrate`
  → **Має бути:** база оновлена, повідомлення про успіх.
- [✅] **Заповни базу даними (seed):** `npm run db:seed`
  → **Має бути:** у консолі `✓ Users: admin=…, customer=…` і створені товари.
- [✅] **Термінал 2 — сервер API:** `npm run start:dev -w apps/store-api`
  → **Має бути:** сервер працює на `http://localhost:3001` (Swagger: `http://localhost:3001/api`).
- [✅] **Термінал 3 — вітрина:** `npm run dev -w apps/store-client`
  → **Має бути:** сайт відкривається на `http://localhost:3000`.
- [✅] **Термінал 4 — адмінка:** `npm run dev -w apps/store-admin`
  → **Має бути:** панель відкривається на `http://localhost:3002`.

### ⚠️ Найважливіша перевірка перед стартом: адреса API в обох сайтах

> Сайти звертаються до сервера за адресою з налаштування `NEXT_PUBLIC_API_URL`. Через
> особливість бібліотеки Axios ця адреса **не має закінчуватися на `/api`** — інакше кожен
> запит перетвориться на `…/api/api/…` і дасть помилку 404. Шлях `/api` уже «зашитий» у самих
> запитах, тож в адресі він не потрібен.

- [✅] **Зроби:** відкрий файл `apps/store-client/.env.local`
  → **Має бути:** `NEXT_PUBLIC_API_URL=http://localhost:3001` (БЕЗ `/api` в кінці).
- [✅] **Зроби:** відкрий файл `apps/store-admin/.env.local`
  → **Має бути:** теж `NEXT_PUBLIC_API_URL=http://localhost:3001` (БЕЗ `/api`).
  Якщо в кінці є `/api` — прибери його та перезапусти відповідний сайт.
- [✅] **Перевір у браузері:** відкрий `http://localhost:3000`, натисни **F12 → Network**, онови
  сторінку → **Має бути:** запити йдуть на `http://localhost:3001/api/...` (один `/api`,
  а не `/api/api/...`).

### Перемикачі режиму `MAIL_ENABLED` і `REDIS_HOST`

- [ ] `MAIL_ENABLED` — за замовчуванням `false` (листи не шлються). Вмикаєш `true` лише для §C4.
      Детальна інструкція — у наступному розділі.
- [ ] `REDIS_HOST` — якщо заданий, працює кеш + захист від частих запитів через Redis; якщо ні —
      через пам'ять (теж робоче). Детальна інструкція — у наступному розділі.

### Тестові акаунти (створюються при seed)

- [✅] **Адмін:** `admin@store.com` / пароль `Admin123!` — для адмін-панелі.
- [✅] **Покупець A:** `customer@store.com` / пароль `Customer123!` — основний покупець.
- [❌ - Цей email вже зареєстровано.] **Покупець B:** окремого немає в seed — **зареєструй сам** другий акаунт (будь-яка інша
  пошта, напр. `userb@store.com`) для перевірок «чужого замовлення» та злиття кошиків.

## 📘 Детальна інструкція: перемикачі `MAIL_ENABLED` і `REDIS_HOST`

> Обидві змінні — це **перемикачі режиму**. Твоє завдання: усвідомлено вибрати режим і
> переконатися, що застосунок поводиться так, як цей режим обіцяє. **Не плутай штатну поведінку
> з багом** (наприклад, «лист не надіслано» при вимкненій пошті — це норма, а не помилка).
>
> Усі зміни робиш у файлі `apps/store-api/.env`. Після **будь-якої** зміни в `.env` треба
> **перезапустити** сервер (у терміналі 2: Ctrl+C, потім знову `npm run start:dev -w apps/store-api`),
> бо налаштування читаються лише при старті.

### Частина 1 — `MAIL_ENABLED` (листи-підтвердження замовлення)

#### Режим A (за замовчуванням) — пошта ВИМКНЕНА. Перевір першим.

- [✅] 1. У `apps/store-api/.env` переконайся, що рядок `MAIL_ENABLED=false` або взагалі відсутній.
- [✅] 2. Запусти весь стек (як у Кроці 1).
- [❌] 3. На вітрині (`:3000`) залогінься як Покупець A, додай товар у кошик, оформи замовлення.
  **Фактично**: на етапі Доставка кнопка Підтвердити замовлення не працює - тільки на підсвічення невалідності полів, якщо все коректно то не працює, в бек нічого не летить.
- [❌-не вдалось оформити] 4. **Має бути:** замовлення оформилось, відкрилась сторінка підтвердження. **Лист НЕ
  приходить — це правильно.**
- [❌] 5. Подивись у термінал 2 (сервер) → **Має бути** рядок типу
  `Mail disabled — skipping order confirmation to <пошта>`. Помилок немає → ✅.

#### Режим B — пошта УВІМКНЕНА (тільки для §C4)

«Ethereal» — безкоштовна фейкова поштова скринька для тестів: реальні листи нікому не йдуть,
а лягають у веб-скриньку, яку бачиш лише ти.

- [ ] 1. Відкрий `https://ethereal.email` → натисни **«Create Ethereal Account»**.
- [ ] 2. Сайт покаже `Host`, `Port`, `Username`, `Password`. Не закривай вкладку.
- [ ] 3. У `apps/store-api/.env` встав (User/Pass — з кроку 2):
     ```
     MAIL_ENABLED=true
     SMTP_HOST=smtp.ethereal.email
     SMTP_PORT=587
     SMTP_USER=<Username з Ethereal>
     SMTP_PASS=<Password з Ethereal>
     MAIL_FROM="Store <no-reply@store.test>"
     ```
- [ ] 4. **Перезапусти** сервер (термінал 2).
- [ ] 5. На вітрині знову оформи замовлення.
- [ ] 6. На вкладці Ethereal відкрий **«Messages»** → **Має бути** лист-підтвердження.
- [ ] 7. Відкрий лист → **Має бути** коректно: у темі номер замовлення; у тілі список товарів,
     кількість, суми, адреса. → ✅
- [ ] 8. Після тесту поверни `MAIL_ENABLED=false` і перезапусти сервер.

### Частина 2 — `REDIS_HOST` (кеш + обмеження частоти запитів)

#### Режим A (найпростіший) — `REDIS_HOST` НЕ задано (пам'ять). Підходить для більшості перевірок.

- [ ] 1. У `apps/store-api/.env` переконайся, що рядка `REDIS_HOST=...` немає (або закоментований).
- [ ] 2. Запусти стек → **Має бути:** сервер стартує без помилок (це і є перевірка fallback).
- [ ] 3. **Кеш:** на вітрині відкрий список товарів, онови ще раз → **Має бути:** друге
     завантаження таке ж або швидше, без помилок.
- [ ] 4. Особливість: після перезапуску сервера кеш стирається (бо живе в пам'яті). Це нормально.

#### Режим B — `REDIS_HOST` задано (кеш у Redis). Потрібно для §C5.

- [ ] 1. Підніми Redis: `docker compose up -d redis`.
- [ ] 2. У `apps/store-api/.env` додай:
     ```
     REDIS_HOST=localhost
     REDIS_PORT=6379
     ```
- [ ] 3. **Перезапусти** сервер.
- [ ] 4. На вітрині відкрий список товарів (щоб щось закешувалося).
- [ ] 5. Перевір, що Redis реально працює. У терміналі:
     ```
     docker compose exec redis redis-cli KEYS "product:*"
     docker compose exec redis redis-cli KEYS "throttle:*"
     ```
     **Має бути:** після перегляду товарів з'являються ключі `product:*`; після кількох
     запитів — `throttle:*`. Порожній список → застосунок не підключився до Redis (перевір
     `REDIS_HOST` і чи запущений контейнер).
- [ ] 6. **Має бути:** тепер кеш переживає перезапуск сервера (дані в Redis, а не в пам'яті).
- [ ] 7. **Стійкість:** зупини Redis (`docker compose stop redis`), онови список товарів →
     **Має бути:** сторінка працює **без помилки 500** (просто без кешу). Поверни:
     `docker compose start redis`.

> **Підсумок:** ❌ став лише тоді, коли поведінка **не збігається** з обраним режимом
> (наприклад, `MAIL_ENABLED=true` + правильні креди, а листа в Ethereal немає; або `REDIS_HOST`
> заданий і Redis запущений, а ключів у `redis-cli` нема).

# ЧАСТИНА C — Сервер/API напряму (через Swagger, `:3001/api`)

> Тут перевіряємо сервер без сайтів. Відкрий `http://localhost:3001/api` — це Swagger, де можна
> натискати запити вручну. Щоб виконувати захищені запити, спершу залогінься через
> `POST /api/auth/login` і встав отриманий токен у кнопку «Authorize».

## C1. Базові контракти та валідація

- [ ] **Зроби:** виконай будь-який запит → **Має бути:** відповідь має вигляд `{ data, meta? }`
      (або `{ error, message, statusCode }` при помилці).
- [ ] **Зроби:** `GET /api/orders` під Покупцем A і під B → **Має бути:** кожен бачить лише свої
      замовлення; `?status=PENDING` фільтрує; `?page=2&limit=5` гортає; `?status=FOO` → 400;
      `?limit=500` → 400 (максимум 100).
- [ ] **Зроби:** створи замовлення з порожнім кошиком → **Має бути:** 400 «Cart is empty»; якщо
      кошик ніколи не створювали → 404 «Cart not found».
- [ ] **Зроби:** надішли примітку понад 500 символів або зіпсовану адресу → **Має бути:** 400.
- [ ] **Зроби (IDOR):** Покупцем B відкрий `GET /api/orders/{номер замовлення A}` → **Має бути:**
      404 (сервер не зізнається, що таке замовлення існує).

## C2. Цілісність складу (КРИТИЧНО)

- [ ] **Зроби:** поклади в кошик N штук, потім зменш запас варіанта нижче N і оформи →
      **Має бути:** 400, замовлення не створено, запас не змінився; на вітрині — повідомлення
      про помилку, кошик НЕ очищається.
- [ ] **Зроби (одночасне перевищення):** запас = 1; майже одночасно надішли два `POST /api/orders`
      від A і B → **Має бути:** рівно один 201, інший 409; запас стає 0, **ніколи не від'ємний**;
      той, хто програв, повністю відкочується.
- [ ] **Зроби (повернення при скасуванні):** оформи (запас впав) → власник
      `PATCH /api/orders/{id}/cancel` → **Має бути:** 200 CANCELLED, запас повернувся; повторне
      скасування / не-PENDING → 409; інший користувач → 404.
- [ ] **Зроби:** спробуй зробити запас від'ємним → **Має бути:** база відхиляє (обмеження
      `CHECK (stock >= 0)`).

## C3. Безпека

- [ ] **Зроби:** виклич адмінський запит без токена / з токеном покупця / з токеном адміна →
      **Має бути:** 401 / 403 / 200 відповідно.
- [ ] **Зроби (CSRF):** мутуючий запит на cookie-сесії без заголовка `x-csrf-token` → **Має
      бути:** 403; з валідним токеном — проходить; запит на Bearer-токені — звільнений від CSRF.
- [ ] **Зроби:** глянь заголовки відповіді → **Має бути:** присутні заголовки Helmet (CSP у

- [ ] **Зроби (rate-limit):** багато разів швидко виклич `POST /api/auth/refresh` → **Має бути:**
      після ліміту 429; загальний ліміт 100 запитів / 60 секунд.
- [ ] **Зроби (CORS):** перевір, що дозволені лише налаштовані джерела.
