# Бекапи та відновлення — ранбук власника (TASK-308)

> **Для кого:** для власника без технічного бекграунду. Команди можна копіювати як є.
>
> **Головна думка цього документа:** бекап, який ви жодного разу не відновлювали, —
> це не бекап, а надія. Розділ 5 («Навчальна тривога») — найважливіший тут. Пройдіть
> його **на staging** до того, як на проді з'являться справжні замовлення.

---

## 0. Що саме ми бекапимо і чому саме це

Магазин складається з трьох частин. Дві з них відновлюються з git за хвилини, третя — ніколи.

| Що                         | Де живе             | Якщо втратити                                       |
| -------------------------- | ------------------- | --------------------------------------------------- |
| **Код**                    | GitHub              | Нічого страшного — усе в git                        |
| **База даних**             | том `postgres_data` | **Замовлення, клієнти, товари, контент — назавжди** |
| **Завантажені зображення** | том `uploads_data`  | **Усі фото товарів — назавжди**                     |

Про зображення забувають майже завжди. Вони **не в базі** і **не в git** — вони просто
лежать файлами на диску сервера. Бекап, який охоплює лише базу, відновить вам магазин,
у якому кожне фото — «битий» значок. Тому `scripts/backup.sh` бекапить **обидва** томи.

---

## 1. Що потрібно налаштувати один раз

### 1.1 Ключ шифрування (`age`)

Бекапи містять персональні дані клієнтів. Вони шифруються **публічним** ключем, а
**приватний ключ ніколи не лежить на сервері** — інакше той, хто зламає сервер, отримає
разом із ним усі історичні бекапи. Сервер уміє створювати бекапи, які сам не може прочитати.

**На своєму ноутбуці** (не на сервері):

```bash
age-keygen -o backup-key.txt
```

Файл виглядатиме так:

```
# public key: age1qy8f...   ← ПУБЛІЧНИЙ — його можна класти на сервер
AGE-SECRET-KEY-1XYZ...      ← ПРИВАТНИЙ — тільки у ваш менеджер паролів
```

> ⚠ **Втратите приватний ключ — втратите всі бекапи.** Збережіть його щонайменше у двох
> місцях (менеджер паролів + роздрукований аркуш у шухляді). Це не перебільшення: без
> нього зашифровані архіви — просто набір випадкових байтів.

Публічний ключ (`age1...`) додайте у **`.env.production` на сервері**:

```
AGE_PUBLIC_KEY=age1qy8f...
```

### 1.2 Off-site сховище (Backblaze B2)

Бекап, що лежить лише на тому ж сервері, захищає рівно від одного сценарію — невдалої
міграції. І ні від чого більше: ні від згорілого диска, ні від видаленого VPS, ні від
шифрувальника. Тому копія має їхати геть із сервера.

1. Зареєструйтесь на [Backblaze B2](https://www.backblaze.com/b2) (перші 10 ГБ безкоштовно).
2. Створіть bucket, напр. `store-ai-backups`, **private**.
3. Створіть Application Key з доступом лише до цього bucket.
4. У самому B2 налаштуйте **Lifecycle rule** — видаляти файли старші за 90 днів.
   Робіть це **на боці bucket, а не на сервері**: зламаний сервер не зможе стерти вашу
   історію бекапів.
5. На сервері: `rclone config` → новий remote типу `b2` з іменем `b2`.
6. У `.env.production`: `RCLONE_REMOTE=b2:store-ai-backups`

### 1.3 Щонічний запуск

На сервері:

```bash
sudo apt install -y age rclone
crontab -e
```

Додайте рядок (бекап о 03:30 щоночі, лог у файл):

```
30 3 * * * cd /opt/store-ai && ./scripts/backup.sh >> /var/log/store-backup.log 2>&1
```

## 2. Зробити бекап прямо зараз

```bash
cd /opt/store-ai
./scripts/backup.sh
```

Скрипт **падає з помилкою**, якщо щось пішло не так — він ніколи не залишить файл, який
лише _схожий_ на бекап. Зокрема, після дампу він одразу перевіряє, що дамп **читається**
(`pg_restore --list`): порожній або обрізаний файл теж має розмір, тож самої лише
перевірки «файл не порожній» недостатньо.

**Перевірити, що нічний бекап справді відпрацював:**

```bash
tail -20 /var/log/store-backup.log     # має закінчуватись "backup: done — <дата>"
ls -lh /opt/store-ai/backups/          # свіжі .age файли
rclone ls b2:store-ai-backups | tail   # і вони доїхали в хмару
```

## 3. Скачати бекап до себе на ноутбук

```bash
# з сервера на ноутбук
scp deploy@<сервер>:/opt/store-ai/backups/db-<дата>.dump.age .

# розшифрувати (приватним ключем, який лежить у вас)
age -d -i backup-key.txt -o db.dump db-<дата>.dump.age
```

Тепер `db.dump` — звичайний файл дампа Postgres. Його можна залити куди завгодно: у
локальну базу, до іншого хостера, у будь-який сервіс. **Ви не заручник свого хостингу.**

## 4. Відновлення

### 4.1 Випадково видалили адміна (або забули пароль)

Найчастіший і найменш страшний випадок. **Не треба нічого відновлювати з бекапу.**

```bash
cd /opt/store-ai
docker compose -f docker-compose.prod.yml exec store-api \
  node dist/scripts/create-admin.js --email ваша@пошта.com
```

Скрипт надрукує новий пароль **один раз**. Він:

- створить адміна, якщо його немає;
- або **підвищить існуючий акаунт до ADMIN і скине йому пароль**;
- зніме позначку «видалено» (`deletedAt`) і активує акаунт;
- **не чіпає жодної іншої таблиці** — жодного товару, жодного замовлення.

> ⚠ **Не запускайте `db:seed` з `ALLOW_PROD_SEED=true`**, щоб «відновити адміна». Це не
> те, що ви думаєте: сід заллє поверх ваших живих даних цілий демо-каталог — товари,
> категорії, замовлення, відгуки. Саме так блокування доступу перетворюється на катастрофу.

### 4.2 Видалили щось важливе в адмінці (товари, категорії)

Не відновлюйте всю базу — ви втратите всі замовлення, зроблені після бекапу.
Витягніть **одну таблицю** з бекапу:

```bash
# 1. підняти "чернеткову" базу поруч, з бекапу
docker run --rm -d --name scratch -e POSTGRES_PASSWORD=x -p 55433:5432 postgres:17-alpine
age -d -i backup-key.txt db-<дата>.dump.age | \
  docker exec -i scratch pg_restore -U postgres -d postgres --no-owner

# 2. подивитись, що там було
docker exec scratch psql -U postgres -c "SELECT id, name FROM products WHERE deleted_at IS NULL;"

# 3. перенести потрібні рядки в бойову базу — вручну, свідомо
docker exec scratch pg_dump -U postgres -t products --data-only > products.sql

# 4. прибрати чернетку
docker stop scratch
```

Саме заради цього дамп робиться у форматі `custom` (`-Fc`), а не простим SQL: із нього
можна дістати **одну таблицю**, не чіпаючи решту.

### 4.3 Погана міграція зіпсувала схему бази

1. **Спершу відкотіть образ** (див. `docs/rollback.md`) — 9 з 10 інцидентів це баг у коді,
   а не в схемі, і відкат образу нічого не коштує.
2. Якщо винна саме схема — відновлюємо з бекапу, який знімається **автоматично перед
   кожним деплоєм**:

```bash
cd /opt/store-ai
docker compose -f docker-compose.prod.yml stop store-api store-client store-admin

age -d -i backup-key.txt -o db.dump backups/db-<дата-перед-деплоєм>.dump.age
cat db.dump | docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner

docker compose -f docker-compose.prod.yml start store-api store-client store-admin
```

3. **Обов'язково після відновлення бази — переіндексувати пошук.** Індекс Meilisearch
   похідний від бази; після відкату він «пам'ятатиме» товари, яких уже немає, і пошук
   показуватиме привидів. В адмінці є кнопка, або:

```bash
curl -X POST https://api.<домен>/api/admin/search/reindex -H "Authorization: Bearer <токен>"
```

> ⚠ **Коли «відновити бекап» перестає бути правильною відповіддю.** Щойно на проді
> з'являться реальні замовлення, зроблені **після** поганої міграції, відновлення бекапу
> їх зітре. З цього моменту правильний шлях — написати нову міграцію, що виправляє
> проблему вперед, а не відкочувати базу назад.

### 4.4 Сервер помер повністю

Це і є той сценарій, заради якого все вище й робиться.

```bash
# на НОВОМУ сервері: базовий setup (docs/deploy.md), потім:
cd /opt/store-ai

# 1. підняти інфраструктуру
docker compose -f docker-compose.prod.yml up -d postgres redis meilisearch

# 2. відновити базу
age -d -i backup-key.txt -o db.dump db-<дата>.dump.age
cat db.dump | docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner

# 3. відновити ЗОБРАЖЕННЯ (те, про що всі забувають)
age -d -i backup-key.txt -o uploads.tar.gz uploads-<дата>.tar.gz.age
docker compose -f docker-compose.prod.yml up -d store-api
cat uploads.tar.gz | docker compose -f docker-compose.prod.yml exec -T store-api \
  tar xzf - -C /app/apps/store-api/uploads

# 4. підняти решту + переіндексувати пошук
docker compose -f docker-compose.prod.yml up -d
```

## 5. Навчальна тривога — зробіть це на staging

**Це найважливіший розділ.** Ви маєте один раз пройти відновлення **власними руками**,
спокійно, без інциденту — щоб під час справжньої аварії це не був перший раз.

Робіть **на staging**, не на проді.

```bash
# 1. ЗАПАМ'ЯТАТИ, скільки чого є ЗАРАЗ — це наш еталон
docker compose -f docker-compose.prod.yml -f docker-compose.staging.yml exec -T postgres \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "SELECT (SELECT count(*) FROM users) AS users,
          (SELECT count(*) FROM products) AS products,
          (SELECT count(*) FROM orders) AS orders;"

# 2. Зробити бекап
./scripts/backup.sh

# 3. ЗЛАМАТИ спеціально — видалити половину товарів
docker compose ... exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "DELETE FROM products WHERE id IN (SELECT id FROM products LIMIT 5);"

# 4. Переконатись, що справді зламали (цифра менша)
#    ...той самий SELECT count(*), що й у кроці 1

# 5. Відновити з бекапу (процедура з розділу 4.3)

# 6. ГОЛОВНЕ: звірити цифри з кроком 1
#    ...той самий SELECT count(*)
```

**Успіх — це коли цифри в кроці 6 збіглися з кроком 1.** Не «команда не видала помилку»,
а саме **збіг чисел**. Команда може відпрацювати «успішно» і не відновити нічого.

Пройдіть це один раз — і страх втратити базу зникне, бо ви знатимете, що вміти її
повертати.

## 6. Коротка пам'ятка

| Ситуація                        | Що робити                                          |
| ------------------------------- | -------------------------------------------------- |
| Видалили адміна / забули пароль | `create-admin.js` (розділ 4.1) — бекап не потрібен |
| Видалили товари/категорії       | Дістати одну таблицю з бекапу (4.2)                |
| Зламався деплой                 | Спершу **відкат образу** (`docs/rollback.md`)      |
| Погана міграція                 | Відкат образу → відновлення бази (4.3) → реіндекс  |
| Сервер згорів                   | Новий сервер + база + **зображення** (4.4)         |
| Не впевнені, що бекапи працюють | Навчальна тривога (розділ 5) — **зробіть її**      |
