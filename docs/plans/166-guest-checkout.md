# План 166 — Гостьовий чекаут

**Статус:** ⬜ до виконання (схема вже на `develop` — план 167, Фаза 0)
**Задача:** TASK-338 (🔴 блокер запуску, рішення власника 2026-07-24)
**Оркестрація:** [план 167](167-stage8-wave-orchestration.md) — WT-A (бекенд), WT-E (вітрина)

---

## Проблема

`/checkout` редіректить гостя на `/login?redirect=/checkout` — купити без акаунта
неможливо. При цьому план 102 §3 обіцяє «Guest-checkout ≈ 2 хв ✅ є», а §5 хук 1
рекламує «Замовлення за 2 хвилини — без реєстрації». Обіцянка хибна вже сьогодні,
і в рекламу її запускати не можна до виконання цієї задачі.

Кошик для гостя **уже працює** (cookie-based, `cart.service.ts` уміє зливати
гостьовий кошик при логіні). Бар'єр стоїть рівно на чекауті.

---

## Що вже готове (Фаза 0)

- `Order.userId` → **nullable**; `guestEmail`, `guestPhone`, `guestName`,
  `accessTokenHash` (unique) — у схемі й міграції.
- `GUEST_ORDER_TOKEN_TTL_DAYS` зареєстровано в чотирьох джерелах.
- Дві помилки типів, які виявила nullable-колонка, уже полагоджені **по суті, а не
  кастом** (див. комміт `c8aa321`): дашборд виключає гостей із метрики повторних
  покупок, відгуки — з бейджа «перевірена покупка».

## Бекенд (WT-A)

1. **`createOrder` приймає актора**, а не `userId`:
   `{ userId?: string } | { guest: { email, phone, name } }`. Рівно одне з двох —
   інваріант тримає застосунок, бо Prisma «одне з двох» не виражає.
2. **Зняти гард із `POST /api/orders`**; гість ідентифікується cookie кошика.
3. **Токен доступу.** Генерується при створенні гостьового замовлення, сирий
   вигляд іде **тільки** в лист; у БД — SHA-256 (той самий at-rest патерн, що в
   `RefreshToken`/`PasswordResetToken`). `GET /api/orders/guest/:token` — єдиний
   спосіб гостя побачити своє замовлення (E-17: без цього він сліпий, щойно зникла
   cookie або змінився пристрій).
4. **Анти-спам:** `@Throttle` на створення замовлення гостем жорсткіший, ніж для
   акаунтів.
5. **Злиття з акаунтом.** Якщо гість пізніше реєструється тим самим email —
   прив'язати його попередні замовлення (проставити `userId`). Гостьові колонки
   **не** чистити: вони лишаються знімком того, що реально ввели на чекауті.
6. **Лист-підтвердження** гостю через наявний outbox, з посиланням на статус.

### Про що не забути

- `MailOutbox`-лист бере email **із замовлення**, а не з користувача — для гостя
  користувача немає.
- Скасування замовлення гостем: або через токен, або взагалі ні (рішення при
  імплементації; безпечніший варіант — телефоном через оператора).
- `Order.userId` тепер nullable **скрізь**, де читається — перевірити admin-фільтри
  й картку клієнта.

## Вітрина (WT-E)

1. `/checkout` більше не редіректить гостя. Форма отримує блок контактів
   (ім'я, email, телефон) — для авторизованого лишається як є.
2. Ненав'язлива пропозиція створити акаунт **після** оформлення, не перед.
3. Сторінка статусу замовлення за токеном із листа.
4. Оновити маркетингові тексти плану 102 §5 — тепер обіцянка стає правдою.

## Ризики

| Ризик                            | Мітигація                                                                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Спам-замовлення без акаунта      | Жорсткіший throttle + (за потреби) підтвердження телефону пізніше                                                                  |
| Гість не бачить свого замовлення | Токен у листі — обов'язкова частина обсягу, не «потім»                                                                             |
| Метрики поїхали                  | Уже враховано: гості виключені з repeat-buyer rate (комміт `c8aa321`)                                                              |
| Email гостя ніхто не перевіряв   | TASK-342 верифікує адреси акаунтів; для гостя лист із токеном сам є перевіркою — якщо адреса чужа, замовлення просто не буде видно |
