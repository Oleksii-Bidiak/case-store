## Навіщо

Правило власника для обох застосунків: **спершу синхронізувати й доопрацювати макети так, щоб
реалізована верстка не деградувала, і лише потім робити нові макети й нові екрани.**

Зараз три джерела правди про вигляд вітрини розійшлися:

- **Код.** Реалізована верстка пішла далі за макети: хвилі 174, 176 і 182 переписали хедер,
  сітку каталогу, PDP, фільтри й тему.
- **`docs/design-system.md`.** Описує токени та правила, але не екрани.
- **Макети «store-client — Pages».** 19 файлів `*.dc.html`, намальованих **вручну inline-стилями**
  поверх токенів із `_ds`. Наприклад, 404-сторінка пропонує «Смартфони / Ноутбуки / Аудіо»
  магазину аксесуарів. Мок-дані Catalog, Homepage, Promo, Wishlist і Product досі без `inStock`,
  тож кожна картка там показує «Немає в наявності» (див. [ранбук](../session-runbook.md) S7.1).

Адмінки в Claude Design немає зовсім.

Макет для нового екрана (TASK-217, `/account/orders`), намальований поверх цього розриву,
успадкує його. Тому спершу потрібна синхронізація.

**Чому адмінці окремий DS-проєкт, а не копія `_ds` у Pages.** `_ds` не існує сама по собі: це
скомпільований вихід DS-проєкту (бандл реальних компонентів, маніфест, adherence-lint). Без
DS-проєкту в «store-admin — Pages» можна покласти хіба рукописний CSS токенів. На ньому артборди
знову малювалися б inline-стилями — рівно з цього виріс нинішній розрив «код ≠ макет» на вітрині.
Адмінка — це 40+ власних shadcn-примітивів (data-table, sortable-tree, rich-text-editor, combobox,
форм-бар), яких у вітринній системі немає. Її токени зараз дзеркалять вітрину, але макетувати її
вітринними компонентами означало б наперед закласти деградацію. Ціна рішення — один налаштувальний
синк і та сама процедура копіювання, що вже працює на вітрині.

**Інструменти.** `/design-sync` — слеш-команду вводить власник, вона веде інструмент `DesignSync`
(лише проєкти DESIGN_SYSTEM). Макети й артборди Claude Code пише через MCP `claude-design`: перед
першим `write_files` викликає `get_claude_design_prompt`, пише з `if_match`, звіряє через
`render_preview`. Правки власник робить у канвасі claude.ai/design, коментарі Claude Code читає через
`list_comments` і гасить через `ack_comments`.

**Правило перед кожною дизайн-сесією:** перевірити, чи дизайн-система не відстала від коду:
`git log 57aa2a97..HEAD -- apps/store-client/src/shared/ui apps/store-client/src/app/globals.css` (для
адмінки — коміт із `.design-sync-admin/NOTES.md`). Не порожньо — спершу синк.

### Д-а — що має бути в аудиті

Звіт — у теці `docs/reviews/`, файл `2026-MM-DD-storefront-design-audit.md` із датою сесії. Таблиця по
кожному маршруту `apps/store-client/src/app/**/page.tsx` (27 маршрутів) і кожному `*.dc.html` у Pages
(19 файлів): **що в коді · що в макеті · що в `design-system.md` · хто правий · дія** (оновити макет /
оновити `design-system.md` / кодова задача в плані 197). Окремо — маршрути без макета: auth-сторінки,
`/search`, `/orders/status`, `/orders/[id]/confirmation`, `/orders/guest/[token]`,
`/categories/[slug]`, `/catalog/[category]/[device]` та інші, які знайде аудит. Спірні пункти («хто
правий» неочевидно) — окремим списком, власник вирішує наприкінці сесії. Кодові розбіжності — нові
рядки в BACKLOG під планом 197.

## Ризики

- **Копія `_ds` застаріває мовчки.** Завантаження в DS-проєкт не оновлює Pages — до 2026-09-19 Pages
  жив на липневому бандлі. Копіювання — обов'язковий крок кожного синку, а не «коли згадаємо».
- **Контракт компонента змінюється під макетом.** 2026-09-19 новий `ProductCard` показав усі товари
  відсутніми, бо мок-дані не мали `inStock`. Після синку — скриншоти всіх сторінок до й після, а не
  вибірка.
- **Артборди адмінки дрейфують, поки йдуть хвилі 191 і 195.** Тому Д-ж починається з ж0: дельта
  `git log <базовий коміт>..develop -- apps/store-admin/src` і дотягування артбордів.
- **Канвас-увага власника послідовна.** Інтерактивні сесії (Д-в2, Д-г, Д-ж2/ж3, Д-н) не ставити
  паралельно одна одній.
- **`.design-sync-admin/` не має зачепити вітринний синк.** Конфіги, shim-и і `build/` адмінки живуть
  окремо; гітігнор-пастку `build/` з `.design-sync/NOTES.md` повторити для нової теки.

## Перевірка

Дизайн-сесії не змінюють коду застосунків. Перевірка — `render_preview` кожного зміненого файла,
`node scripts/check-docs-links.js` для звітів у `docs/`, для синків — validate конвертера (0 BAD) і
`git status` чистий після коміту `.design-sync*`.
