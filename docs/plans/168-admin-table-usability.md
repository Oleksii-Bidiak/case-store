## 1. Чому задача змінює форму

TASK-292 стояла 🅿️ з умовою: «розблокувати лише коли зʼявиться підтверджена потреба в
масовому виділенні». Умова спрацювала — і дала відповідь, протилежну очікуваній.

**TASK-293** (масове активування/деактивування категорій, 2026-07-13) закрив рівно цю
потребу й закрив її **без TanStack**: чекбокс-колонка, `aria-multiselectable` /
`aria-selected`, `Ctrl+Space`, `Shift+↑/↓` діапазон, tri-state «вибрати все», bulk-bar із
blast-radius-підтвердженням і батч-ендпоінт `PATCH /admin/categories/status`. Причому
generic row-model і не дав би того, що там потрібно: це `role="treegrid"` із живим
медіа-гейтом ролей, а не плоска таблиця.

Тобто гіпотезу memo 157 («якщо колись знадобиться масове виділення — правильний
інструмент TanStack») було перевірено на практиці й спростовано.

**А головне — початковий задум задачі був інший.** При актуалізації 2026-07-29 власник
сформулював його прямо: «користуватись незручно — немає фільтрів, можливості сортування,
кнопки оновлення таблиці і тому подібне; зараз seed-дані маленькі, у майбутньому це біль».
Memo 157 переформулювало TASK-292 у «пілот TanStack» і тим підмінило намір: воно розглядало
бібліотеку, а питання було про спроможності.

Цей план повертає TASK-292 до її змісту.

## 2. Виміряний стан (21 таблиця-список, 2026-07-29)

Не оцінка — прогін по всіх віджетах `store-admin`, що рендерять `<Table>`.

| Спроможність           | Стан                                                                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Сортування**         | **3 з 21** — `order-list`, `product-list`, `user-list` через `useTableSort` + `SortableColumnHeader`                                                      |
| **Кнопка оновлення**   | **0 з 21**. Жодного ручного refetch; обидва збіги grep на `refetch` виявились коментарями                                                                 |
| **Пагінація**          | немає в 6: `banner-list`, `carousel-list`, `faq-list`, `device-brand-list`, `blog-category-list`, `product-group-list`                                    |
| **Мовчазне обрізання** | `blog-post-list` і `page-list` тягнуть `limit: 100` без контролю сторінок і **без жодної ознаки, що щось обрізано** — 101-й запис просто зникає з адмінки |
| **Фільтри**            | бесповторні, є приблизно в 7 таблицях                                                                                                                     |

**Бекенд.** `sortBy` / `sortOrder` приймають лише 5 DTO: category, discount, order, product,
user. З них `discount` **уже має серверне сортування, якого фронт не використовує** —
безкоштовна перемога. Відгуки, звернення, повернення, підписники й журнал дій сортування не
приймають узагалі (`admin-review-query.dto.ts` — це `status/page/limit`, і все).

**Чому «немає оновлення».** `apps/store-admin/src/app/providers.tsx:15` ставить
`staleTime: 5 хв` **на всі** запити адмінки. `refetchOnWindowFocus` у TanStack Query типово
`true`, але при такому staleTime повернення у вкладку не робить нічого. Разом із відсутністю
кнопки це означає: таблиця показує дані пʼятихвилинної давнини й змусити її оновитись
неможливо. Це не відчувається на seed-даних і буде відчуватись щодня на живому магазині,
де двоє операторів дивляться на ту саму чергу замовлень.

## 4. Фаза 1 — TASK-353, спільний шар

Послідовно, до будь-якої роботи над окремими таблицями: усі чотири гілки Фази 2 залежать
від цього шару, і паралелити його ні з чим не можна.

### 4.1 `shared/ui/table-toolbar.tsx`

Один ряд над таблицею: слот пошуку, слот фільтрів, кнопка **«Оновити»**. Кнопка показує
стан `isFetching` (спінер) і підтверджує завершення через `aria-live`. Стилістику беремо з
наявного `shared/ui/form-actions-bar.tsx`, щоб не заводити другу мову тулбарів.

> **Кнопка «Оновити» — доповнення до інвалідації кешу, а не заміна їй.** Якщо мутація не
> інвалідує свій ключ, кнопка це замаскує: оператор натисне, дані оновляться, і ніхто не
> дізнається, що баг є. У ревʼю кожної гілки Фази 2 перевіряємо, що мутації й далі
> інвалідують свої ключі самі.

### 4.2 Політика свіжості

`providers.tsx` лишає `staleTime: 5 хв` дефолтом. Операційні списки (замовлення, звернення,
відгуки, повернення) отримують короткий `staleTime` **у своїх query-хуках**, точково — так
само, як `features/category-tree-reorder/model/use-admin-category-tree-query.ts` уже локально
задає `refetchOnWindowFocus: false`. Глобально не чіпаємо: довіднику брендів опитуватись
частіше нема сенсу, а фонове навантаження на API реальне.

### 4.3 `shared/lib/use-row-selection.ts`

Плоска версія механіки виділення, витягнута з
`widgets/category-tree/ui/admin-category-tree.tsx` (~рядки 280–550):

- `toggle(id)` з оголошенням у live-region;
- `Shift+↑/↓` — діапазон від **якоря**, а не від останнього рядка;
- tri-state заголовок (`true | false | "indeterminate"`);
- **виділене фільтрується проти поточної сторінки** — рядок, який зник (інший оператор
  видалив, змінився фільтр), не потрапляє в дію. Сира множина при цьому не чиститься:
  у дереві це дозволяло згорнутому вузлу лишатись вибраним. Для плоскої таблиці
  залишаємо ту саму семантику — зміна сторінки не має мовчки скидати вибір.

Дерево-специфічне (згорнуті вузли, `role="treegrid"`, DnD-якорі) **не переносимо**.

### 4.4 Чекбокс-колонка в `shared/ui/table.tsx`

Розмітковий гачок уже є — `[&:has([role=checkbox])]:pr-0` на `TableHead` і
`data-[state=selected]:bg-muted` на `TableRow` (спадок shadcn). `shared/ui/checkbox.tsx` теж є.

**Уся складність — у card-mode.** Нижче `md` рядок стає карткою (`max-md:flex-col`), і кожна
комірка стікається з підписом. Чекбокс у такому вигляді перетворився б на рядок «Вибір: ☐»
над назвою товару — безглуздо. Потрібно, щоб у картці він жив у шапці, поруч із назвою.
При цьому `rowLabel` (TASK-276) лишається джерелом `aria-label` для `role="group"`, і
медіа-гейт ролей чіпати не можна.

Додаємо **поверх** наявного рядка, не переписуючи його.

### 4.5 `shared/ui/bulk-actions-bar.tsx`

Узагальнення `features/category-bulk-status/ui/category-bulk-actions-bar.tsx`: замість
зашитих `onActivate`/`onDeactivate` — `actions: { label, variant, onClick }[]`. `role="status"`
і поведінку «зникає при порожньому виділенні» лишаємо: поява бару **сама є** зворотним
звʼязком про наявність вибору, і полайт-регіон повідомляє про це, не забираючи фокус.

### 5.1 Батч-ендпоінти — за зразком TASK-293

Еталон: `PATCH /admin/categories/status` (`admin-category.controller.ts:180`). Три речі з
нього повторюємо свідомо:

1. **Маршрут оголошується ПЕРЕД `:id`-роутами.** Інакше `status` матчиться як `:id` і
   запит іде не туди. Це не стиль — це порядок резолву в NestJS.
2. **Одна транзакція.** Частина неіснуючих id не має лишити половину змін.
3. **Ті самі побічні ефекти, що й у пер-рядкової дії** — інвалідація кешу, реіндекс Meili,
   аудит-лог. TASK-293 закрив рівно цю дірку для категорій: пер-рядкові
   `activate`/`deactivate` не робили нічого з цього, і розбіжність виявилась лише коли
   зʼявився масовий шлях.

### 5.2 ⚠️ Відхилення відгуку — це hard delete

`admin-review.controller.ts:139` — `DELETE :id`, і коментар пояснює чому: «frees the unique
slot so the author may re-submit». Тобто масове відхилення = **масове безповоротне
видалення**. Воно йде через blast-radius-підтвердження з кількістю (як у TASK-293), а не
через звичайний `window.confirm`.

## 8. Перевірка

Гейт на кожній гілці — один синхронний прогін:

```bash
npm run typecheck && npm run lint && npm run test
npm run test:e2e -w apps/store-api -- --runInBand    # гілки з новими ендпоінтами
```

Після інтеграції на `develop`:

```bash
npm run swagger:export -w apps/store-api && npm run generate:api
npm run build && npm run typecheck && npm run lint
npm run test && npm run test:e2e -w apps/store-api -- --runInBand
```

**Нові автотести, без яких епік не закритий:**

- `use-row-selection.test.ts` — `Shift`-діапазон рахується від якоря; tri-state заголовок;
  вибраний рядок, що зник зі сторінки, не потрапляє в дію.
- `table.test.tsx` (розширення) — чекбокс-колонка не ламає `role="group"` / `aria-label`
  у card-mode і не рендериться підписаною коміркою нижче `md`.
- `*-bulk.e2e-spec.ts` на кожен новий батч — порожній список id → 400; частина id
  неіснуючі → не змінено **нічого**; побічні ефекти ті самі, що в пер-рядковій дії.
- Сортування — e2e на кожне нове поле `sortBy`: невідоме значення відхиляється валідацією,
  а не падає в 500.
- Пагінація — `blog-post-list` і `page-list` більше не обрізають мовчки: за межею сторінки
  є контроль, а не порожнеча.

**Живі перевірки** — блок `### TASK-292` у кінець `docs/manual-qa-pending.md`
(append-only): «Оновити» підтягує зміну, зроблену в іншій вкладці; сортування переживає
перезавантаження (воно в URL); масова дія на 20 рядках; клавіатурне виділення без миші;
таблиця з чекбоксами на вузькому екрані.

## 9. Поза обсягом

- **TanStack Table.** Рішення ухвалено — не беремо. Аргументи memo 157 §3 лишаються чинними
  й тепер підкріплені тим, що TASK-293 обійшовся без нього з кращою a11y.
- **Сортування довідників.** Рішення «за рівнями»: 10 таблиць на 5–30 рядків не варті
  `sortBy` у 10 бекенд-модулях.
- **Збереження налаштувань таблиці на користувача** (набір колонок, сорт за замовчуванням) —
  потребує сховища преференсів; окрема задача, якщо колись знадобиться.
