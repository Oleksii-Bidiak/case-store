# План 186 — Головна як блоки, перегляд без редагування, підписане прев'ю (реалізація B-9 / TASK-451)

**Статус:** ⬜ не почато · **Задачі:** TASK-660…671 · **Гілка:** `feature/660-home-blocks`
(від `develop`) · **Джерело:** [B-9 плану 178](178-brainstorms.md), «Рішення 2026-09-15 (B-9)» —
вісім питань розділу, закриті власником.

> Номер 186, а не 185: `185-deletion.md` зайнято рішенням B-2 того ж дня.

## Навіщо

Власник міняє структуру головної **часто** — під акції, сезон, свята. Сьогодні він не може
змінити її ніяк: порядок секцій зашитий у JSX `apps/store-client/src/app/page.tsx`, і навіть
сховати «Ви переглядали» на час розпродажу — це задача розробнику. Вміст при цьому вже адмінський
(банери за плейсментами, каруселі з п'ятьма джерелами), тобто бракує рівно двох речей: **чи
секція є** і **де вона стоїть**.

Друге: секцій із табами може бути тільки одна. Кошик `HOME_TABS` один на весь магазин, тож
«Техніка Apple» (iPhone/iPad/Mac) і окремо «Аксесуари» (чохли/зарядки) на одній сторінці
неможливі.

Третє: **подивитись чернетку можна тільки опублікувавши її наживо.** Підписаного preview-маршруту
у вітрині немає взагалі (ні `draftMode`, ні токена), а `/products/preview/[slug]` живе в адмінці й
малює товар адмінськими компонентами — це інспектор даних, не те, що побачить покупець.
Перебудова головної під Чорну п'ятницю відбувається на очах у покупців.

Четверте, знайдене під час сесії: **контентні розділи мають лише `:write`**. У каталозі прав є
`pages:write`, `banners:write`, `carousels:write`, `faq:write`, `blog:write` — і жодного `:read`,
на відміну від `products:read`, `orders:read`, `returns:read`, `customers:read`, `media:read`.
Навігація адмінки рендериться за тим самим ключем (`admin-nav-list.tsx:142`), тож роль **або
редагує банери, або взагалі не бачить розділу**. Менеджеру, якому треба просто звірити текст
банера, доводиться давати право його міняти.

## Рішення, за якими будуємо

Повний текст — у [плані 178](178-brainstorms.md), «Рішення 2026-09-15 (B-9)». Коротко:

- **Реєстр + адресні блоки, не конструктор сторінки.** `HomeBlock` = тип + порядок + видимість +
  publish-цикл. Вміст редагується там, де й зараз, — у «Каруселях» і «Банерах». Другого редактора
  вмісту не заводимо.
- **Блок ставиться явно.** Опублікована карусель на головній не з'являється, поки її не поставили
  блоком. Одна правда про позицію, один шлях запису.
- **Секцій із табами скільки завгодно.** Наслідок: `Carousel.placement` і `CarouselPlacement`
  **видаляються повністю**.
- **Перегляд — через право, а не через нові сторінки.** `:read`-ключі + read-only режим тієї
  самої сторінки. Кожен новий `:read` іде **з бекфілом** тим, хто має відповідний `:write`.
- **Прев'ю — підписане, на самій вітрині**, 24 години, посиланням можна поділитись, є відкликання.
  Обсяг: головна, товар, сторінки, блог.

## Два обмеження, що не обговорюються

1. **Прев'ю поза кешем і поза індексацією.** `no-store`, жодного ISR-тегу, `noindex` у метаданих.
   Інакше чернетка потрапить у видачу — і це не гіпотеза: у нас `/` віддається через ISR із
   тегами `banners` і `carousels`.
2. **Секрет тримає тільки API.** Вітрина токен не підписує і не перевіряє сама — вона передає
   його у серверний запит, а рішення «віддати чернетку» ухвалює бекенд. Інакше секрет доведеться
   класти в оточення вітрини, а вона збирається з `NEXT_PUBLIC_*` і має публічний бандл.

## Задачі

### A. Блоки головної (TASK-660…665)

| ID       | Що робимо                                  |
| -------- | ------------------------------------------ |
| TASK-660 | Схема + міграція                           |
| TASK-661 | Бекенд `home-block`                        |
| TASK-662 | Адмінський екран «Головна»                 |
| TASK-663 | Вітрина рендерить блоки                    |
| TASK-664 | Каруселі без плейсмента + зона content-map |
| TASK-665 | Право `home:write` з бекфілом              |

**TASK-660 — схема.** `HomeBlock` (`id`, `type`, `title?`, `sortOrder`, `status`, `publishedAt`,
`scheduledAt`, `carouselId?`) + `HomeBlockTab` (`homeBlockId`, `carouselId`, `sortOrder`,
`@@unique([homeBlockId, carouselId])`). Enum `HomeBlockType`: `HERO | TRUST | CATEGORY_NAV |
TABS | CAROUSEL | PROMO_BANNER | RECENTLY_VIEWED | NEWSLETTER`. `carouselId` значуще лише для
`CAROUSEL`, `title` — лише для `TABS` (enforced у DTO, як це вже зроблено для
`Carousel.categoryId`). `onDelete: Cascade` на `HomeBlockTab.carousel` і `SetNull` на
`HomeBlock.carousel` — блок мусить пережити зникнення каруселі, як це вже робить
`Carousel.category`.

Міграція **з бекфілом**, трьома кроками в одній транзакції:

1. вісім рядків `HomeBlock` у нинішньому порядку `page.tsx` — `HERO(0)`, `TRUST(1)`,
   `CATEGORY_NAV(2)`, `TABS(3)`, потім по одному `CAROUSEL` на кожну `HOME_RAILS`-карусель у її
   `sortOrder`, далі `PROMO_BANNER`, `RECENTLY_VIEWED`, `NEWSLETTER`, усі `PUBLISHED`;
2. кожна `HOME_TABS`-карусель стає `HomeBlockTab` того єдиного блока `TABS`
   (`title = 'Популярне'`), порядок = її `Carousel.sortOrder`;
3. **`DROP COLUMN placement` + `DROP TYPE CarouselPlacement`** — після кроків 1–2, не раніше.

Міграція пишеться через `migrate diff --script` (`prisma migrate dev` тут non-interactive і не
працює — див. [план 181](181-access-model.md)), бекфіл дописується в той самий файл руками.
Гейт — інтеграційний тест на справжньому Postgres: після міграції головна віддає **той самий**
перелік секцій у тому ж порядку, що й до неї.

**TASK-661 — бекенд.** Модуль `home-block` (controller → service → repository) за
`nestjs-module`. Публічний `GET /api/home-blocks` — лише `PUBLISHED`, із резолвом каруселей
(`CAROUSEL` → товари, `TABS` → таби з товарами) в одній відповіді, щоб вітрина не робила N+1.
Адмінський CRUD + `PATCH /api/admin/home-blocks/reorder`; вставка й перенесення — **під
адвізорним локом** через `nextSortOrder()`, як це вже робить `BannersRepository.create()` (шлях
оновлення банерів цієї вади досі має — TASK-580, не наша задача, але зразок брати з `create`, не
з `update`). Publish-цикл через наявний `PublishablePort` (авто-дискавері, план 104) — щоб
`SCHEDULED` перемикався тим самим кроном, що й банери.

**TASK-662 — адмінський екран «Головна»** (`/home`). Список блоків із drag-reorder (той самий
`sortable-tree`/dnd-kit, що в категоріях — і **без локального фільтра над перетягуванням**: саме
ця пара дала дефект у хвилі 175). Вмикання/вимикання, додавання блоку `CAROUSEL` (вибір каруселі)
і `TABS` (заголовок + впорядкований список каруселей-табів), видалення блока. Кнопка
«Подивитись на сайті» → прев'ю (TASK-670). Права — `home:write`.

**TASK-663 — вітрина.** `page.tsx` рендерить блоки з `GET /api/home-blocks` замість зашитого JSX;
мапа `type → компонент` лишається в коді (компоненти — код, порядок — дані). Резерв на
недоступний API — **нинішній зашитий порядок**, точно як зараз резервуються банери й каруселі:
головна мусить рендеритись завжди. Новий ISR-тег `home-blocks` + ревалідація з
`/api/revalidate` при зміні блоків.

**TASK-664 — каруселі.** Прибрати селект «Плейсмент» із `carousel-form.tsx` (поля більше немає).
Додати в список каруселей колонку «На головній» (`ні` / назва блока) і кнопку «Додати на
головну» — це і є закриття пастки «створив, опублікував, не видно». Додати в
`content-map-zones.ts` зону для головної-як-блоків із посиланням на `/home`: сьогодні каруселей
на схемі немає взагалі.

**TASK-665 — право `home:write`** у зоні `CONTENT` каталогу прав, **з бекфілом** усім, хто має
`carousels:write` або `banners:write`: до цієї хвилі керування головною було саме цими двома
ключами, і мовчазний бекфіл зберігає те, що оператор міг учора. Зразок міграції —
`MEDIA_BACKFILL_SOURCE_PERMISSIONS` (TASK-441). Окремим рядком, а не всередині 661/662, бо
**умовний бекфіл прав у цьому репо вже один раз не видав нічого** (хвиля 180: матриця — один
рядок на весь магазин) і мусить мати власний тест.

### B. Перегляд без редагування (TASK-666…667)

**TASK-666 — `:read`-ключі + бекфіл + гейтинг.** Додати `categories:read`, `brands:read`,
`devices:read`, `attributes:read`, `addons:read`, `discounts:read`, `pages:read`, `blog:read`,
`banners:read`, `carousels:read`, `faq:read`, `home:read`. **Бекфіл кожного** тим, хто має
відповідний `:write` (одна міграція, один тест «нікому нічого не зникло»). Навігація адмінки
гейтиться `:read` замість `:write` (`admin-nav-list.tsx`). Адмінські **GET**-маршрути цих
довідників приймають `:read` там, де зараз вимагають `:write`; мутації лишаються на `:write`.
Обов'язковий тест: роль із самим `:read` бачить розділ і **отримує 403 на будь-який запис**.

**TASK-667 — read-only шаблон сторінки.** Спільний примітив у `shared/ui` адмінки: та сама
`[id]/edit`-сторінка без `:write` рендериться переглядом — **значення текстом, не заблоковані
інпути** — з кнопкою «Редагувати» для тих, хто має право. Застосувати до категорій, брендів,
пристроїв, послуг, знижок, сторінок, блогу, банерів, каруселей, FAQ і нового `/home`. Жодного
нового маршруту. Окремі картки (`products/[id]`, `orders/[id]`, `returns/[id]`, `staff/[id]`,
`users/[id]`) лишаються як є — вони показують те, чого у формі немає.

### C. Підписане прев'ю (TASK-668…670)

**TASK-668 — бекенд.** `POST /api/admin/preview-tokens` — видає підписаний токен на 24 години з
областю (`scope`: `home` | `product:<id>` | `page:<id>` | `post:<id>`); видача вимагає того
самого права, що дає бачити сутність (`:read` або `:write`). `DELETE /api/admin/preview-tokens`
— «Відкликати всі прев'ю» (bump секрета/версії, а не перебір рядків). Публічні read-маршрути, що
беруть участь у прев'ю, приймають токен і **тільки тоді** віддають чернетковий стан; без токена
поведінка не змінюється ні на біт. Тест, що токен іншої області чернетку не відкриває.

**TASK-669 — вітрина.** Preview-режим на `/`, `/products/[slug]`, `/info|legal/[slug]`,
`/blog/[slug]`: приймає токен, передає його у серверний запит до API, вимикає кеш (`no-store`,
без ISR-тегів), ставить `robots: noindex` у метаданих і малює смужку «Це прев'ю — вийти». Вітрина
**не тримає секрета** і токен не перевіряє. Тест: та сама сторінка без токена лишається
кешованою й індексованою.

**TASK-670 — адмінка.** Кнопка «Подивитись на сайті» на формах товару, сторінки, статті та на
екрані «Головна»; копіювання посилання в буфер; «Відкликати всі прев'ю» в налаштуваннях.
Адмінський інспектор `/products/preview/[slug]` **лишається** — він показує інше (залишки,
SEO-перевизначення, історія змін), тож вони не дублюються; у dict розвести назви, щоб оператор
розумів, що з них що.

### D. Хвіст (TASK-671)

**TASK-671 — доки й ручні перевірки.** `AD-*`/`SF-*` у `docs/qa-recheck.md` **і ids під цією
задачею в Appendix А** (перевірка поза Appendix А після деплою не підбирається); розділ «Головна»
в `docs/admin-guide.md` (що таке блок, чому карусель сама не з'являється, як подивитись чернетку,

`docs/user-stories.md`; оновити `docs/design-system.md`, якщо блоки додадуть нові відступи між
секціями.

## Порядок і гілки

TASK-660 блокує все A. TASK-665 і TASK-666 — обидва міграції прав; **вести їх в одній гілці й
одному прогоні**, інакше друга міграція ризикує знести бекфіл першої (рівно це сталося у хвилях
180/181, де дві міграції однієї хвилі відповіли протилежно на одне питання). C не залежить від A
за кодом, але залежить за сенсом: прев'ю головної нема чого показувати, доки головна не стала
блоками, тож C йде після TASK-663.

Гейти приймання: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run test:e2e`
(`--runInBand`), **`npm run test:int -w apps/store-api`** (міграції й бекфіли — на справжньому
Postgres) і `npm run test:e2e:pw`. Останні два в `npm run test` не входять — запускати окремо;
`test:int` узагалі не має рядка в кореневому `package.json`.
