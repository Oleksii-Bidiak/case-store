## TASK-332 — серверна машина станів (WT-A, робити ПЕРШИМ)

Сьогодні `admin-order.controller.ts` записує **будь-який** статус «як є» — докблок
визнає це прямо, а адмін-UI пропонує всі статуси, крім поточного
(`transitions.ts` — forward-only мапу свідомо прибрали в TASK-151). Без машини
станів webhook оплати не має куди приземлитись: він або перезапише статус, який
оператор щойно виставив, або застрягне.

**Обсяг:**

1. `order-state-machine.ts` — чиста таблиця дозволених переходів + `canTransition()`.
   Чиста функція, бо саме її покриває TDD.
2. `OrderService.updateStatus` відхиляє недозволений перехід **409**, а не пише його.
   Наявні гілки revive / auto-restock лишаються — вони вже коректні.
3. Новий ендпоінт `GET /api/admin/orders/:id/allowed-transitions` — щоб адмін-UI
   пропонував лише валідне, а не «все, крім поточного» (WT-G).
4. Оптимістичний лок по `updatedAt`: два адміни одночасно (E-11) сьогодні дають
   last-write-wins і засмічену історію. Повторити патерн `409 REORDER_STALE` із
   TASK-291/295/298.

**AC:** заборонений перехід → 409; історія не поповнюється при відмові;
`applyPaymentEvent` користується тією самою таблицею, а не власною логікою.

## TASK-330-A — порт, адаптер, webhook, звірка (WT-B)

### Підкроки в порядку виконання

1. **Підпис — першим.** `liqpay.signature.ts` + `liqpay.signature.spec.ts` з
   еталонним тест-вектором із живих доків. Причина: доки LiqPay суперечать самі
   собі (sha1 у старих, sha3-256 у поточній callback-доці), офіційний Node SDK
   покинутий. Тест-вектор перетворює майбутню міграцію алгоритму на один червоний
   іменований тест замість мовчазної поломки продакшн-оплат.
2. **`LiqPayAdapter`** реалізує `PaymentProvider`. Уся вокабулярка LiqPay тут:
   побудова `data`, назви полів, **мапа статусів у чотири корзини** (див.
   `docs/payments-liqpay.md` §7). `sandbox` вважається успіхом **лише** коли
   `LIQPAY_SANDBOX=true` — у проді це відмова.
3. **`PaymentService`** — створення `Payment` (його id іде в LiqPay як `order_id`,
   **не** id замовлення), вставка `PaymentEvent`, делегування в
   `OrderService.applyPaymentEvent`.
4. **`LiqPayWebhookController`** — публічний POST. Перевірити тестом, що його **не**
   блокує CSRF (він змонтований лише на трьох роутах) і що DTO оголошує **рівно**
   `data` + `signature` (глобальний `forbidNonWhitelisted` інакше дасть 400).
5. **`PaymentReconcileWorker`** — крон (`SchedulerRegistry`, як `MailOutboxWorker`):
   опитує «висячі» платежі через `fetchStatus` і авто-скасовує прострочені
   резерви. **Це не «потім»** — LiqPay не документує ретраї, тож без звірки
   магазин мовчки втрачає оплати.
6. **Refund** — `PaymentProvider.refund`; підтвердження приходить callback-ом зі
   статусом `reversed`, не поверненням виклику.
7. **Redaction:** додати `data`, `signature`, `LIQPAY_PRIVATE_KEY` у
   `pino.config.ts`.

### Обов'язкові тести

- `liqpay.signature.spec.ts` — тест-вектор.
- `payment.service.spec.ts` — повторний callback нічого не змінює двічі; підміна
  суми відхиляється; невірний підпис → 400; `sandbox` у проді → відмова.
- `order-reservation.int-spec.ts` — авто-скасування повертає стік **рівно один
  раз** під конкурентним навантаженням (за зразком `order-restock.repository.int-spec.ts`).
- `security.e2e-spec.ts` — webhook-роут не блокується CSRF і не вимагає токена.
