### TASK-268 — SERP-прев'ю для meta-полів — **M, quick-win**

Скрізь, де редагуються `metaTitle`/`metaDescription` (форма товару, категорії, сторінки,
`/settings/seo`) — живий Google-сніпет-прев'ю під полями: заголовок з застосованим
`%s | brand`-шаблоном, зелений URL, опис з обрізанням; лічильники символів з м'якими
порогами (title ~60, description ~160) і підказкою «порожньо = сформується автоматично
з назви/опису» (це правда — `resolveSeo()` так і працює).

- Реалізація: один спільний FSD-компонент `seo-snippet-preview` у shared/ui адмінки;
- Acceptance: власник розуміє без документації, що і де з'явиться в Google.

### TASK-269 — Сторінка «SEO-здоров'я» — **M**

`/settings/seo` (вкладка або секція): автоматичний чек-лист — скільки товарів/категорій/
сторінок без власного metaTitle (це ок — покаже «автоматично», не помилка), чи заповнені
дефолти SeoSettings, чи вимкнений глобальний noindex (**червоне попередження, якщо
ввімкнений** — класична причина «сайту немає в Google»), лінки на sitemap/robots/llms.txt.
Backend: один легкий COUNT-endpoint. Це запобіжник для недосвідченого власника.

## Блок H — CI/CD: тест-сервер замовника + прод _(нова вимога; нарівні з Блоком A)_

> **Що вже є:** сильний CI (`.github/workflows/ci.yml` — typecheck/lint/build/unit/e2e/
> Playwright(non-blocking)). **Чого немає:** Dockerfile'ів застосунків і деплою взагалі.
> **Цільова топологія (власник):** ① прод, ② тест-сервер замовника (staging).
> **Припущення:** обидва — VPS з Docker Compose (власник не обрав хмару). Якщо це не так —
> зупинитись і уточнити у власника перед стартом TASK-270.

### TASK-270 — Продакшн-упаковка: Dockerfile'и + compose — **H**

- Multi-stage Dockerfile'и для `store-api`, `store-client`, `store-admin`
  (Next.js — `output: "standalone"`; API — prisma generate на build-стадії, non-root user);
- `docker-compose.prod.yml`: 3 застосунки + наявна інфра (Postgres/Redis/Meili) + Umami
  (з TASK-261) + reverse-proxy (Caddy — автоматичний HTTPS, найпростіший для соло-власника;
  або Nginx, якщо на сервері вже є) з доменами: вітрина / `admin.` / `api.`;
- healthcheck'и на кожен сервіс; volumes для Postgres/Meili/uploads (перевірити, де живуть
  файли image-pipeline TASK-103 — вони мають переживати редеплой);
- `.env.production.example` з усіма ключами (JWT, SMTP, NP, Sentry DSN, MEILI, Umami)
  і коментарями-підказками;
- Acceptance: `docker compose -f docker-compose.prod.yml up` на чистій VM піднімає
  робочий магазин; smoke: головна, логін адмінки, створення замовлення.

### TASK-271 — Деплой staging (тест-сервер замовника) — **H** _(після 270)_

GitHub Actions: push у `develop` (після зеленого CI) → build образів → GHCR (registry) →
SSH на staging-сервер → `docker compose pull && up -d` → `prisma migrate deploy` →
smoke-check (curl health-endpoint'и).

- Secrets у GitHub Environments (`staging`): SSH-ключ, hostname, env-файл;
- Обмежити паралельність (concurrency group) — один деплой за раз;
- Повідомлення про результат (мінімум — статус у GitHub; Telegram-нотифікація опційно);
- Runbook `docs/deploy.md`: як подивитись логи, як перезапустити, як відкотитись
  (попередній тег образу) — мовою для нетехнічного власника.

### TASK-272 — Деплой production — **H** _(після 271 обкатки на staging)_

Той самий пайплайн, тригер — push у `main` (реліз через GitFlow merge) + **manual approval**
через GitHub Environment `production` (required reviewer = власник).

- Перед міграцією — `pg_dump` бекап у файл з датою (і нічний cron-бекап на сервері,
  retention 14 днів — описати в runbook);
- Post-deploy: on-demand revalidate вітрини (механізм `POST /api/revalidate` вже є),
  Meilisearch reindex (закриває пункт manual-qa §6 з TASK-200);
- Acceptance: повний цикл feature → develop → staging-перевірка замовником → merge у
  main → approve → прод; відкат перевірений навчально один раз.
