# Адміністрування магазину — щоб він не падав (TASK-312)

> **Для кого:** для власника, який ніколи не адміністрував сервер. Це не довідник —
> це те, що треба знати, щоб магазин працював, а ви спали.
>
> **Три документи, які працюють разом:**
>
> - `docs/deploy.md` — як підняти сервер і як туди потрапляють зміни
> - `docs/backup-restore.md` — як не втратити дані і як їх повернути
> - **цей файл** — як не дати магазину впасти, і що робити, коли впав

---

## 0. Головне за одну хвилину

Дешевий VPS падає майже завжди з однієї з двох причин. **Обидві повністю передбачувані,
і обидві вже закриті в конфігурації** — але ви маєте знати, що вони існують:

1. **Закінчилось місце на диску.** Docker за замовчуванням зберігає логи **вічно**. Нічого
   не ламається, ніхто не попереджає — просто через кілька місяців Postgres не може
   записати байт, і все зупиняється одночасно. → Закрито ротацією логів у
   `docker-compose.prod.yml` (10 МБ × 3 файли × 8 сервісів ≈ 240 МБ стеля).
2. **Закінчилась пам'ять.** Один додаток «тече», росте, і ядро Linux вбиває **найбільший
   процес** — а це зазвичай Postgres. Тобто витік у вітрині кладе базу. → Закрито лімітами
   пам'яті: тепер помирає той, хто винен, і `restart: unless-stopped` його одразу піднімає.

Третя причина — **ви самі**, під час деплою. Про це розділ 4.

## 1. Щоб ви дізнались про поломку раніше за клієнта

Це найважливіший розділ, який усі відкладають. Без нього ви дізнаєтесь про падіння
магазину з листа розлюченого покупця — через 6 годин.

### 1.1 Sentry — помилки в коді

DSN **уже вшитий у код**, але порожній у конфігу. Треба лише заповнити.

1. Зареєструйтесь на [sentry.io](https://sentry.io) (безкоштовний тариф вистачає).
2. Створіть проєкт → скопіюйте DSN.
3. У `.env.production` на сервері: `SENTRY_DSN=https://...`
4. У GitHub → Environments → `production` → Variables: `NEXT_PUBLIC_SENTRY_DSN`.

Тепер кожна 500-та помилка прилітає вам на пошту з повним стеком і контекстом запиту.

### 1.2 Uptime-моніторинг — «сайт лежить»

Sentry не побачить, якщо сервер **зовсім** не відповідає. Потрібна перевірка ззовні.

1. [UptimeRobot](https://uptimerobot.com) — безкоштовно, 50 моніторів.
2. Додайте три монітори (ті самі URL, що перевіряє CI після деплою):
   - `https://api.<домен>/health` ← **найважливіший**
   - `https://<домен>/`
   - `https://admin.<домен>/`
3. Сповіщення → на телефон (push у застосунку) і на пошту.

> **Чому `/health` — найважливіший.** Він **справді перевіряє базу даних** (пінгує її й
> віддає 503, якщо вона не відповідає). Раніше він завжди відповідав «все добре» без
> жодної перевірки — тобто моніторинг мовчав би при мертвій базі, а CI зеленів би на
> зламаному деплої. Тепер це реальний датчик.

### 1.3 Місце на диску

```bash
# додайте в crontab на сервері (перевірка щогодини)
0 * * * * df -h / | awk 'NR==2 && int($5) > 80 {print "УВАГА: диск заповнений на "$5}' | mail -s "store-ai: диск" ваша@пошта.com
```

Якщо `mail` не налаштований — просто перевіряйте руками раз на тиждень: `df -h`.

## 2. Щоденні / щотижневі дії

### Подивитись, чи все живе

```bash
ssh deploy@<сервер>
cd /opt/store-ai

docker compose -f docker-compose.prod.yml ps
```

У колонці `STATUS` має бути `Up ... (healthy)` у всіх. Якщо десь `unhealthy` або
`Restarting` — див. розділ 5.

### Подивитись логи

```bash
# останні 100 рядків бекенду (там видно помилки замовлень, авторизації)
docker compose -f docker-compose.prod.yml logs --tail=100 store-api

# «живі» логи (Ctrl+C — вийти)
docker compose -f docker-compose.prod.yml logs -f store-api
```

### Перезапустити один сервіс

```bash
docker compose -f docker-compose.prod.yml restart store-api
```

> Перезапуск **не розлогінює** користувачів. Сесія тримається на JWT + refresh-токені в
> базі, а не в пам'яті контейнера. Клієнти навіть не помітять.

### Перевірити, що нічний бекап відпрацював

**Робіть це щотижня.** Бекап, який тихо зламався три місяці тому, — це найгірший сценарій.

```bash
tail -5 /var/log/store-backup.log        # має закінчуватись "backup: done — <дата>"
ls -lht /opt/store-ai/backups/ | head -3 # свіжі файли
rclone ls b2:store-ai-backups | tail -3  # і вони доїхали в хмару
```

### Місце на диску

```bash
df -h /                    # загальне
docker system df           # скільки з'їв Docker
docker image prune -f      # прибрати старі образи (безпечно)
```

## 3. Безпека акаунтів — найслабша ланка

Тут немає коду. Але саме тут вас найімовірніше зламають.

### ⚠ Увімкніть 2FA прямо зараз — на трьох сервісах

1. **GitHub** — тут лежать SSH-ключі до вашого сервера. Зламаний GitHub = зламаний прод.
2. **Hetzner** (або інший хостер) — можна просто видалити ваш сервер.
3. **Реєстратор домену** — можна вкрасти домен разом із поштою й репутацією.

Це п'ять хвилин роботи і найбільший приріст безпеки з усього, що ви можете зробити.

### Захист гілки `main` на GitHub

Зараз коміти в `main` блокує лише локальний хук на **вашому комп'ютері**. На самому GitHub
**нічого не заважає** запушити напряму в `main` — і це одразу запустить прод-деплой в обхід
усіх тестів.

GitHub → Settings → Branches → Add rule для `main`:

- ✅ Require a pull request before merging
- ✅ Require status checks to pass → обрати `Type Check`, `Lint`, `Unit Tests`, `E2E Tests`
- ✅ Do not allow bypassing the above settings

### Ротація секретів

| Секрет                              | Що станеться при зміні                                       | Коли робити                 |
| ----------------------------------- | ------------------------------------------------------------ | --------------------------- |
| `JWT_SECRET` / `JWT_REFRESH_SECRET` | **Розлогінить УСІХ** — і клієнтів, і вас                     | Вікно низького трафіку      |
| `POSTGRES_PASSWORD`                 | Треба змінити в базі **і** в `.env` + рестарт стека          | Плановане вікно             |
| `CSRF_SECRET`                       | Зламає відкриті форми у клієнтів (вони перезавантажать)      | Будь-коли, майже безболісно |
| `AGE_PUBLIC_KEY`                    | Старі бекапи читаються старим ключем — **не втрачайте його** | Обережно                    |

Загальне правило: **не міняйте секрети «про всяк випадок»**. Міняйте, якщо є підозра на витік.

## 4. Деплой без падінь (ви робитимете це багато разів)

Ваш цикл буде такий: задеплоїли → підключили платіжку → підключили ключ Нової пошти →
задеплоїли ще раз. І так десятки разів.

### Що відбувається автоматично при деплої в прод

```
1. CI проганяє тести           ← червоні тести = деплою не буде
2. Ви натискаєте "Approve"     ← ручний запобіжник
3. Знімається БЕКАП бази       ← якщо не вдався — деплой зупиняється
4. Збираються ТІЛЬКИ змінені образи
5. Накочується міграція        ← migrate deploy, ніколи не видаляє дані
6. Smoke-check трьох адрес     ← якщо червоний — відкат
```

### Чому більшість деплоїв тепер не роняють сайт

Кожен образ тегується SHA останнього коміту, що зачепив **саме його**. Якщо ви змінили
лише вітрину — API й адмінка отримають ті самі теги, що й були, і Docker **навіть не
перестворить їхні контейнери**. Вони працюють без перерви, нікого не викидає.

У Summary деплою це видно:

```
- store-api: prod-abc123 (built: false)   ← не чіпали, не перезапускали
- store-client: prod-def456 (built: true) ← перезібрали й перезапустили
```

### Правила, які рятують

1. **Не деплойте в піковий час.** Навіть 20 секунд перезапуску вітрини — це втрачені кошики.
2. **Червоний smoke-check → відкат.** Не «спробую ще раз». `docs/rollback.md`, розділ 1.
3. **Не деплойте в п'ятницю ввечері.** Це не забобон: якщо зламається, лагодити доведеться
   у вихідні, наспіх і без сил.
4. **Одна зміна за раз**, поки не звикнете. Коли деплой ламається, ви маєте знати, що саме
   ви змінили.

## 5. Playbook інциденту — сайт лежить

Роздрукуйте. Під час аварії ви не будете думати ясно — і це нормально.

```
┌─ САЙТ НЕ ВІДКРИВАЄТЬСЯ ────────────────────────────────────────┐
│                                                                │
│ 1. Це сталося одразу після деплою?                             │
│      ТАК → ВІДКАТ ОБРАЗУ. docs/rollback.md, розділ 1.           │
│            Не розслідуйте зараз. Спершу підніміть магазин.      │
│      НІ  → далі                                                 │
│                                                                │
│ 2. ssh deploy@<сервер> && cd /opt/store-ai                      │
│    docker compose -f docker-compose.prod.yml ps                 │
│                                                                │
│    Хтось "Exited" / "Restarting"?                              │
│      → docker compose ... logs --tail=100 <сервіс>              │
│      → шукайте перший ERROR згори, не знизу                     │
│                                                                │
│ 3. curl -i https://api.<домен>/health                           │
│                                                                │
│    HTTP 503 + "database":"down"  → база впала (крок 4)          │
│    Взагалі не відповідає         → сервер/Caddy (крок 5)        │
│    HTTP 200                      → API живий, проблема у вітрині │
│                                                                │
│ 4. БАЗА ВПАЛА                                                   │
│    df -h /              ← диск заповнений? найчастіша причина    │
│    docker compose ... logs postgres --tail=50                    │
│    docker compose ... restart postgres                           │
│                                                                │
│ 5. СЕРВЕР НЕ ВІДПОВІДАЄ ВЗАГАЛІ                                 │
│    Пінгується? Заходить по ssh?                                  │
│      НІ → консоль Hetzner → reboot                              │
│      ТАК → docker compose -f docker-compose.prod.yml up -d      │
│                                                                │
│ 6. НІЩО НЕ ДОПОМАГАЄ                                            │
│    → docs/backup-restore.md, розділ 4.4                         │
│      (підняти магазин з нуля на новому сервері з бекапів)       │
└────────────────────────────────────────────────────────────────┘
```

### Перше правило інциденту

**Спершу відновіть роботу, потім шукайте причину.** Відкат образу займає хвилину і нічого
не руйнує. Розслідування може зачекати годину — ваші клієнти не можуть.

## 6. Аварійні команди — шпаргалка

```bash
# --- ДОСТУП ---
ssh deploy@<сервер>
cd /opt/store-ai
COMPOSE="docker compose -f docker-compose.prod.yml"

# --- ДІАГНОСТИКА ---
$COMPOSE ps                          # хто живий
$COMPOSE logs --tail=100 store-api   # що сталось
curl -i https://api.<домен>/health   # чи жива база
df -h /                              # чи є місце
docker stats --no-stream             # хто їсть пам'ять

# --- ЛІКУВАННЯ ---
$COMPOSE restart store-api           # перезапустити один сервіс
$COMPOSE up -d                       # підняти те, що впало
docker image prune -f                # звільнити місце

# --- КАТАСТРОФА ---
./scripts/backup.sh                  # зробити бекап ПРЯМО ЗАРАЗ
# відкат образу      → docs/rollback.md
# відновлення бази   → docs/backup-restore.md

# --- ВТРАТИЛИ ДОСТУП ДО АДМІНКИ ---
$COMPOSE exec store-api node dist/scripts/create-admin.js --email ваша@пошта.com
```

## 7. Що зробити ДО першого реального клієнта

Чек-лист. Поки хоч один пункт не закритий — на прод не йдемо.

- [ ] **2FA** на GitHub, хостері, реєстраторі домену
- [ ] **Branch protection** на `main` (розділ 3)
- [ ] **Бекапи налаштовані** — `age`-ключ, B2, нічний cron (`docs/backup-restore.md`)
- [ ] **Навчальна тривога пройдена** — ви особисто відновили базу на staging і **звірили
      цифри** (`docs/backup-restore.md`, розділ 5). Це не формальність: бекап, який ви не
      відновлювали, — це надія, а не бекап
- [ ] **Репетиція відкату** — ви особисто відкотили образ на staging (`docs/rollback.md`, розділ 4)
- [ ] **Sentry** заповнений (розділ 1.1)
- [ ] **Uptime-моніторинг** налаштований (розділ 1.2)
- [ ] **`MAIL_ENABLED=true` + реальний SMTP** — інакше клієнти не отримують листів про
      замовлення. Система більше не робить вигляд, що відправила (лишає листи в черзі й
      пише помилку), але це не заміна робочій пошті
- [ ] **`NP_API_KEY`** — без нього доставка рахується як **0 грн**, тобто ви возите за свій кошт
- [ ] **Юридичні сторінки заповнені** — оферта, реквізити ФОП (`docs/legal-checklist.md`)
- [ ] **Платіжна система** — або підключена, або чекаут чесно каже «оплата при отриманні»
      (зараз саме так)
- [ ] **`docs/manual-qa-pending.md` пройдений** на staging

## 8. Що НЕ треба робити

- ❌ **Не запускайте `db:seed` на проді**, щоб «щось відновити». Він заллє демо-каталог
  поверх ваших живих даних. Для відновлення адміна є `create-admin.js`.
- ❌ **Не вмикайте `noindexSite` в базі на проді.** Це прибере магазин із Google, і
  повертатись він буде тижнями. Чекбокс прибрано з адмінки саме тому.
- ❌ **Не редагуйте файли просто на сервері.** Наступний деплой їх перезапише. Усі зміни —
  через git.
- ❌ **Не тримайте приватний `age`-ключ на сервері.** Сенс шифрування бекапів саме в тому,
  що зламаний сервер не дає доступу до історії бекапів.
- ❌ **Не робіть `docker compose down -v`.** `-v` видаляє томи — базу і всі фото товарів.
  Правильно: `down` (без `-v`) або `restart`.
