# Перший деплой

> Після [04-secrets-ci.md](04-secrets-ci.md) деплой уже працює сам. Цей документ — про те,
> **що саме відбувається** і **як зрозуміти, що воно вдалося**.

---

## 1. Як це запускається

**Staging** — просто злийте щось у `develop`. Усе.

**Прод** — злийте `develop` → `main` через PR. Деплой **зупиниться й чекатиме**, поки ви
натиснете «Approve».

---

## 2. Що відбувається автоматично

**Staging** (гілка `develop`):

```
1. CI: тести / лінт / збірка       ← червоне = деплою не буде
2. Збірка трьох образів → GHCR      теги: staging-<SHA> і staging-latest
3. SSH на сервер: pull + up -d
4. Міграції бази: prisma migrate deploy
5. Smoke-check трьох адрес
```

**Прод** (гілка `main`) — те саме плюс два запобіжники:

```
1. CI: тести                        ← червоне = деплою не буде
2. Ви натискаєте "Approve"          ← ручний запобіжник
3. БЕКАП бази                       ← не вдався = деплой зупиняється
4. Збираються ТІЛЬКИ змінені образи
5. Міграція (migrate deploy — ніколи не видаляє дані)
6. Smoke-check трьох адрес
```

> **Один деплой за раз.** Дві зміни майже одночасно → другий деплой **стане в чергу** й
> дочекається першого, а не обірве його.

### Чому більшість деплоїв не роняють сайт

Кожен образ тегується SHA останнього коміту, що зачепив **саме його**. Змінили лише вітрину
→ API й адмінка отримають ті самі теги, що були, і Docker **навіть не перестворить їхні
контейнери**. Вони працюють без перерви, нікого не викидає.

У Summary деплою це видно:

```
- store-api:    prod-abc123 (built: false)   ← не чіпали, не перезапускали
- store-client: prod-def456 (built: true)    ← перезібрали й перезапустили
```

---

## 3. Де дивитись, чи деплой пройшов

- **GitHub → Actions** → workflow **CI** → останній запуск. Задача **Deploy to Staging**
  (або **Deploy to Production**) має бути зелена. У **Summary** — коміт, теги образів і три
  посилання.
- **GitHub → Environments → `staging` / `production`** — історія всіх деплоїв.
- Червоно на кроці **Smoke check** → образи зібрались і завантажились, але застосунок не
  відповів. Логи — [06-day-to-day.md](06-day-to-day.md) §2.

Перевірити руками з будь-якого комп'ютера:

```bash
curl -i https://api.<домен>/health     # HTTP 200 і "database":"up"
curl -i https://<домен>/               # вітрина
curl -i https://admin.<домен>/         # адмінка
```

> **`/health` справді перевіряє базу** — пінгує її й віддає 503, якщо не відповідає. Тому
> зелений smoke-check щось означає. (Раніше він відповідав «все добре» без жодної перевірки
> — і CI зеленів би на деплої з мертвою базою.)

---

## 4. ⚠ Разова дія при першому деплої на старий staging

Якщо staging-том створювався **до** появи історії міграцій, у ньому немає службової таблиці
`_prisma_migrations`. Перший `migrate deploy` на ньому впаде з **«relation already exists»**.

Це очікувано. Лікується одним свідомим стиранням тому — staging-дані одноразові (§6).

---

## 5. Правила, які рятують

1. **Не деплойте в піковий час.** Навіть 20 секунд перезапуску вітрини — втрачені кошики.
2. **Червоний smoke-check → відкат.** Не «спробую ще раз».
   → [07-rollback.md](07-rollback.md)
3. **Не деплойте в п'ятницю ввечері.** Не забобон: зламається — лагодитимете у вихідні,
   наспіх і без сил.
4. **Одна зміна за раз**, поки не звикнете. Коли деплой ламається, ви маєте знати, що саме
   змінили.

---

## 6. Аварійне: перезалити staging з нуля

Дані staging одноразові, тож найшвидший спосіб полагодити «заплутаний» стан — знести стек
**разом із томами** й підняти заново.

> ### ⛔ НІКОЛИ не робіть цього на проді
>
> `-v` видаляє томи: базу і **всі фото товарів**.

```bash
cd /opt/store-ai
COMPOSE="docker compose -f docker-compose.prod.yml -f docker-compose.staging.yml --env-file .env.production"

$COMPOSE down -v
$COMPOSE up -d
```

Схему бази наллє наступний деплой, або вручну:

```bash
$COMPOSE exec -T store-api npx prisma migrate deploy --config prisma.config.ts
```

> **Саме `--config`, не `--schema`.** URL бази лежить у `prisma.config.ts`, а не в
> `schema.prisma`, тож виклик через `--schema` падає з «datasource.url property is required»
> ще **до** застосування будь-чого. (У попередній версії цього документа тут стояв саме
> `--schema` — команда не спрацювала б.)

---

## 7. Що НЕ треба робити

- ❌ **Не запускайте `db:seed` на проді**, щоб «щось відновити». Він заллє демо-каталог
  **поверх ваших живих даних**. Для відновлення адміна є `create-admin.js`
  ([08-backup-restore.md](08-backup-restore.md) §4.1).
- ❌ **Не редагуйте файли просто на сервері.** Наступний деплой їх перезапише. Усі зміни —
  через git.
- ❌ **Не запускайте `prisma migrate dev` проти сервера.** Це команда для локальної
  розробки: побачивши розбіжність, вона запропонує **скинути базу**. На серверах —
  виключно `migrate deploy`.
- ❌ **Не робіть `docker compose down -v` на проді.** Правильно: `down` (без `-v`) або
  `restart`.

## Довідка для розробника

- **swagger.json.** Образи вітрини/адмінки генерують Orval-хуки **всередині збірки** з
  `apps/store-api/swagger.json`. Файл у git ігнорується, тому пайплайн **регенерує його на
  раннері перед `docker build`** (`npm ci` → `prisma generate` → `swagger:export` з
  тимчасовим Postgres і dummy-секретами). Без цього кроку `docker build` фронтендів упав би
  на `generate:api`.
- **Чому `migrate deploy`, а не `db push`.** Раніше staging синхронізував схему через
  `db push --accept-data-loss`, бо історія міграцій не потрапляла в git. Виправлено:
  усі міграції закомічені, staging накочує схему **тією самою командою, що й прод** — це
  принципово, бо staging є репетицією лише тоді, коли репетирує справжню процедуру.
  `migrate deploy` **ніколи не видаляє дані** і **відмовляється** працювати на базі з
  розбіжною історією — завалює деплой замість того, щоб мовчки перекроїти схему.
- **CLI `prisma` в образі.** Рантайм-образ `store-api` містить CLI `prisma` (він у
  `dependencies`, тож переживає `npm prune --omit=dev`). Якщо колись побачите
  «prisma: not found» — перевірте, що `prisma` лишається в `dependencies`, а не в
  `devDependencies`.
- **Одноразові образи.** `NEXT_PUBLIC_*` запікаються в бандл на етапі збірки, тож
  staging-образ прив'язаний до staging-домену і **не може** бути промоутнутий у прод — прод
  збирає свої образи.
