# 03b · Тестовий деплой БЕЗ домену (демо на nip.io)

> **Коли це для вас:** домену ще немає, а показати робочий магазин треба вже —
> замовнику для узгодження чи інвесторам для фінансування. Це **тимчасове викидне
> демо**, а не прод. Підняли → показали → знесли.
>
> Це відгалуження від основного шляху (тому `03b`, а не окремий крок). Коли з'явиться
> справжній домен — повертаєтесь на [02-domain-dns.md](02-domain-dns.md) і
> [03-server.md](03-server.md) → далі по порядку.

---

## 0. Що це і чого це НЕ

| Це                                        | Це НЕ                                               |
| ----------------------------------------- | --------------------------------------------------- |
| Повний стек по HTTPS на тимчасовій адресі | Прод (жодних живих клієнтів, жодних грошей)         |
| Викидний сервер — знести не шкода         | Не CI/CD: піднімаємо **вручну**, без GitHub Actions |
| Демо-каталог із сідера                    | Не для індексації Google (закриваємо, крок 8)       |

⚠️ **Голий IP без домену не працює** — потрібні три піддомени (`shop`, `admin.`, `api.`),
яких у голого IP не буває; Caddy не видасть HTTPS-сертифікат на IP; а без HTTPS куки
`__Host-`/`Secure` браузер відкидає і логін ламається. Обхід — `nip.io` (крок 4).

---

## 1. ⚠️ Правильний продукт Hetzner — **Cloud**, не «Webhosting»

Беріть **Hetzner Cloud** (окрема панель [console.hetzner.cloud](https://console.hetzner.cloud)),
план **CX22** (~€4/міс, 2 vCPU / 4 GB / 40 GB). Оплата **погодинна** — сервер живе кілька днів
демо і коштує копійки.

**НЕ беріть «Webhosting S/M».** Це shared-хостинг під PHP-сайти: немає root-доступу, **не
запустити Docker**. Маркери в описі: «PHP processes», «memory limit 192/256MB». Наш стек — це
Docker + NestJS + PostgreSQL, йому потрібен саме Cloud-сервер.

## 2. Підняти сервер

Мінімум для демо (повний хардненг — у [03-server.md](03-server.md), для викидного демо
не обов'язковий):

1. Створіть сервер CX22, образ **Ubuntu**, додайте свій SSH-ключ у панелі.
2. Зайдіть: `ssh root@<IP-сервера>`.
3. Встановіть Docker:
   ```bash
   curl -fsSL https://get.docker.com | sh
   ```
4. Відкрийте порти **80** і **443** — Caddy бере на них Let's Encrypt-сертифікат. Порт 22
   (SSH) лишіть відкритим для себе.
   > **Що таке порт і чи треба щось робити.** Порт — це «двері» до сервера за номером: 80 —
   > звичайний веб (HTTP), 443 — веб по HTTPS («замочок»), 22 — SSH (ваш термінал). Свіжий
   > сервер **Hetzner Cloud за замовчуванням БЕЗ firewall — усі порти вже відкриті**, тож для
   > викидного демо зазвичай робити нічого не треба. Хочете акуратно — заведіть **Hetzner
   > Cloud Firewall** у панелі (ліве меню _Firewalls_ → _Create_): Inbound-правила TCP на
   > порти **22, 80, 443**, source _Any IPv4/IPv6_, і застосуйте до сервера. Якщо колись
   > вмикаєте локальний `ufw` — **спершу** `ufw allow 22`, інакше замкнете себе без SSH.

Далі всі команди — на сервері, якщо не сказано «на ноуті».

## 3. Код на сервер

Для деплою з локальною збіркою потрібен **повний вихідний код** (не лише compose-файли).
Склонуйте репозиторій у `/opt/case-store` — **з гілки `develop`**:

```bash
mkdir -p /opt/case-store && cd /opt/case-store
git clone -b develop <URL-репозиторію> .   # приватний репо → PAT або deploy-ключ
```

> **Спершу — на ноуті:** переконайтесь, що ваша локальна `develop` **запушена**
> (`git push origin develop`). Сервер клонує з `origin`, а не з вашого ноута — усе, що не
> запушено, на сервер не потрапить.

> ⚠️ **Дві пастки в одному рядку — перевірте обидві.**
>
> **1. Гілка `develop`, а не `main`.** Дефолтна гілка репозиторію — `main`, тож `git clone`
> **без `-b develop`** візьме саме її. Але за GitFlow уся робота живе в `develop`, а `main`
> поки містить лише початковий коміт: там немає ані `docker-compose.prod.yml`, ані
> `Caddyfile`, і крок 6 впаде одразу. (На справжньому запуску прод збиратиметься з `main` —
> але тільки після того, як `develop` вперше зіллють туди релізним PR, див.
> [05-first-deploy.md](05-first-deploy.md).)
>
> **2. Крапка в кінці.** Вона означає «клонуй прямо в поточну теку». Без неї git створить
> підтеку `/opt/case-store/<ім'я-репо>/`, і кроки 5–8 (усі вони роблять `cd /opt/case-store`)
> нічого не знайдуть — помилки будуть невиразні, а причина лишиться далеко позаду.
>
> **Перевірте одразу:**
>
> ```bash
> cd /opt/case-store
> git branch --show-current   # має бути: develop
> ls -la                      # має бути: apps/ docs/ docker-compose.prod.yml Caddyfile .git/
> ```
>
> Щось не так — переклонуйте (безпечно саме тут: своїх файлів у теці ще немає,
> `.env.production` з'явиться лише на кроці 5):
>
> ```bash
> rm -rf /opt/case-store
> mkdir -p /opt/case-store && cd /opt/case-store
> git clone -b develop <URL-репозиторію> .
> ```
>
> `rm -rf` видаляє без підтвердження й без кошика — перечитайте шлях очима, має бути рівно
> `/opt/case-store`.

## 4. Адреса замість домену — `nip.io`

`nip.io` — безкоштовний wildcard-DNS: будь-яке ім'я, що закінчується на вашу IP з дефісами,
резолвиться в цю IP. Нічого налаштовувати не треба.

**Спершу дізнайтесь IP свого сервера:**

```bash
curl -4 -s ifconfig.me
```

(або подивіться в панелі Hetzner Cloud — колонка IPv4.)

> 🚨 **`203.0.113.10` нижче — приклад, а НЕ ваша адреса.** Увесь діапазон `203.0.113.0/24`
> зарезервований стандартом (RFC 5737) саме під документацію — реальних серверів там не
> буває. Скопіюєте його як є — Let's Encrypt стукатиме не на ваш сервер, сертифікат не
> видасться, HTTPS не підніметься. А оскільки `NEXT_PUBLIC_*` **запікаються в образ**,
> виправлення коштуватиме **повної перезбірки** (крок 6 із `--build`), а не рестарту.
> Перевірте себе на кроці 5: у конфізі не має лишитись жодного `203-0-113-10`.

Далі в прикладах IP сервера — `203.0.113.10`; **підставляйте свою**. Тоді ваш `DOMAIN`:

```
203-0-113-10.nip.io
```

Автоматично отримуєте три робочі адреси (Caddy додає `admin.`/`api.` сам):

| Роль    | Адреса                              |
| ------- | ----------------------------------- |
| Вітрина | `https://203-0-113-10.nip.io`       |
| Адмінка | `https://admin.203-0-113-10.nip.io` |
| API     | `https://api.203-0-113-10.nip.io`   |

Усі три — піддомени `nip.io`, тож вони **same-site**, і куки `__Host-`/`sameSite=strict`
працюють. Caddy бере на них **справжній Let's Encrypt** сертифікат. Нуль змін коду —
`DOMAIN` у нас просто рядок.

## 5. Заповнити `.env.production`

```bash
cd /opt/case-store
cp .env.production.example .env.production
```

### Як його відкрити й відредагувати

Файл починається з крапки — він **прихований**, звичайний `ls` його не покаже (потрібен
`ls -la`).

**Подивитись:**

```bash
less /opt/case-store/.env.production   # ↑↓ PgUp/PgDn — гортати, /текст — пошук, q — вийти
```

(`cat` теж працює, але вивалює **всі секрети** в історію термінала — не робіть цього під час
демонстрації екрана.)

**Редагувати** — редактором `nano`:

```bash
nano /opt/case-store/.env.production
```

| Дія            | Клавіші                                          |
| -------------- | ------------------------------------------------ |
| знайти рядок   | **Ctrl+W** → наберіть напр. `JWT_SECRET` → Enter |
| зберегти       | **Ctrl+O** → Enter                               |
| вийти          | **Ctrl+X**                                       |
| скасувати дію  | Alt+U                                            |
| вирізати рядок | Ctrl+K                                           |

Підказки видно внизу екрана, `^` там означає Ctrl. **Миша не працює** — рухайтесь стрілками.
Вставити з буфера: правий клік (Windows Terminal / PuTTY) або Ctrl+Shift+V.

Формат рядків: `KEY=value` **без пробілів** навколо `=`; лапки потрібні, лише якщо у значенні
є пробіл; `#` на початку рядка — коментар.

### Чим генерувати секрети

```bash
openssl rand -hex 32
```

> ⚠️ **Не `node -e "…randomBytes…"`**, як радять інші доки: на кроці 2 ви поставили на сервер
> **лише Docker**, Node там немає → `node: command not found`. `openssl` є в Ubuntu з коробки.
> (На ноуті, де Node є, `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
> робить те саме.) Бонус hex-формату: лише символи `0-9a-f`, тож `POSTGRES_PASSWORD` не
> доведеться URL-кодувати — а він підставляється в `postgresql://…`.

Запустіть команду **окремо для кожного** із семи секретів нижче.

### Що заповнити

Нижче — **не весь файл, а лише рядки, які треба змінити**; решта (їх більшість) лишається як
є. Не шукайте повного збігу зі змістом файлу очима — знаходьте кожен рядок через **Ctrl+W**.
Схожі назви поруч не плутайте: заповнити треба `UMAMI_APP_SECRET`, а не `UMAMI_ORIGIN`
(другий — опційний і лишається порожнім).

Замініть IP на свою:

```env
DOMAIN=203-0-113-10.nip.io
CORS_ORIGINS=https://203-0-113-10.nip.io,https://admin.203-0-113-10.nip.io
PUBLIC_BASE_URL=https://api.203-0-113-10.nip.io

# BUILD-TIME — запікаються в образ (тому крок 6 із --build)
NEXT_PUBLIC_API_URL=https://api.203-0-113-10.nip.io
NEXT_PUBLIC_APP_URL=https://203-0-113-10.nip.io
NEXT_PUBLIC_ADMIN_URL=https://admin.203-0-113-10.nip.io
NEXT_PUBLIC_SITE_URL=https://203-0-113-10.nip.io

# Секрети (обов'язкові; JWT_SECRET ≠ JWT_REFRESH_SECRET, кожен ≥32 символи)
POSTGRES_PASSWORD=<згенеруйте>
REDIS_PASSWORD=<згенеруйте>
MEILI_MASTER_KEY=<згенеруйте, ≥16>
JWT_SECRET=<згенеруйте, ≥32>
JWT_REFRESH_SECRET=<інший, ≥32>
CSRF_SECRET=<згенеруйте, ≥32>
UMAMI_APP_SECRET=<згенеруйте, ≥32>

# Для демо лишіть вимкненими
MAIL_ENABLED=false
STAGING_BASIC_AUTH=
```

> **`POSTGRES_USER=store` і `POSTGRES_DB=store` уже заповнені — не міняйте їх.** Інакше
> `DATABASE_URL` із кроку 7.3 не зійдеться з базою, і сід не достукається.

> **`AGE_PUBLIC_KEY` для демо не потрібен.** Він обов'язковий лише для бекапів, а бекап
> блокує деплой тільки в **CI-джобі прода**. Ми ж піднімаємо стек вручну (крок 6), тож
> цей запобіжник не спрацьовує. Для реального прода — [08-backup-restore.md](08-backup-restore.md).

### Перевірте себе перед кроком 6

Три команди; жодна не друкує секретів.

**1. Чи не лишилось незаповнених обов'язкових змінних.** Без будь-якої з цих 15 стек не
підніметься — у `docker-compose.prod.yml` вони оголошені як `${VAR:?…}`, а `:?` падає і на
**порожньому** значенні, не лише на відсутньому:

```bash
grep -nE '^(DOMAIN|POSTGRES_USER|POSTGRES_PASSWORD|POSTGRES_DB|REDIS_PASSWORD|MEILI_MASTER_KEY|UMAMI_APP_SECRET|JWT_SECRET|JWT_REFRESH_SECRET|CORS_ORIGINS|CSRF_SECRET|PUBLIC_BASE_URL|NEXT_PUBLIC_API_URL|NEXT_PUBLIC_APP_URL|NEXT_PUBLIC_ADMIN_URL)=$' /opt/case-store/.env.production
```

`=$` означає «після `=` порожньо». **Порожній вивід — усе гаразд.** Що вивелось — те й зупинить
крок 6.

**2. Чи не лишилось плейсхолдерів із прикладу:**

```bash
grep -n 'change-me' /opt/case-store/.env.production   # має бути ПОРОЖНЬО
```

**3. Адреси — очима:**

```bash
grep -n '203-0-113-10\|example\.com' /opt/case-store/.env.production   # має бути ПОРОЖНЬО
grep -n '^DOMAIN=\|^CORS_ORIGINS=\|^PUBLIC_BASE_URL=\|^NEXT_PUBLIC_' /opt/case-store/.env.production
```

Перша ловить найдорожчу помилку кроку 5 — залишену **приклад-адресу** з доки (`203-0-113-10`,
див. 🚨 у кроці 4) або `example.com` із шаблону. Друга показує всі сім рядків з адресами —
у кожному має стояти ваша `nip.io`.

> Перевірки 1 і 2 не замінюють одна одну: `change-me` ловить забутий плейсхолдер, а `=$` —
> змінну, яку ви очистили й не встигли заповнити. Порожнє значення виглядає «прибраним», але
> для compose воно таке саме фатальне, як відсутнє.

## 6. Підняти стек

### 6.0. Спершу привезти `swagger.json` — інакше збірка впаде

`apps/store-api/swagger.json` — це OpenAPI-контракт, з якого Orval генерує типізовані хуки
фронтенду. Він **у `.gitignore`** (генерований артефакт), тож у свіжому клоні на сервері його
**немає**, а Dockerfile під час збірки виконує `npm run generate:api`. Без файлу збірка
падає так:

```
🛑 storeClient - Failed to resolve input: Please provide a valid string value or pass a loader
target store-admin: failed to solve: ... "npm run generate:api -w apps/store-admin" ... exit code: 1
```

Згенерувати його на сервері не можна: скрипт піднімає `AppModule` (тобто потребує Node,
ts-node і живої БД), а на сервері стоїть лише Docker. Тому — **як і сід на кроці 7 — робимо
це на ноуті**, а на сервер веземо готовий артефакт.

**На ноуті, у теці репозиторію:**

```bash
docker compose up -d postgres              # export піднімає AppModule, йому потрібна БД
npm run swagger:export -w apps/store-api
scp apps/store-api/swagger.json root@203.0.113.10:/opt/case-store/apps/store-api/swagger.json
```

> **Генеруйте наново, не везіть старий.** Файл відображає контролери й DTO на момент
> генерації; якщо API змінювався після того, як ви робили це востаннє, фронт збереться зі
> **застарілими** хуками — і це не впаде, а тихо розійдеться з реальним API.

> Для довідки: у CI цього кроку робити не треба — `ci.yml` піднімає одноразовий Postgres і
> сам виконує `swagger:export` перед кожною збіркою образів.

### 6.1. Збірка

```bash
cd /opt/case-store
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Перша збірка — кілька хвилин. `--build` **обов'язковий**: `NEXT_PUBLIC_*` запікаються в
образ, тож фронт треба зібрати саме під nip.io-адресу (готові GHCR-образи прив'язані до
іншого домену й не підійдуть).

Накотіть схему бази:

```bash
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"
$COMPOSE exec -T store-api npx prisma migrate deploy --config prisma.config.ts
```

> **Саме `--config`, не `--schema`** — URL бази лежить у `prisma.config.ts`.

Перевірте, що застосунок живий:

```bash
curl -sI https://api.203-0-113-10.nip.io/health   # 200
```

## 7. Демо-каталог — єдиний нетривіальний крок

Каталог наливає сідер (`prisma/seed.ts`): категорії, товари, банери, каруселі, сторінки,
відгуки. Але запустити його **всередині серверного образу не можна** — прод-образ **навмисно
позбавлений** інструментів сіду (`tsx` вирізаний prune-ом, `src/` у рантайм не копіюється).
Це не баг, а захист: образ не має вміти заливати демо-акаунти з відомими паролями.

Тому сідимо **зі свого ноута** (там повне оточення) проти серверної бази через SSH-тунель.
Сідер БД самодостатній — Meilisearch йому не потрібен.

**7.1. На сервері** — тимчасово відкрийте Postgres лише на localhost. Створіть
`docker-compose.demo.yml`:

```yaml
services:
  postgres:
    ports:
      - "127.0.0.1:5432:5432"
```

і перезапустіть із ним:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.demo.yml \
  --env-file .env.production up -d postgres
```

Порт `127.0.0.1` — назовні НЕ видно, лише через SSH-тунель.

**7.2. На ноуті** — відкрийте тунель (лишіть цей термінал працювати):

```bash
ssh -N -L 5432:localhost:5432 root@203.0.113.10
```

**7.3. На ноуті, в теці репозиторію** (інший термінал) — запустіть документований
демо-сід ([seed-guide.md](../seed-guide.md) §6), задавши свій пароль адміна:

```bash
NODE_ENV=production ALLOW_PROD_SEED=true \
  ADMIN_SEED_EMAIL='admin@ваш-магазин.demo' \
  ADMIN_SEED_PASSWORD='<надійний-унікальний-пароль>' \
  DATABASE_URL='postgresql://store:<POSTGRES_PASSWORD>@localhost:5432/store' \
  npm run db:seed
```

> **Windows.** Синтаксис `VAR=value … команда` — це **bash**, у **PowerShell він не працює**.
> Запускайте цю команду в **Git Bash** (ставиться разом із Git), або в PowerShell задайте
> змінні окремо — `$env:ALLOW_PROD_SEED="true"` (і так кожну: `NODE_ENV`, `ADMIN_SEED_EMAIL`,
> `ADMIN_SEED_PASSWORD`, `DATABASE_URL`), а тоді окремим рядком `npm run db:seed`.

> Дефолтний `admin@store.com` / `Admin123!` у цьому режимі **не пройде** — `ALLOW_PROD_SEED`
> вимагає задати власні `ADMIN_SEED_*`. Це і є ваш логін в адмінку.

Після сіду тунель можна закрити (Ctrl-C).

## 8. Закрити демо від Google

Прод-Caddy глушить індексацію лише `admin.` і `api.`, а **вітрину — ні** (у справжньому
проді вона МАЄ індексуватись). Для тимчасового демо це небажано.

> **Не шукайте перемикач в адмінці — його прибрали (TASK-307).** Старий чекбокс «Приховати
> сайт від пошукових систем» (`noindexSite`) був заряджений на живий магазин і давав лише
> `robots.txt`-disallow. Тепер середовище закривають на рівні проксі заголовком
> **`X-Robots-Tag: noindex`** (так само робить staging — `Caddyfile.staging`). Він **сильніший
> за `robots.txt`**: не просто _просить_ не сканувати, а здатний **прибрати з індексу** навіть
> URL, які Google уже знає. І не потребує ані логіну в адмінку, ані запису в БД.

Додайте цей заголовок на блок вітрини в Caddy (усе — на сервері):

1. Відкрийте конфіг: `nano /opt/case-store/Caddyfile`.
2. Знайдіть блок вітрини — він починається з `{$DOMAIN} {` і **єдиний без** `X-Robots-Tag`
   (`admin.`/`api.` уже мають його). Додайте всередину блоку рядок:

   ```
   {$DOMAIN} {
       header X-Robots-Tag "noindex, nofollow, noarchive"

       encode zstd gzip
       reverse_proxy store-client:3000
   }
   ```

   Збережіть: **Ctrl+O**, Enter; вийдіть: **Ctrl+X**.

3. Перечитайте конфіг проксі:

   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.production restart caddy
   ```

4. Перевірте, що заголовок віддається:

   ```bash
   curl -sI https://203-0-113-10.nip.io | grep -i x-robots-tag   # має бути noindex
   ```

> **Про «вікно індексації».** Google індексує сторінку лише **після того, як знайде** її
> URL (посилання десь, sitemap, ручна подача). Свіжий `nip.io`-хост без жодного вхідного
> посилання для Google практично невидимий, тож ризик у короткому демо ≈ нульовий. Щоб
> закрити вікно повністю — виставте цей заголовок **до кроку 9** (перш ніж роздати
> посилання). Разом з обскурною адресою й коротким життям демо цього достатньо.

## 9. Показати

Дайте глядачеві три посилання й логін до адмінки:

```
Вітрина: https://203-0-113-10.nip.io
Адмінка: https://admin.203-0-113-10.nip.io   (логін із кроку 7.3)
```

Basic-auth навмисно немає — щоб глядач відкрив без тертя.

## 10. Знести

```bash
cd /opt/case-store
docker compose -f docker-compose.prod.yml --env-file .env.production down -v
```

`-v` стирає томи (базу, фото). Далі — **видаліть сам сервер** у панелі Hetzner Cloud, щоб не
капала погодинна оплата. Тут `down -v` безпечний саме тому, що це викидне демо (на проді —
ніколи, див. [05-first-deploy.md](05-first-deploy.md) §7).

## ⚠️ Перехід на справжній домен — це НЕ підміна конфіга

Коли замовник купить домен, «просто поміняти nip.io на домен» **не вийде**: `NEXT_PUBLIC_*`
запечені в образ на етапі збірки. Зміна адрес = **повна перезбірка фронт-образів** (`--build`),
а не рестарт. Тому для реального запуску йдіть штатним шляхом:
[02-domain-dns.md](02-domain-dns.md) → [03-server.md](03-server.md) →
[04-secrets-ci.md](04-secrets-ci.md) → [05-first-deploy.md](05-first-deploy.md), де деплоєм
керує CI, а не ручна збірка.
