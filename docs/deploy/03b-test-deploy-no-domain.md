# 03b · Тестовий деплой БЕЗ домену (демо на nip.io)

> **Коли це для вас:** домену ще немає, а показати робочий магазин треба вже —
> замовнику для узгодження чи інвесторам для фінансування. Це **тимчасове викидне
> демо**, а не прод. Підняли → показали → знесли.
>
> Це відгалуження від основного шляху (тому `03b`, а не окремий крок). Коли з'явиться
> справжній домен — повертаєтесь на [02-domain-dns.md](02-domain-dns.md) і
> [03-server.md](03-server.md) → далі по порядку.

---

## 0. Що це і чого це НЕ

| Це                                        | Це НЕ                                               |
| ----------------------------------------- | --------------------------------------------------- |
| Повний стек по HTTPS на тимчасовій адресі | Прод (жодних живих клієнтів, жодних грошей)         |
| Викидний сервер — знести не шкода         | Не CI/CD: піднімаємо **вручну**, без GitHub Actions |
| Демо-каталог із сідера                    | Не для індексації Google (закриваємо, крок 8)       |

⚠️ **Голий IP без домену не працює** — потрібні три піддомени (`shop`, `admin.`, `api.`),
яких у голого IP не буває; Caddy не видасть HTTPS-сертифікат на IP; а без HTTPS куки
`__Host-`/`Secure` браузер відкидає і логін ламається. Обхід — `nip.io` (крок 4).

---

## 1. ⚠️ Правильний продукт Hetzner — **Cloud**, не «Webhosting»

Беріть **Hetzner Cloud** (окрема панель [console.hetzner.cloud](https://console.hetzner.cloud)),
план **CX22** (~€4/міс, 2 vCPU / 4 GB / 40 GB). Оплата **погодинна** — сервер живе кілька днів
демо і коштує копійки.

**НЕ беріть «Webhosting S/M».** Це shared-хостинг під PHP-сайти: немає root-доступу, **не
запустити Docker**. Маркери в описі: «PHP processes», «memory limit 192/256MB». Наш стек — це
Docker + NestJS + PostgreSQL, йому потрібен саме Cloud-сервер.

## 2. Підняти сервер

Мінімум для демо (повний хардненг — у [03-server.md](03-server.md), для викидного демо
не обов'язковий):

1. Створіть сервер CX22, образ **Ubuntu**, додайте свій SSH-ключ у панелі.
2. Зайдіть: `ssh root@<IP-сервера>`.
3. Встановіть Docker:
   ```bash
   curl -fsSL https://get.docker.com | sh
   ```
4. Відкрийте порти **80** і **443** — Caddy бере на них Let's Encrypt-сертифікат. Порт 22
   (SSH) лишіть відкритим для себе.
   > **Що таке порт і чи треба щось робити.** Порт — це «двері» до сервера за номером: 80 —
   > звичайний веб (HTTP), 443 — веб по HTTPS («замочок»), 22 — SSH (ваш термінал). Свіжий
   > сервер **Hetzner Cloud за замовчуванням БЕЗ firewall — усі порти вже відкриті**, тож для
   > викидного демо зазвичай робити нічого не треба. Хочете акуратно — заведіть **Hetzner
   > Cloud Firewall** у панелі (ліве меню _Firewalls_ → _Create_): Inbound-правила TCP на
   > порти **22, 80, 443**, source _Any IPv4/IPv6_, і застосуйте до сервера. Якщо колись
   > вмикаєте локальний `ufw` — **спершу** `ufw allow 22`, інакше замкнете себе без SSH.

Далі всі команди — на сервері, якщо не сказано «на ноуті».

## 3. Код на сервер

Для деплою з локальною збіркою потрібен **повний вихідний код** (не лише compose-файли).
Склонуйте репозиторій у `/opt/case-store` — **з гілки `develop`**:

```bash
mkdir -p /opt/case-store && cd /opt/case-store
git clone -b develop <URL-репозиторію> .   # приватний репо → PAT або deploy-ключ
```

> **Спершу — на ноуті:** переконайтесь, що ваша локальна `develop` **запушена**
> (`git push origin develop`). Сервер клонує з `origin`, а не з вашого ноута — усе, що не
> запушено, на сервер не потрапить.

> ⚠️ **Дві пастки в одному рядку — перевірте обидві.**
>
> **1. Гілка `develop`, а не `main`.** Дефолтна гілка репозиторію — `main`, тож `git clone`
> **без `-b develop`** візьме саме її. Але за GitFlow уся робота живе в `develop`, а `main`
> поки містить лише початковий коміт: там немає ані `docker-compose.prod.yml`, ані
> `Caddyfile`, і крок 6 впаде одразу. (На справжньому запуску прод збиратиметься з `main` —
> але тільки після того, як `develop` вперше зіллють туди релізним PR, див.
> [05-first-deploy.md](05-first-deploy.md).)
>
> **2. Крапка в кінці.** Вона означає «клонуй прямо в поточну теку». Без неї git створить
> підтеку `/opt/case-store/<ім'я-репо>/`, і кроки 5–8 (усі вони роблять `cd /opt/case-store`)
> нічого не знайдуть — помилки будуть невиразні, а причина лишиться далеко позаду.
>
> **Перевірте одразу:**
>
> ```bash
> cd /opt/case-store
> git branch --show-current   # має бути: develop
> ls -la                      # має бути: apps/ docs/ docker-compose.prod.yml Caddyfile .git/
> ```
>
> Щось не так — переклонуйте (безпечно саме тут: своїх файлів у теці ще немає,
> `.env.production` з'явиться лише на кроці 5):
>
> ```bash
> rm -rf /opt/case-store
> mkdir -p /opt/case-store && cd /opt/case-store
> git clone -b develop <URL-репозиторію> .
> ```
>
> `rm -rf` видаляє без підтвердження й без кошика — перечитайте шлях очима, має бути рівно
> `/opt/case-store`.

## 4. Адреса замість домену — `nip.io`

`nip.io` — безкоштовний wildcard-DNS: будь-яке ім'я, що закінчується на вашу IP з дефісами,
резолвиться в цю IP. Нічого налаштовувати не треба.

**Спершу дізнайтесь IP свого сервера:**

```bash
curl -4 -s ifconfig.me
```

(або подивіться в панелі Hetzner Cloud — колонка IPv4.)

> 🚨 **`203.0.113.10` нижче — приклад, а НЕ ваша адреса.** Увесь діапазон `203.0.113.0/24`
> зарезервований стандартом (RFC 5737) саме під документацію — реальних серверів там не
> буває. Скопіюєте його як є — Let's Encrypt стукатиме не на ваш сервер, сертифікат не
> видасться, HTTPS не підніметься. А оскільки `NEXT_PUBLIC_*` **запікаються в образ**,
> виправлення коштуватиме **повної перезбірки** (крок 6 із `--build`), а не рестарту.
> Перевірте себе на кроці 5: у конфізі не має лишитись жодного `203-0-113-10`.

Далі в прикладах IP сервера — `203.0.113.10`; **підставляйте свою**. Тоді ваш `DOMAIN`:

```
203-0-113-10.nip.io
```

Автоматично отримуєте три робочі адреси (Caddy додає `admin.`/`api.` сам):

| Роль    | Адреса                              |
| ------- | ----------------------------------- |
| Вітрина | `https://203-0-113-10.nip.io`       |
| Адмінка | `https://admin.203-0-113-10.nip.io` |
| API     | `https://api.203-0-113-10.nip.io`   |

Усі три — піддомени `nip.io`, тож вони **same-site**, і куки `__Host-`/`sameSite=strict`
працюють. Caddy бере на них **справжній Let's Encrypt** сертифікат. Нуль змін коду —
`DOMAIN` у нас просто рядок.

## 5. Заповнити `.env.production`

```bash
cd /opt/case-store
cp .env.production.example .env.production
```

### Як його відкрити й відредагувати

Файл починається з крапки — він **прихований**, звичайний `ls` його не покаже (потрібен
`ls -la`).

**Подивитись:**

```bash
less /opt/case-store/.env.production   # ↑↓ PgUp/PgDn — гортати, /текст — пошук, q — вийти
```

(`cat` теж працює, але вивалює **всі секрети** в історію термінала — не робіть цього під час
демонстрації екрана.)

**Редагувати** — редактором `nano`:

```bash
nano /opt/case-store/.env.production
```

| Дія            | Клавіші                                          |
| -------------- | ------------------------------------------------ |
| знайти рядок   | **Ctrl+W** → наберіть напр. `JWT_SECRET` → Enter |
| зберегти       | **Ctrl+O** → Enter                               |
| вийти          | **Ctrl+X**                                       |
| скасувати дію  | Alt+U                                            |
| вирізати рядок | Ctrl+K                                           |

Підказки видно внизу екрана, `^` там означає Ctrl. **Миша не працює** — рухайтесь стрілками.
Вставити з буфера: правий клік (Windows Terminal / PuTTY) або Ctrl+Shift+V.

Формат рядків: `KEY=value` **без пробілів** навколо `=`; лапки потрібні, лише якщо у значенні
є пробіл; `#` на початку рядка — коментар.

### Чим генерувати секрети

```bash
openssl rand -hex 32
```

> ⚠️ **Не `node -e "…randomBytes…"`**, як радять інші доки: на кроці 2 ви поставили на сервер
> **лише Docker**, Node там немає → `node: command not found`. `openssl` є в Ubuntu з коробки.
> (На ноуті, де Node є, `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
> робить те саме.) Бонус hex-формату: лише символи `0-9a-f`, тож `POSTGRES_PASSWORD` не
> доведеться URL-кодувати — а він підставляється в `postgresql://…`.

Запустіть команду **окремо для кожного** із восьми секретів нижче.

### Що заповнити

Нижче — **не весь файл, а лише рядки, які треба змінити**; решта (їх більшість) лишається як
є. Не шукайте повного збігу зі змістом файлу очима — знаходьте кожен рядок через **Ctrl+W**.
Схожі назви поруч не плутайте: заповнити треба `UMAMI_APP_SECRET`, а не `UMAMI_ORIGIN`
(другий — опційний і лишається порожнім).

Замініть IP на свою:

```env
DOMAIN=203-0-113-10.nip.io
CORS_ORIGINS=https://203-0-113-10.nip.io,https://admin.203-0-113-10.nip.io
PUBLIC_BASE_URL=https://api.203-0-113-10.nip.io

# BUILD-TIME — запікаються в образ (тому крок 6 із --build)
NEXT_PUBLIC_API_URL=https://api.203-0-113-10.nip.io
NEXT_PUBLIC_APP_URL=https://203-0-113-10.nip.io
NEXT_PUBLIC_ADMIN_URL=https://admin.203-0-113-10.nip.io
NEXT_PUBLIC_SITE_URL=https://203-0-113-10.nip.io

# Секрети (обов'язкові; JWT_SECRET ≠ JWT_REFRESH_SECRET, кожен ≥32 символи)
POSTGRES_PASSWORD=<згенеруйте>
REDIS_PASSWORD=<згенеруйте>
MEILI_MASTER_KEY=<згенеруйте, ≥16>
JWT_SECRET=<згенеруйте, ≥32>
JWT_REFRESH_SECRET=<інший, ≥32>
CSRF_SECRET=<згенеруйте, ≥32>
UMAMI_APP_SECRET=<згенеруйте, ≥32>
REVALIDATE_SECRET=<згенеруйте, ≥32>

# Для демо лишіть вимкненими
MAIL_ENABLED=false
STAGING_BASIC_AUTH=
```

> 🚨 **`REVALIDATE_SECRET` — це той рядок, через який демо виглядає зламаним, а насправді
> просто мовчить.** Це спільний секрет між API та вітриною: саме ним API просить вітрину
> скинути кеш після кожної правки в адмінці. Розійдуться значення — вітрина відповість 401;
> буде порожнім — API нічого не надішле. В обох випадках **усе виглядає справним**: контейнери
> здорові, адмінка каже «збережено», логи чисті. Просто новий логотип чи банер зʼявляються на
> сайті не одразу, а за випадкові 0–60 хвилин, коли перегенерується кеш ISR. Саме так цей
> варіант і пропустили на першому демо — до TASK-383 змінної в цьому списку не було зовсім.
> Тепер API **не стартує** без неї в проді, а обидві відмови пишуться в лог.

> **`POSTGRES_USER=store` і `POSTGRES_DB=store` уже заповнені — не міняйте їх.** Інакше
> `DATABASE_URL` із кроку 7.3 не зійдеться з базою, і сід не достукається.

> **`PUBLIC_BASE_URL` і `NEXT_PUBLIC_API_URL` мають збігатися символ у символ.** Це не
> формальність: сід запікає `PUBLIC_BASE_URL` у посилання на **кожну** картинку товару
> (крок 7.4), а вітрина будує аллоулист `next/image` із `NEXT_PUBLIC_API_URL` **на збірці**.
> Для цього аллоулиста `localhost` і `127.0.0.1` — різні походження, тож найменша розбіжність
> дає порожні плитки замість фото. Те саме значення знадобиться вам на ноуті в кроці 7.4.

> **`AGE_PUBLIC_KEY` для демо не потрібен.** Він обов'язковий лише для бекапів, а бекап
> блокує деплой тільки в **CI-джобі прода**. Ми ж піднімаємо стек вручну (крок 6), тож
> цей запобіжник не спрацьовує. Для реального прода — [08-backup-restore.md](08-backup-restore.md).

### Перевірте себе перед кроком 6

Три команди; жодна не друкує секретів.

**1. Чи не лишилось незаповнених обов'язкових змінних.** Без будь-якої з цих 16 стек не
підніметься — у `docker-compose.prod.yml` вони оголошені як `${VAR:?…}`, а `:?` падає у **двох**
випадках: значення порожнє **або** рядка немає взагалі.

```bash
cd /opt/case-store
for v in DOMAIN POSTGRES_USER POSTGRES_PASSWORD POSTGRES_DB REDIS_PASSWORD \
         MEILI_MASTER_KEY UMAMI_APP_SECRET JWT_SECRET JWT_REFRESH_SECRET \
         CORS_ORIGINS CSRF_SECRET REVALIDATE_SECRET PUBLIC_BASE_URL \
         NEXT_PUBLIC_API_URL NEXT_PUBLIC_APP_URL NEXT_PUBLIC_ADMIN_URL; do
  grep -qE "^${v}=." .env.production || echo "ВІДСУТНЯ або ПОРОЖНЯ: $v"
done
```

`^VAR=.` вимагає щонайменше один символ після `=`, тому один прохід ловить обидва стани.
**Порожній вивід — усе гаразд.** Що вивелось — те й зупинить крок 6.

> До 2026-08-04 тут стояв `grep -nE '^(DOMAIN|…)=$'`, який ловив лише **порожнє** значення.
> Шаблон `=$` за визначенням вимагає наявний рядок, тож файл, у якому змінної немає зовсім,
> проходив перевірку з порожнім виводом — тобто доця казала «все гаразд» рівно в тому випадку,
> який найчастіше й трапляється при оновленні (див. наступний блок).

**2. Чи не лишилось плейсхолдерів із прикладу:**

```bash
grep -n 'change-me' /opt/case-store/.env.production   # має бути ПОРОЖНЬО
```

**3. Адреси — очима:**

```bash
grep -n '203-0-113-10\|example\.com' /opt/case-store/.env.production   # має бути ПОРОЖНЬО
grep -n '^DOMAIN=\|^CORS_ORIGINS=\|^PUBLIC_BASE_URL=\|^NEXT_PUBLIC_' /opt/case-store/.env.production
```

Перша ловить найдорожчу помилку кроку 5 — залишену **приклад-адресу** з доки (`203-0-113-10`,
див. 🚨 у кроці 4) або `example.com` із шаблону. Друга показує всі сім рядків з адресами —
у кожному має стояти ваша `nip.io`.

> Перевірки 1 і 2 не замінюють одна одну: `change-me` ловить забутий плейсхолдер, перевірка 1 —
> змінну, яку ви очистили й не встигли заповнити або яка так і не з'явилась у файлі. Порожнє
> значення виглядає «прибраним», але для compose воно таке саме фатальне, як відсутнє.

### Якщо ви оновлюєте вже розгорнутий стек

Усе вище написано під сценарій «заповнюю файл з нуля». Другий сценарій — ви розгортали демо
місяць тому, тепер перезаливаєте свіжий код — має власну пастку: `.env.production` лишився
таким, яким ви його заповнили, а в `docker-compose.prod.yml` за цей час **додались нові
обов'язкові змінні**. У файлі їх немає — і не тому, що ви щось пропустили.

Перевірка 1 їх покаже, але вона знає лише сьогоднішній список із 16. Ця команда показує повну
дельту проти шаблону, включно з необов'язковими:

```bash
cd /opt/case-store
comm -23 <(grep -oE '^[A-Z_][A-Z0-9_]*=' .env.production.example | sort -u) \
         <(grep -oE '^[A-Z_][A-Z0-9_]*=' .env.production          | sort -u)
```

Друкує лише **імена** ключів, яких у вашому файлі немає; значення не читаються, тож команду
безпечно виконувати з демонстрацією екрана. Далі зіставте вивід із
[04a-env-matrix.md](04a-env-matrix.md) — там сказано, що кожна змінна робить і чи обов'язкова
вона, — і допишіть потрібні рядки в кінець файлу.

Найсвіжіший приклад, на якому це вже спіткнулись: **`REVALIDATE_SECRET`** додали 2026-07-27
(TASK-324) одразу як обов'язкову. Файл, заповнений до цієї дати, зупиняє **збірку** з
`required variable REVALIDATE_SECRET is missing a value` — див. 🚨 у кроці 6.2.

```bash
printf 'REVALIDATE_SECRET=%s\n' "$(openssl rand -hex 32)" >> .env.production
grep -c '^REVALIDATE_SECRET=' .env.production   # має бути рівно 1
```

> Дописуйте `>>` (додати в кінець), а не `>` — одна зайва дужка стирає весь файл.

## 6. Підняти стек

### 6.0. `swagger.json` уже в репозиторії — везти нічого не треба

`apps/store-api/swagger.json` — це OpenAPI-контракт, з якого Orval генерує типізовані хуки
фронтенду під час збірки образів. **Файл закомічений у git** (TASK-325), тож у клоні на
сервері він уже є і збірка знаходить його сама. Жодних `scp` перед кроком 6.1.

> **Раніше було не так.** Файл лежав у `.gitignore`, і цей крок вимагав згенерувати його на
> ноуті та привезти на сервер вручну — інакше збірка падала на
> `🛑 storeClient - Failed to resolve input`. Якщо натрапите на цю інструкцію в старих
> нотатках — вона застаріла.

**Що лишилося вашою відповідальністю:** якщо ви **змінювали API** (контролери, DTO,
Swagger-декоратори), контракт треба перегенерувати **й закомітити** — інакше фронт збереться
зі старими хуками. Це не впаде, а тихо розійдеться з реальним API. На ноуті:

```bash
docker compose up -d postgres              # export піднімає AppModule, йому потрібна БД
npm run swagger:export -w apps/store-api
npm run generate:api                       # оновити хуки під новий контракт
git add apps/store-api/swagger.json && git commit -m "chore(api): refresh OpenAPI contract"
```

> У повноцінному пайплайні про це не треба пам'ятати: джоба `contract-freshness` у `ci.yml`
> перегенеровує контракт і **валить білд**, якщо закомічений файл розійшовся з кодом API.
> Тут, у демо без CI, такої страховки немає — перевіряйте самі.

### 6.1. Додати swap — інакше збірка не влізе в пам'ять

CX22 має **4 ГБ RAM і жодного swap** (образи Hetzner Cloud його не створюють). Продакшн-білд
Next 16 з Turbopack сам по собі важкий, а `up --build` запускає збірку трьох образів
**паралельно** — два фронти опиняються в `npm run build` одночасно й не влазять. Ядро вбиває
buildkit, і ви бачите:

```
failed to execute bake: signal: killed
```

Це не помилка коду — це OOM. Перевірити можна через `dmesg -T | grep -i "killed process"`.

```bash
df -h /        # у колонці Avail має бути помітно більше за 4 ГБ (образи вже з'їли своє)
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
free -h        # має з'явитись рядок Swap
```

Тека, з якої ви це запускаєте, значення не має: `/swapfile` — абсолютний шлях, а swap —
налаштування всієї системи. Якщо місця обмаль, вистачить і 2 ГБ (`fallocate -l 2G`). Після
перезавантаження swap зникне; щоб лишався — `echo '/swapfile none swap sw 0 0' >> /etc/fstab`.

### 6.2. Збірка — по одному образу за раз

```bash
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"
$COMPOSE config >/dev/null && echo "інтерполяція ОК"
$COMPOSE build store-api
$COMPOSE build store-client
$COMPOSE build store-admin
$COMPOSE up -d
```

Swap рятує від вбивства процесу, послідовна збірка — від того, щоб узагалі впертись у стелю;
разом надійно. Кілька хвилин на образ. Останній `up -d` — **без `--build`**: образи вже
зібрані, він лише піднімає стек.

Перший рядок — сухий прогін: `config` проганяє **ту саму** підстановку змінних, що й `build`,
але за секунду й без витрати пам'яті. Мовчить (крім вашого «інтерполяція ОК») — жодна `${VAR:?…}`
далі не впаде. Дешевше, ніж дізнатись про це на третій хвилині збірки.

> 🚨 **Збірка ОДНОГО сервісу все одно вимагає ВСІХ змінних — навіть чужих.** Compose підставляє
> змінні в **увесь** файл, і лише потім залишає сервіс, який ви назвали. Тому це реальний,
> а не вигаданий вивід:
>
> ```
> $COMPOSE build store-client
> error while interpolating services.store-api.environment.REVALIDATE_SECRET:
> required variable REVALIDATE_SECRET is missing a value
> ```
>
> Ви збираєте **вітрину**, а падає на змінній **API** — і `REVALIDATE_SECRET` при цьому взагалі
> не бере участі в збірці вітрини (в її `Dockerfile` немає такого `ARG`; це рантайм-змінна).
> Це не поламаний Dockerfile і не помилка в команді: у `.env.production` просто немає рядка.
> Лікується кроком 5 — перевірка 1 і блок «Якщо ви оновлюєте вже розгорнутий стек».

Збирати **обов'язково локально** (а не брати готові з GHCR): `NEXT_PUBLIC_*` запікаються в
образ, тож фронт має бути зібраний саме під вашу nip.io-адресу — образи з GHCR прив'язані до
іншого домену й не підійдуть.

> У штатному шляху цієї проблеми немає: при деплої через CI образи збираються **на раннерах
> GitHub**, а сервер лише робить `pull`. Пам'ять на збірку йому не потрібна взагалі.

### 6.3. Схема бази та перевірка

Накотіть схему (змінна `$COMPOSE` — з кроку 6.2; якщо відкрили новий термінал, задайте
її знову):

```bash
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"
$COMPOSE exec -T store-api npx prisma migrate deploy --config prisma.config.ts
```

> **Саме `--config`, не `--schema`** — URL бази лежить у `prisma.config.ts`.

Перевірте, що застосунок живий:

```bash
curl -sI https://api.203-0-113-10.nip.io/health   # 200
```

## 7. Демо-каталог — єдиний нетривіальний крок

Каталог наливає сідер (`prisma/seed/`): категорії, товари, банери, каруселі, сторінки,
відгуки. Але запустити його **всередині серверного образу не можна** — прод-образ **навмисно
позбавлений** інструментів сіду (`tsx` вирізаний prune-ом, `src/` у рантайм не копіюється).
Це не баг, а захист: образ не має вміти заливати демо-акаунти з відомими паролями.

Тому сідимо **зі свого ноута** (там повне оточення) проти серверної бази через SSH-тунель.
Сідер БД самодостатній — Meilisearch йому не потрібен.

> ⚠️ **Сід — це не лише рядки в базі.** Крім записів він **малює картинки** (`sharp`) і
> кладе їх файлами у теку на **тій машині, де запущений**, тобто на вашому ноуті. У базу при
> цьому лягають посилання на **серверну** адресу. Тому тунель — це лише половина роботи:
> файли доведеться перенести окремо, крок **7.5**. Пропустите його — каталог на демо буде,
> а замість кожного фото порожня плитка.

Вам знадобляться **два вікна на ноуті** (одне назавжди займе тунель) і одне на сервері.

> 🚨 **Якщо база вже сіджена — спершу прочитайте 7.\* нижче про ресет.** Просто повторити цей
> крок поверх наявного каталогу **не можна**: сід впаде посеред роботи. Деталі — у підрозділі
> [«Перезалив на вже сіджений сервер»](#перезалив-на-вже-сіджений-сервер) одразу після 7.7.

### 7.0. На сервері — дізнатись пароль бази

Він знадобиться на ноуті у кроках 7.3–7.4:

```bash
grep '^POSTGRES_PASSWORD=' /opt/case-store/.env.production
```

> Це єдина команда всього ранбука, яка друкує секрет на екран. **Не виконуйте її під час
> демонстрації екрана** і не лишайте у видимій історії термінала.

### 7.1. На сервері — відкрити Postgres на localhost

Створіть `docker-compose.demo.yml`:

```bash
cd /opt/case-store
cat > docker-compose.demo.yml <<'YAML'
services:
  postgres:
    ports:
      - "127.0.0.1:5432:5432"
YAML
```

і перезапустіть Postgres із цим файлом:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.demo.yml \
  --env-file .env.production up -d postgres
```

Префікс `127.0.0.1` означає «слухати лише локальну петлю» — назовні порт НЕ видно, дістатись
можна винятково через SSH-тунель. Контейнер Postgres при цьому **перестворюється** (дані в
томі лишаються), а `store-api` на кілька секунд втратить з'єднання й перепідключиться — це
нормально.

**Перевірте результат, а не код виходу** — порт має бути реально опублікований:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.demo.yml \
  --env-file .env.production ps postgres
```

У колонці PORTS має стояти `127.0.0.1:5432->5432/tcp`. Якщо там порожньо або просто
`5432/tcp` — overlay не підхопився (найчастіше: забули другий `-f`), і тунель на кроці 7.2
впаде з `connection refused`.

### 7.2. На ноуті, вікно №1 — тунель

```bash
ssh -N -o ExitOnForwardFailure=yes -L 55432:localhost:5432 root@203.0.113.10
```

> ⚠️ **Порт `55432`, а не `5432`.** Ваш власний dev-Postgres майже напевно вже тримає 5432,
> і тунель на тому ж номері впаде з `bind: Address already in use`. Ліве число — порт **на
> вашому ноуті**, праве — на сервері; збігатись вони не зобов'язані.

> ⚠️ **`localhost` у цьому рядку резолвиться НА СЕРВЕРІ.** Це той самий `127.0.0.1:5432`,
> який ви щойно відкрили на кроці 7.1, — а не щось на вашому ноуті.

> **Після вводу пароля команда «зависає» — так і має бути.** `-N` означає «не виконувати
> жодної команди на сервері, лише тримати тунель», тому запрошення командного рядка ви не
> отримаєте: сесія просто стоїть відкрита. Доки вікно висить — тунель живий. Закриєте
> (**Ctrl+C**) — тунель зникне. **Не закривайте його до кінця кроку 7.6.**

> `-o ExitOnForwardFailure=yes` доданий навмисно: без нього ssh, не змігши зайняти локальний
> порт, лише друкує попередження й **лишається висіти** — тобто виглядає точно так само, як
> робочий тунель, а сід тим часом піде не туди. З цим прапорцем невдале прокидання одразу
> обриває з'єднання.

### 7.3. На ноуті, вікно №2 — переконатись, що ціль правильна

**Найважливіша перевірка кроку.** Якщо тунель не піднявся або змінна не підхопилась, сідер
мовчки заллє демо-каталог у **ваш локальний dev-Postgres**, і ви цього не помітите: команда
відпрацює успішно, а вітрина на сервері лишиться порожньою.

У теці репозиторію (Git Bash або PowerShell — рядок однаковий, крім задання змінної):

```powershell
$env:DATABASE_URL="postgresql://store:<POSTGRES_PASSWORD>@localhost:55432/store"
```

```bash
# Git Bash — те саме:
export DATABASE_URL='postgresql://store:<POSTGRES_PASSWORD>@localhost:55432/store'
```

```bash
node -e "const{Pool}=require('pg');const p=new Pool({connectionString:process.env.DATABASE_URL});p.query('select current_database() as db, (select count(*) from products) as products, (select count(*) from users) as users').then(r=>console.table(r.rows)).catch(e=>console.error('ERR',e.message)).finally(()=>p.end())"
```

| Що бачите                                  | Що це означає                                                          |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| `db: store`, `products: 0`, `users: 0`     | ✅ це серверна база після міграцій — вперед                            |
| `products` і `users` **не нульові**        | 🛑 ви на **власному dev-Postgres**. Порт 5432 замість 55432. **Стоп.** |
| `ERR … ECONNREFUSED`                       | тунель не працює — поверніться до 7.1 / 7.2                            |
| `ERR … relation "products" does not exist` | достукались, але міграції не накочені — крок 6.3                       |

Свіжозмігрована серверна база порожня — тому будь-яке ненульове число тут означає, що ви
дивитесь не туди. Точні числа сіду називати марно: каталог росте, а от **нуль** надійний.

### 7.4. На ноуті, вікно №2 — сід

Документований демо-сід ([seed-guide.md](../seed-guide.md) §6). `DATABASE_URL` уже заданий на
кроці 7.3 — вдруге не задавайте.

```powershell
# PowerShell
$env:NODE_ENV="production"
$env:ALLOW_PROD_SEED="true"
$env:PUBLIC_BASE_URL="https://api.203-0-113-10.nip.io"
$env:ADMIN_SEED_EMAIL="admin@ваш-магазин.demo"
$env:ADMIN_SEED_PASSWORD="<надійний-унікальний-пароль>"
npm run db:seed
```

```bash
# Git Bash
NODE_ENV=production ALLOW_PROD_SEED=true \
  PUBLIC_BASE_URL='https://api.203-0-113-10.nip.io' \
  ADMIN_SEED_EMAIL='admin@ваш-магазин.demo' \
  ADMIN_SEED_PASSWORD='<надійний-унікальний-пароль>' \
  npm run db:seed
```

> **Windows.** Синтаксис `VAR=value … команда` — це **bash**, у PowerShell він не працює.
> Тому вище два варіанти; змішувати їх не треба.

> **`PUBLIC_BASE_URL` тут обов'язковий** — рівно те саме значення, що ви записали в
> `.env.production` на кроці 5. Сід підставляє його в посилання на кожну картинку, і без
> нього під `NODE_ENV=production` він **навмисно падає** з повідомленням
> `Seed images: PUBLIC_BASE_URL must be set…`. Запобіжник свідомий: інакше в базу тихо
> лягли б посилання на `localhost`, робочі рівно на одному ноуті у світі — вашому.

> Дефолтний `admin@store.com` / `Admin123!` у цьому режимі **не пройде** — `ALLOW_PROD_SEED`
> вимагає задати власні `ADMIN_SEED_*`. Це і є ваш логін в адмінку.

> **Скільки чекати:** ~1–2 хвилини. Більшу частину часу займає не база, а малювання
> картинок. У виводі має бути рядок
> `ℹ Seed images: https://api.203-0-113-10.nip.io/uploads/products/ → <тека на ноуті>` —
> **запам'ятайте цю теку**, з неї копіюєте файли на кроці 7.5.

> ⚠️ **Вікно PowerShell тепер має `NODE_ENV=production`.** Ніколи не запускайте в ньому
> `npm install` — він викине devDependencies. Закрийте це вікно після кроку 7.6.

### 7.5. Перенести картинки на сервер

Зараз база на сервері знає про фото, але самих файлів там немає — вони лежать на ноуті, у
теці з рядка `ℹ Seed images: … → <тека>`. Перенесемо їх у том `uploads_data`, звідки їх
роздає API.

**1. На ноуті, вікно №2 — запакувати й відправити:**

```powershell
tar.exe -czf seed-images.tgz -C apps/store-api/uploads products
scp seed-images.tgz root@203.0.113.10:/tmp/
```

> `tar` і `scp` є у Windows 10/11 з коробки — ставити нічого не треба. У PowerShell пишіть
> саме `tar.exe`: голе `tar` може перехопити аліас. У Git Bash обидва рядки працюють як є.

> Пакуємо всю теку `uploads/products`. Якщо ви колись вантажили фото через локальну адмінку,
> вони поїдуть теж — на викидному демо це нешкідливо: імена не перетинаються (сідові файли —
> `seed-<хеш>.webp`, завантажені — `<uuid>.<розширення>`).

**2. На сервері — розпакувати й покласти в том:**

```bash
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"

mkdir -p /tmp/seed-images
tar -xzf /tmp/seed-images.tgz -C /tmp/seed-images
$COMPOSE cp /tmp/seed-images/products store-api:/app/apps/store-api/uploads/
```

**3. Полагодити власника — не пропускайте:**

```bash
$COMPOSE exec -u root store-api chown -R nestjs:nodejs /app/apps/store-api/uploads
```

> `docker cp` кладе файли від імені `root`, а застосунок у контейнері працює під
> користувачем `nestjs`. Читати фото він зможе й так, тому проблема не побачиться одразу —
> вона вилізе пізніше, коли ви спробуєте **завантажити фото товару з адмінки**: адмінка
> пише в цю саму теку `products/` — і не зможе, бо тека вже не її.

**4. Перевірити результат, а не код виходу:**

```bash
$COMPOSE exec store-api sh -c 'ls /app/apps/store-api/uploads/products | wc -l'
$COMPOSE exec store-api sh -c 'ls /app/apps/store-api/uploads/products | head -1'
```

Перше число має бути **тризначним** (близько 125 сідових файлів; точне значення залежить від
каталогу). Якщо `0` або `No such file` — крок 2 не спрацював.

Тоді, підставивши ім'я з другої команди, перевірте, що файл реально роздається:

```bash
curl -sI https://api.203-0-113-10.nip.io/uploads/products/<ім'я-файлу>.webp
```

Очікується `200` і `content-type: image/webp`. `404` тут означає, що файли лягли не в той
том — найчастіше через одруківку в шляху `store-api:/app/apps/store-api/uploads/`.

**5. Прибрати за собою** (файли вже в томі, копії в `/tmp` не потрібні):

```bash
rm -rf /tmp/seed-images /tmp/seed-images.tgz
```

### 7.6. Перевірити, що каталог справді з'явився

**1. База** — той самий one-liner, що й на 7.3:

```bash
node -e "const{Pool}=require('pg');const p=new Pool({connectionString:process.env.DATABASE_URL});p.query('select (select count(*) from products) as products, (select count(*) from users) as users, (select count(*) from categories) as categories, (select count(*) from product_images) as images').then(r=>console.table(r.rows)).catch(e=>console.error('ERR',e.message)).finally(()=>p.end())"
```

Орієнтир: `products` — **понад 150**, `categories` — **понад 40**, `users` — **понад 25**,
`images` — **понад 300**.
Точні числа навмисно не наводимо: каталог демо-даних змінюється, і саме на цих числах цей
ранбук уже одного разу протух. Актуальні значення — в [seed-guide.md](../seed-guide.md) §8.
Важливе тут не збіг до одиниці, а що жоден лічильник не нульовий.

**2. Перезапустіть API на сервері** — це не косметика:

```bash
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"
$COMPOSE restart store-api
```

Сідер писав **прямо в Postgres, повз застосунок**, тому Redis може тримати закешовані
_порожні_ відповіді, а Meilisearch — порожній індекс. Рестарт лагодить обидва разом:
пошуковий сервіс робить best-effort реіндекс на старті. Якщо каталог видно, а пошук порожній —
добийте з адмінки (Налаштування → Пошук) або `POST /api/admin/search/reindex`.

> ⚠️ **При перезаливі цей крок обов'язковий, а не бажаний.** Ресет бази не чіпає Meilisearch,
> тож індекс лишається **не порожнім, а стухлим**: у ньому id товарів, яких у базі вже немає.
> А запасний шлях через Postgres вмикається, лише коли Meilisearch віддав **нуль** збігів або
> помилку. Стухлий індекс віддає ненульові збіги — просто всі вони відсіюються, коли застосунок
> іде за ними в базу. Результат: сторінка пошуку пише «знайдено 42» над **порожньою** сіткою, і
> так лишається, доки не переіндексуєте. Каталог і головна при цьому виглядають бездоганно, бо
> вони ходять у базу напряму.

**3. Очима, з ноута:**

```powershell
curl.exe -s "https://api.203-0-113-10.nip.io/api/products?limit=1"
```

І відкрийте в браузері `https://203-0-113-10.nip.io` — має бути каталог, головна з каруселями
й банерами.

**Дивіться саме на фото.** На плитках категорій і картках товарів мають бути картинки, а не
сірі заглушки з іконкою. Якщо заглушки — база в порядку, а проблема в картинках, і причин
рівно дві:

| Що перевірити                                                             | Якщо не так                                 |
| ------------------------------------------------------------------------- | ------------------------------------------- |
| файли в томі — `curl` на `/uploads/products/<файл>.webp` віддає `200`     | поверніться до кроку 7.5                    |
| `PUBLIC_BASE_URL` у кроці 7.4 = `NEXT_PUBLIC_API_URL` у `.env.production` | адреси розійшлись — див. примітку в кроці 5 |

У другому випадку самого лише виправлення `.env.production` замало: посилання вже записані
в базу. Виправте адреси в `.env.production`, перезберіть фронт (крок 6.2 — `NEXT_PUBLIC_*`
запікаються в образ) і перезалийте каталог за підрозділом «Перезалив на вже сіджений сервер»
нижче.

> **Не `down -v`.** Раніше тут стояла саме ця порада — вона зручна, але коштує дорожче, ніж
> здається: `-v` зносить **усі** томи, зокрема `caddy_data` із сертифікатами й ACME-акаунтом.
> Кожен такий цикл — це 4 нові сертифікати Let's Encrypt (корінь, `admin.`, `api.`,
> `analytics.`) при ліміті **5 дублікатів на тиждень**. `nip.io` у Public Suffix List, тож
> ліміт рахується саме на вашу адресу: два-три перезаливи — і домен без HTTPS до кінця вікна.
> `prisma migrate reset` б'є рівно по базі й лишає сертифікати цілими.

### 7.7. Закрити двері

1. У вікні №1 (тунель) — **Ctrl+C**.
2. На сервері підняти Postgres **без** demo-overlay, щоб прибрати публікацію порту:

   ```bash
   cd /opt/case-store
   docker compose -f docker-compose.prod.yml --env-file .env.production up -d postgres
   docker compose -f docker-compose.prod.yml --env-file .env.production ps postgres
   ```

   У колонці PORTS не має лишитись `127.0.0.1:5432->5432/tcp`. Назовні порт не був видний і
   так, але лишати відкриті двері без потреби нема сенсу.

Файл `docker-compose.demo.yml` не видаляйте — він не під git, переживе `git reset --hard`
(крок 10) і знадобиться, якщо колись доведеться сідити повторно.

### Перезалив на вже сіджений сервер

Усе, що вище, написано під **порожню** базу: крок 7.3 вважає `products: 0` єдиним правильним
результатом. Коли ви перезаливаєте демо вдруге, база не порожня — і просто повторити 7.4
**не можна**.

**Чому.** Позиції сідяться `upsert`-ом по `slug`, але в схемі унікальний ще й `sku`. Коли нова
ревізія каталогу переносить той самий SKU на інший slug, `upsert` за новим slug нічого не
знаходить, іде в гілку «створити» і падає з
`Unique constraint failed on the fields: (sku)`. Саме це зробив TASK-366 (2026-07-30): він
замінив англомовний демо-каталог українським і переніс 9 iPhone-івських SKU на нові slug.
Товари — 6-й із 20 кроків сіду, тож усе решта (атрибути, каруселі, знижки, замовлення,
відгуки, сторінки, блог) просто не виконається, а база лишиться напів-залитою.

Навіть без конфлікту SKU повтор поверх старого каталогу лишає **сиріт**: сідер нічого не
видаляє, тож позиції, яких у новому каталозі вже немає, лишаються в базі живими й видимими.

**Як правильно.** Знести дані й залити наново. Порядок:

1. Кроки **7.1–7.3** як написано (demo-overlay, тунель, `DATABASE_URL`). Перевірка 7.3 покаже
   ненульові лічильники — це нормально, ви ж перезаливаєте; таблиця з ✅ там писана під перший
   запуск.
2. **Ресет бази** — на ноуті, у вікні №2, при піднятому тунелі:

   ```bash
   npx prisma migrate reset --skip-seed --config apps/store-api/prisma.config.ts
   ```

   - Б'є **рівно по базі**: сертифікати Caddy, том із завантаженнями, Redis і Meilisearch
     лишаються на місці. Тому не `down -v` (див. врізку в 7.6).
   - `--skip-seed` **обов'язковий**: без нього Prisma запустить сід сама — ще до того, як ви
     виставите змінні з 7.4, — і він впаде на запобіжнику `ALLOW_PROD_SEED`.
   - `--config`, а не `--schema` — та сама пастка, що в кроці 6.3: URL бази лежить у
     `prisma.config.ts`.
   - Reset сам накотить міграції, тож окремий `migrate deploy` після нього не потрібен.
   - Тепер повторіть перевірку 7.3: має бути `products: 0`, `users: 0`.

3. **Прибрати старі картинки на сервері** — прунер сідера працює на ноуті, до серверного тому
   він не дотягується, тож файли старого каталогу лишились би сиротами:

   ```bash
   cd /opt/case-store
   COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"
   $COMPOSE exec store-api sh -c 'rm -f /app/apps/store-api/uploads/products/seed-*.webp'
   ```

   Реальних завантажень не зачепить: ті названі `<uuid>.<розширення>` і під шаблон
   `seed-*.webp` не підпадають.

4. Далі **7.4 → 7.5 → 7.6** без змін. Крок 7.6.2 (рестарт API) після перезаливу **критичніший,
   ніж при першому запуску** — причина у врізці там же.

## 8. Закрити демо від Google

Прод-Caddy глушить індексацію лише `admin.` і `api.`, а **вітрину — ні** (у справжньому
проді вона МАЄ індексуватись). Для тимчасового демо це небажано.

> **Не шукайте перемикач в адмінці — його прибрали (TASK-307).** Старий чекбокс «Приховати
> сайт від пошукових систем» (`noindexSite`) був заряджений на живий магазин і давав лише
> `robots.txt`-disallow. Тепер середовище закривають на рівні проксі заголовком
> **`X-Robots-Tag: noindex`** (так само робить staging — `Caddyfile.staging`). Він **сильніший
> за `robots.txt`**: не просто _просить_ не сканувати, а здатний **прибрати з індексу** навіть
> URL, які Google уже знає. І не потребує ані логіну в адмінку, ані запису в БД.

Додайте цей заголовок на блок вітрини в Caddy (усе — на сервері):

1. Відкрийте конфіг: `nano /opt/case-store/Caddyfile`.
2. Знайдіть блок вітрини — він починається з `{$DOMAIN} {` і **єдиний без** `X-Robots-Tag`
   (`admin.`/`api.` уже мають його). Додайте всередину блоку рядок:

   ```
   {$DOMAIN} {
       header X-Robots-Tag "noindex, nofollow, noarchive"

       encode zstd gzip
       reverse_proxy store-client:3000
   }
   ```

   Збережіть: **Ctrl+O**, Enter; вийдіть: **Ctrl+X**.

3. Перечитайте конфіг проксі:

   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.production restart caddy
   ```

4. Перевірте, що заголовок віддається:

   ```bash
   curl -sI https://203-0-113-10.nip.io | grep -i x-robots-tag   # має бути noindex
   ```

> **Про «вікно індексації».** Google індексує сторінку лише **після того, як знайде** її
> URL (посилання десь, sitemap, ручна подача). Свіжий `nip.io`-хост без жодного вхідного
> посилання для Google практично невидимий, тож ризик у короткому демо ≈ нульовий. Щоб
> закрити вікно повністю — виставте цей заголовок **до кроку 9** (перш ніж роздати
> посилання). Разом з обскурною адресою й коротким життям демо цього достатньо.

## 10. Оновити демо після змін у коді

CI тут немає, тож `git push` **сам по собі нічого не робить** — сервер про нього не дізнається.
Оновлення завжди ручне, і послідовність має значення.

**1. На ноуті** — закоміть і запуш зміни у `develop`. Якщо зачепили API (контролери, DTO,
Swagger-декоратори) — **перегенеруйте контракт і закоміть його разом зі змінами**, інакше
фронт збереться зі старим (крок 6.0). Везти файл окремо більше не треба — він приїде з
`git reset --hard` на кроці 2:

```bash
npm run swagger:export -w apps/store-api
npm run generate:api
git add apps/store-api/swagger.json && git commit -m "chore(api): refresh OpenAPI contract"
git push
```

**2. На сервері — забрати код.** У теці є локальні правки в трекованих файлах, тому звичайний
`git pull` упреться в конфлікт. Для викидного демо найпростіше взяти стан гілки як є:

```bash
cd /opt/case-store
git fetch origin
git reset --hard origin/develop
```

> `reset --hard` затирає всі правки в **трекованих** файлах. Ваше локальне лежить поза git:
> `.env.production` — у `.gitignore`, `docker-compose.demo.yml` — не доданий до індексу.
> Вони переживуть скидання.
>
> ⚠️ **`swagger.json` тепер трекований** (TASK-325) — `reset --hard` **перезапише** його
> версією з гілки. Це саме те, що потрібно: контракт має приїжджати з кодом, а не жити на
> сервері окремим життям. Не редагуйте його на сервері.
>
> **А от одну правку треба повернути руками:** заголовок `X-Robots-Tag` у `Caddyfile` (крок 8).
> Перегенеровувати локфайл на сервері більше не треба — linux-бінарники `lightningcss` і
> `@tailwindcss/oxide` тепер закріплені в кореневих `optionalDependencies` (TASK-326), тож
> `npm ci` усередині образу ставить їх сам.
>
> Щоб не робити це щоразу вручну, збережіть копію під іншим ім'ям **одразу після кроку 8** —
> `Caddyfile.demo` не під git, тож `reset --hard` його не чіпає:
>
> ```bash
> cp Caddyfile Caddyfile.demo            # один раз
> cp Caddyfile.demo Caddyfile            # після кожного reset --hard
> ```
>
> **Обов'язково перевіряйте після оновлення** — забутий заголовок означає, що демо відкрите
> для індексації:
>
> ```bash
> curl -sI https://203-0-113-10.nip.io | grep -i x-robots-tag
> ```
>
> (у PowerShell на ноуті: `curl.exe -sI https://… | Select-String X-Robots-Tag` — `curl` там
> аліас на `Invoke-WebRequest`, а `grep` немає взагалі)

> 🚫 **`Caddyfile.demo` помирає разом із демо — на інші середовища не переносьте.** Цей хак
> потрібен рівно тут, бо демо крутиться на **прод**-конфізі Caddy. Далі по маршруту все інакше:
>
> | Середовище            | Вітрина в пошуку      | Хто це забезпечує                                                            |
> | --------------------- | --------------------- | ---------------------------------------------------------------------------- |
> | демо на `nip.io`      | закрита               | ручна правка `Caddyfile` (крок 8)                                            |
> | staging / тест-сервер | закрита               | `Caddyfile.staging` — `X-Robots-Tag` на всіх трьох + basic_auth, автоматично |
> | **прод замовника**    | **МАЄ індексуватись** | прод-`Caddyfile` глушить лише `admin.` і `api.` — так і задумано             |
>
> Занести цей заголовок на живий магазин = прибрати його з Google і знищити органічний трафік,
> заради якого робився весь SEO-блок.

**3. Перезібрати тільки те, що змінилось** (по одному — крок 6.2):

| Що змінили                                       | Що перезбирати         |
| ------------------------------------------------ | ---------------------- |
| код `apps/store-api`                             | `store-api`            |
| код вітрини / адмінки                            | відповідний фронт      |
| будь-який `NEXT_PUBLIC_*` або адресу             | **обидва** фронти      |
| лише `.env.production` (runtime-змінні, не бейк) | нічого, досить `up -d` |

```bash
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"
$COMPOSE build store-client        # приклад: змінили лише вітрину
$COMPOSE up -d
```

`up -d` перестворює **лише** ті контейнери, у яких змінився образ, — решта продовжує працювати.

**4. Якщо мінялась схема Prisma** — накотіть міграції (крок 6.3):

```bash
$COMPOSE exec -T store-api npx prisma migrate deploy --config prisma.config.ts
```

**5. Сід повторно НЕ запускайте** — він залив би демо-каталог поверх даних, які ви вже
показували. Він потрібен рівно один раз, на кроці 7.

> Якщо все ж довелося пересіяти — **повторіть і крок 7.5**. Імена файлів картинок
> вираховуються з їхнього вмісту, тож інший каталог дає інший набір файлів, і старі в томі
> вже нічому не відповідають.

> **Демо, підняте до 2026-07-30**, стоїть на старому каталозі (наполовину англійському, з
> фото зі стороннього сервісу). Пересів його не полагодить: сід нічого не видаляє, тож старі
> позиції лишаться поруч із новими. Для викидного демо найпростіше — знести стек і пройти
> кроки 6–7 заново (розділ 11).

**6. Перевірте:**

```bash
$COMPOSE ps                                        # усі healthy
curl -sI https://api.203-0-113-10.nip.io/health    # 200
```

керує CI, а не ручна збірка.
