## Куди ми йдемо

Магазин живе на **двох власних серверах** (VPS), у Docker. Зміни потрапляють туди
автоматично через GitHub Actions:

- **Staging** — тестовий магазин. Усе, що зливається в `develop`, після зелених тестів
  їде туди **саме́**. Закритий паролем. Дані одноразові — там можна й **треба** ламати.
- **Продакшен** — справжній магазин. Їде з `main` і **чекає, поки ви натиснете «Approve»**.
  Перед кожним деплоєм автоматично знімається бекап бази.

> ⚠️ **Staging — це репетиція, а не «перевірений образ, який поїде далі».** Прод
> **збирає власні образи з нуля**, а не бере ті, що вже перевірені на staging. Так
> вийшло не через недогляд: значення з префіксом `NEXT_PUBLIC_` **запікаються в
> образ під час збірки**, тобто staging-образ фізично містить staging-адреси й на
> проді працювати не може.
>
> Практичний висновок: зелений staging доводить, що **код** справний — але не
> гарантує, що прод отримає той самий бінарник. Речі, які на staging і на проді
> задані **різними** значеннями (адреси, `NEXT_PUBLIC_PAYMENT_METHODS`, ключі),
> перевіряються на проді **окремо** — див. [09-pre-launch.md](09-pre-launch.md).

> **Одна дорога, не дві.** У проєкті колись була альтернативна інструкція на Vercel +
> Railway. Вона **більше не актуальна** й лежить в `../archive/deploy-vercel.md` — не
> користуйтесь нею: під VPS-шлях зроблено все інше (бекапи, відкат, моніторинг, CI).

## Словник за 30 секунд

| Слово        | Що це                                                                                                            |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| **VPS**      | орендований сервер у хмарі                                                                                       |
| **CI**       | автоматичні перевірки коду на GitHub (тести, лінт, збірка)                                                       |
| **образ**    | «заморожена» збірка одного застосунку                                                                            |
| **GHCR**     | сховище образів GitHub (`ghcr.io`), звідки сервер їх завантажує                                                  |
| **сервіс**   | один контейнер: `store-api`, `store-client`, `store-admin`, `postgres`, `redis`, `meilisearch`, `umami`, `caddy` |
| **SHA**      | короткий код коміту, напр. `a1b2c3d`; тег образу — `prod-<SHA>`                                                  |
| **міграція** | зміна структури бази даних                                                                                       |
| **staging**  | тестовий магазин-двійник, де можна ламати                                                                        |

Стек на сервері живе в теці **`/opt/case-store`**:

```bash
ssh deploy@<адреса-сервера>
cd /opt/case-store
```

> **Про довгі команди.** На **staging** усі команди `docker compose` беруть **два** файли:
> `-f docker-compose.prod.yml -f docker-compose.staging.yml`. На **проді** — тільки перший.
> Якщо команда поводиться дивно — перевірте це першим.

## Чесно про терміни

**Staging і проходження QA — реально.** Прод із прийманням оплати — ні: найдовше там не код,
а **мерчант-акаунт** (ФОП + схвалення банку, тижні бюрократії). Це не залежить від
розробки й має початися паралельно, вже зараз.

Зараз чекаут чесно каже «оплата при отриманні» — це робочий стан для запуску.
