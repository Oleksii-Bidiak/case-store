# 10. Скільки витримає сервер і який купувати

> **Кому це.** Тому, хто має ухвалити рішення про залізо — і не хоче ухвалювати
> його навмання. Крок 10 у маршруті [00-start-here.md](00-start-here.md).
>
> **Коли читати.** Перед покупкою бойового сервера, і потім щоразу, коли зʼявилось
> відчуття «сайт почав гальмувати». Друге важливіше: без цифри «як було» слово
> «гальмує» нічим не перевіриш.

## 0. Головне за одну хвилину

1. Купувати треба **під заміряну цифру**, а не під відчуття. До TASK-392 у
   репозиторії не було жодного навантажувального тесту, тож усі оцінки місткості
   були висновками з конфігів.
2. Стартова точка — **Hetzner CX22/CX23: 2 vCPU / 4 ГБ / 40 ГБ, ~5 €/міс**. Ліміти
   памʼяті в `docker-compose.prod.yml` складені саме під неї.
3. **Тільки x86-64.** ARM (CAX/Ampere) не збереться — див. [03-server.md](03-server.md).
4. Прогін робиться **на staging**, з чужої машини, і **ніколи** з того самого
   сервера, який міряєш.
5. Спершу прочитай §4 «Що знецінює прогін». Три з чотирьох пасток дають красиві
   цифри, які нічого не означають.

---

## 1. Що саме міряємо

Три сценарії в `scripts/load/`, кожен відповідає на своє питання:

| Скрипт      | Питання                                   | Коли запускати               |
| ----------- | ----------------------------------------- | ---------------------------- |
| `browse.js` | Скільки покупців одночасно тримає вітрина | Основний прогін              |
| `images.js` | Скільки коштує оптимізація картинок       | Двічі: холодний і теплий кеш |
| `admin.js`  | Чи можна вести адмінку в робочий час      | **Одночасно** з `browse.js`  |

Третій — не факультатив. Питання «невже ніхто не сидітиме ночами, додаючи товар»
має заміряну відповідь, а не думку: правки в адмінці роблять помітно більше
роботи, ніж перегляд сторінки (інвалідація ключів Redis через `SCAN`, переіндексація
Meilisearch, і з TASK-384 ще й скидання головної на вітрині).

## 2. Як запускати

k6 береться готовим образом — у репозиторій нічого не додається.

```bash
# 1. Основний прогін (з ноутбука, НЕ з сервера)
docker run --rm -i -v "$PWD/scripts/load:/load" \
  -e BASE_URL=https://staging.<домен> \
  -e BASIC_AUTH_USER=staging -e BASIC_AUTH_PASS='<пароль>' \
  grafana/k6 run /load/browse.js

# 2. Паралельно, у другому терміналі — на сервері
watch -n 2 'docker stats --no-stream; uptime'
```

`BASIC_AUTH_*` обовʼязкові для staging: він закритий паролем у `Caddyfile.staging`,
і без них **кожен** запит поверне 401 — прогін виглядатиме блискавичним і не
виміряє нічого.

Для картинок — два прогони підряд, і саме **різниця** між ними є результатом:

```bash
docker compose -f docker-compose.prod.yml restart store-client   # кеш порожній
docker run ... -e RUN_LABEL=cold grafana/k6 run /load/images.js
docker run ... -e RUN_LABEL=warm grafana/k6 run /load/images.js
```

Холодна цифра — це те, що бачать відвідувачі **після кожного деплою**; тепла — те,
що вони бачать решту часу.

## 3. Як перетворити результат на рішення

Беремо **найвищу сходинку**, на якій `page_duration` p95 < 800 мс, нема 5xx і нема 429. Далі:

```
одночасні відвідувачі ≈ (переглядів сторінок за секунду на цій сходинці)
                        × середній інтервал між кліками (8 с)
```

Тобто стійкі 6 переглядів/с ≈ **48 одночасних відвідувачів**. Назад до добових
візитів: пік години в українському e-commerce — приблизно 12–15 % добового трафіку,
тож 48 одночасних тримають пік приблизно 1 500–2 500 візитів на добу.

> Число 8 с — не константа всесвіту, а те саме `THINK_TIME_SECONDS` зі
> `scripts/load/lib.js`. Змінюєш там — змінюй і тут, інакше формула бреше.

Далі за результатом:

| Що показав прогін                                                 | Рішення                                                                                                                                                                                           |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| p95 < 800 мс на цільовому навантаженні, CPU < 60 %                | **Нічого не купувати.** CX22/CX23 вистачає                                                                                                                                                        |
| Уперлось у CPU, і `store_prod_client` їсть ядра на `/_next/image` | Спершу перевірити, що заголовки з TASK-387 і том `next_image_cache` на місці. Переміряти. Лише потім — CX33 (4 vCPU / 8 ГБ, ~8,5 €/міс)                                                           |
| Контейнер убитий OOM                                              | CX33 + перерозподіл `MEM_*` (з `MEM_MEILI` можна безболісно зняти до 192m)                                                                                                                        |
| Помилки з `pool_timeout` через 20 с                               | Підняти `PRISMA_CONNECTION_LIMIT` (зараз 10). Спершу перевірити, що це справді діє: рантайм працює через `PrismaPg`-адаптер, тобто пул — це `pg.Pool`, чий дефолт `max` теж 10, і збіг випадковий |
| Багато 429                                                        | **Це не про залізо.** Див. §4                                                                                                                                                                     |

### Про «докупити залізо» на Hetzner

Так, можна, з двома нюансами:

1. Rescale вимагає **короткого вимкнення** сервера — хвилини простою, кілька
   кліків у консолі.
2. **Диск росте лише в один бік.** При апгрейді обирай «CPU and RAM only», інакше
   диск теж збільшиться і сервер уже **не здешевиш назад**. Тобто нарощуй CPU/RAM
   (оборотно), диск чіпай востаннє.

Горизонтальне масштабування вже підготовлене й **не потребує Kubernetes**: другий
контейнер `store-api` з `SCHEDULER_ENABLED=false` (інакше подвійна розсилка листів і
подвійна звірка платежів). Другу репліку **вітрини** так просто додати не можна —
Next тримає реєстр кеш-тегів у памʼяті процесу, тож `revalidateTag` дійде лише до
однієї з них.

## 4. Що знецінює прогін

Чотири речі. Три з них дають гарні цифри — тому вони й небезпечні.

**1. 429 у результатах.** `rate_limited_429` рахується окремо від решти помилок
навмисно: 429 означає «сервер відмовив, не почавши роботу». Такий прогін для
сайзингу **непридатний** — ти виміряв ліміт, а не сервер. До TASK-386 усі
відвідувачі ділили одне відро на 100 запитів/хв, бо за проксі Express бачив адресу
контейнера Caddy замість адреси покупця. Якщо 429 зʼявились знову — питання не в
залізі.

**2. Прогін із того самого сервера.** k6 і магазин почнуть ділити ті самі два ядра.
Цифра буде про суміш, а не про магазин.

**3. Прогін з Windows / Docker Desktop.** Виміряєш Docker Desktop.

**4. Порожній каталог.** Сторінки без товарів рендеряться миттєво. `browse.js` і
`images.js` спеціально падають на старті, якщо каталог порожній, — краще відмова,
ніж швидка неправда.

## 5. Журнал прогонів

Заповнюй **кожен** прогін, навіть невдалий. Одна цифра — це анекдот; ряд цифр — це
підстава щось купувати.

| Дата | Стенд | Сценарій | VUs на межі | p95, мс | 5xx | 429 | CPU max | Висновок                 |
| ---- | ----- | -------- | ----------- | ------- | --- | --- | ------- | ------------------------ |
| —    | —     | —        | —           | —       | —   | —   | —       | _(baseline ще не знято)_ |

> **Baseline знімається до наступних оптимізацій, а не після.** Без «як було»
> будь-яке «стало краще» — це віра.
