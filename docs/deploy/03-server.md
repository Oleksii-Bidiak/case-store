# Сервери — оренда й налаштування

> **Перед цим:** [01-accounts-access.md](01-accounts-access.md) — щоб не орендувати сервер
> не на того. Переносити потім боляче.
>
> Робіть **спершу staging**. Це і є репетиція: усе те саме, але ціна помилки нульова.

---

## 1. Скільки серверів — два

Один VPS для staging, один для прода. Причина не в потужності (обидва невеликі), а в тому,
що на staging ви будете **навмисно ламати й скидати** — репетиція відновлення бекапу,
репетиція відкату, повне стирання бази.

Окремий сервер робить відповідь на питання «в якому я середовищі?» **фізичною**, а не
питанням уважності о другій ночі. Це головний аргумент: колись ви втомлені виконаєте
руйнівну команду, і має бути гарантія, що вона потрапила не в прод.

**Рекомендація:** Hetzner CX22 (2 vCPU / 4 ГБ / 40 ГБ), ~€4/міс кожен. DigitalOcean —
рівноцінна заміна; решта інструкції від хостера не залежить. Ціни звіряйте на сайті.

> Акаунт хостера — **на замовника** ([01-accounts-access.md](01-accounts-access.md) §1).
> Це не формальність: панель хостера — майстер-ключ до сервера (§5).

---

## 2. Створити користувача

Працювати під `root` щодня — погана ідея: будь-яка помилка стає незворотною.

```bash
# на сервері, під root
adduser deploy
usermod -aG sudo deploy
```

## 3. SSH-ключі — і одразу другий, резервний

**На своєму ноутбуці**, не на сервері:

```bash
ssh-keygen -t ed25519 -C "store-ai deploy"
ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@<IP-сервера>
```

### ⚠ Одразу зробіть резервний ключ

Це п'ять хвилин зараз замість інциденту потім. Після наступного розділу вхід паролем буде
вимкнений, і приватний ключ існуватиме рівно у двох місцях: **ваш ноут** і **GitHub
Secrets** — звідки його **не прочитати назад** ніколи.

**Помер ноут → SSH-доступу немає ні в кого.**

```bash
# другий ключ, окремий
ssh-keygen -t ed25519 -C "store-ai backup key" -f ~/.ssh/store-ai-backup
ssh-copy-id -i ~/.ssh/store-ai-backup.pub deploy@<IP-сервера>
```

Приватну частину (`~/.ssh/store-ai-backup`) покладіть **у менеджер паролів** — і видаліть
з ноута. Сенс саме в тому, щоб вона не лежала поруч із основним ключем.

> ⚠ **Перш ніж закрити root-сесію** — відкрийте **другий термінал** і переконайтесь, що
> `ssh deploy@<IP>` працює. Інакше можна замкнути себе зовні власного сервера.

## 4. Захист сервера

```bash
# 1. Вимкнути вхід паролем і root-логін
sudo nano /etc/ssh/sshd_config      # PasswordAuthentication no / PermitRootLogin no
sudo systemctl restart sshd

# 2. Фаєрвол + автооновлення безпеки + fail2ban + інструменти бекапу
sudo apt update && sudo apt install -y ufw unattended-upgrades fail2ban age rclone
sudo ufw allow OpenSSH && sudo ufw allow 80 && sudo ufw allow 443 && sudo ufw enable
sudo dpkg-reconfigure -plow unattended-upgrades

# 3. Docker
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker deploy

# 4. Тека стека
sudo mkdir -p /opt/store-ai && sudo chown deploy /opt/store-ai
```

**Порти 80 і 443 мають бути відкриті** — без них Caddy не отримає HTTPS-сертифікат
([02-domain-dns.md](02-domain-dns.md) §6).

Файли (`docker-compose*.yml`, `Caddyfile*`, `scripts/`, `docker/`) пайплайн **копіює сам**
на кожному деплої — вручну класти не треба.

## 5. Якщо доступ усе-таки втрачено

Знати це **до** того, як знадобиться.

Панель хостера дає **веб-консоль** — віртуальний монітор і клавіатуру, підключені до сервера
напряму. Вона працює навіть коли `sshd` мертвий або вимкнений, тому `PasswordAuthentication
no` їй не заважає.

1. Панель хостера → сервер → **Reset root password**.
2. Панель → **Console** → зайти як `root`.
3. Додати новий публічний ключ у `/home/deploy/.ssh/authorized_keys`.
4. Перевірити вхід по SSH з нового ноута — **і лише потім** закрити консоль.

**Це і є причина, чому акаунт хостера потребує 2FA і має бути на замовнику** — інакше
майстер-ключ від сервера лежить у випадкової людини.

### Репетиція — зробіть один раз на staging

Дві репетиції вже є в цих доках (відновлення бекапу, відкат образу). **Це третя, і вона
найдешевша:** один раз зайдіть через веб-консоль хостера, не користуючись SSH-ключем.

Перевіряєте одразу дві речі: що шлях працює **і** що акаунт хостера справді доступний.
Займає 10 хвилин. Робиться один раз. Знімає найгірший сценарій із трьох.

## 6. Перевірка

```bash
ssh deploy@<IP>                     # заходить без пароля
ssh -i ~/.ssh/store-ai-backup deploy@<IP>   # резервний ключ теж працює
docker --version                    # Docker є
sudo ufw status                     # 80, 443, OpenSSH — allow
```

Обидва ключі мають працювати. Якщо резервний не працює — ви дізнаєтесь про це зараз, а не
в аварії.

Ті самі кроки — **на другому сервері** (прод).
