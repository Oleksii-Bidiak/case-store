# Щоденна робота — щоб магазин не падав

> **Для кого:** для того, хто ніколи не адміністрував сервер. Це не довідник — це те, що
> треба знати, щоб магазин працював, а ви спали.
>
> Розділ 5 (playbook аварії) — **роздрукуйте**. Під час інциденту ви не будете думати ясно,
> і це нормально.

---

## 0. Головне за одну хвилину

Дешевий VPS падає майже завжди з однієї з двох причин. **Обидві повністю передбачувані, і
обидві вже закриті в конфігурації** — але ви маєте знати, що вони існують:

1. **Закінчилось місце на диску.** Docker за замовчуванням зберігає логи **вічно**. Нічого
   не ламається, ніхто не попереджає — просто через кілька місяців Postgres не може
   записати байт, і все зупиняється одночасно. → Закрито ротацією логів (≈240 МБ стеля).
2. **Закінчилась пам'ять.** Один застосунок «тече», росте, і ядро Linux вбиває **найбільший
   процес** — а це зазвичай Postgres. Тобто витік у вітрині кладе базу. → Закрито лімітами
   пам'яті: тепер помирає той, хто винен, і `restart: unless-stopped` його одразу піднімає.

Третя причина — **ви самі**, під час деплою. Про це [05-first-deploy.md](05-first-deploy.md) §5.

## 1. Щоб ви дізнались про поломку раніше за клієнта

Найважливіший розділ, який усі відкладають. Без нього ви дізнаєтесь про падіння магазину з
листа розлюченого покупця — через 6 годин.

### 1.1 Sentry — помилки в коді

DSN **уже вшитий у код**, лишилось заповнити.

1. Зареєструйтесь на [sentry.io](https://sentry.io) (безкоштовного тарифу вистачає).
2. Створіть проєкт → скопіюйте DSN.
3. GitHub → Environments → `production` → Secrets → **`PROD_ENV_FILE`**: додайте рядок
   `SENTRY_DSN=https://...` і запустіть деплой (Actions → CI → Run workflow).
4. GitHub → Environments → `production` → **Variables**: `NEXT_PUBLIC_SENTRY_DSN`.
   Це вже **білд-тайм** значення — потрібне перезбирання, а не перезапуск.

Тепер кожна 500-та помилка прилітає вам із повним стеком і контекстом запиту.

> 📌 **Куди насправді писати змінні — читайте один раз і назавжди.**
> Джерело істини для рантайм-змінних — секрет **`PROD_ENV_FILE`** у GitHub
> Environment, а **не** файл на сервері: кожен деплой перезаписує
> `/opt/case-store/.env.production` із цього секрету. Правка руками на сервері —
> це **тимчасовий обхід під час інциденту**, і її треба того ж дня продублювати в
> секрет, інакше наступний деплой мовчки поверне старе значення.
> Ця сторінка й [05a-analytics.md](05a-analytics.md) подекуди кажуть «відредагуйте
> `.env.production` на сервері» — читайте це саме як обхід; правило з
> [05-first-deploy.md](05-first-deploy.md) §7 («ніколи не редагуйте файли на
> сервері») головніше.
>
> І окремо: після правки — **`up -d`, а не `restart`**. `docker compose restart`
> перезапускає процес зі **старими** змінними, бо env-файл перечитує лише `up -d`.
> Половина випадків «я ж змінив значення, а нічого не змінилось» — саме це.

#### Правила сповіщень — без них Sentry мовчить

Сам по собі Sentry **збирає** помилки, але пише вам лише за правилами. Нове правило
«за замовчуванням», яке Sentry створює з проєктом, — не те, на що варто покладатись: ви
маєте знати, **що** саме вас розбудить. Потрібно два правила. Назви пунктів меню Sentry час
від часу змінює — шукайте розділ **Alerts** (сповіщення) і тип правила **Issues** (за
помилками, не за метриками).

1. **«Нова помилка»** — дізнатись про поломку, якої ще не було.
   - Alerts → **Create Alert** → **Issues**.
   - **Environment:** `production` (інакше розбудить і staging).
   - **When:** «A new issue is created» (створено нову помилку).
   - **Then:** «Send a notification to» → **Member** → ви (лист на пошту).
   - Назва: `prod — нова помилка`.
2. **«Сплеск»** — стара помилка раптом почала сипатись сотнями.
   - Alerts → **Create Alert** → **Issues**, **Environment:** `production`.
   - **When:** «The issue is seen more than **50** times in **1 hour**» (помилку побачено
     понад 50 разів за годину).
   - **Then:** лист вам. **Action interval** (як часто повторювати): **1 hour**.
   - Назва: `prod — сплеск`.

Канал — **пошта**: вбудованої інтеграції з Telegram у Sentry немає, а пошта є на
безкоштовному тарифі й працює без налаштувань. Щоб не проґавити лист, увімкніть для адреси
відправника Sentry сповіщення на телефоні (або пересилання в Telegram, якщо ваша пошта це
вміє).

**Перевірка правил** (раз, після налаштування): у правилі «Нова помилка» є кнопка
**Send Test Notification** — натисніть і переконайтесь, що лист дійшов і не в спам.

> **Staging.** Staging може слати в той самий проєкт Sentry: його помилки приходять із
> міткою `staging`, тож правила вище (фільтр `production`) через тестові поломки вас не
> будитимуть. Нічого налаштовувати не треба — мітку `staging` для API жорстко задає
> `docker-compose.staging.yml`, і вона перемагає `SENTRY_ENVIRONMENT=production`, який
> потрапляє в env-секрет staging разом із копією прод-шаблону (TASK-739); фронти отримують
> `staging` ще під час збірки в CI. Тож рядок `SENTRY_ENVIRONMENT` у секреті staging можна
> не чіпати — на staging він не діє.

#### Трасування — `SENTRY_TRACES_SAMPLE_RATE=0.05`

Крім помилок, Sentry вміє показати, **який запит повільний і чому** (трасування). Записувати
кожен запит — дорого для безкоштовної квоти; 5 % — кожен двадцятий — вистачає, щоб бачити
повільні місця, і квота живе.

| Де                | Змінна                                  | Куди записати                                                                        | Що після                    |
| ----------------- | --------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------- |
| API (`store-api`) | `SENTRY_TRACES_SAMPLE_RATE=0.05`        | рядок у секреті **`PROD_ENV_FILE`** (GitHub → Environments → `production` → Secrets) | деплой (він робить `up -d`) |
| Вітрина й адмінка | `NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` | **поки що нікуди** — див. нижче                                                      | —                           |

- **API** читає змінну під час старту. Значення поза межами 0…1 (наприклад `5` замість
  `0.5`) **не дасть API стартувати** — це навмисно, щоб помилка не пройшла тихо. Тож
  пишіть рівно `0.05`.
- **Вітрина й адмінка** читають `NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE`, а вона
  **вшивається під час збірки образу**. Збірка в CI зараз цю змінну не передає (відкрита
  задача TASK-737 у `BACKLOG.md`), тож додавати її в GitHub Variables поки марно — фронти
  трасують 0 %. Це не проблема: **помилки** з фронтів летять і без трасування, а
  найцінніше трасування — саме API.

### 1.2 Uptime-моніторинг — «сайт лежить»

Sentry не побачить, якщо сервер **зовсім** не відповідає. Потрібна перевірка ззовні: сервіс,
який кожні кілька хвилин відкриває ваш сайт з іншого кінця світу і пише вам, коли не зміг.

**Вибір: [UptimeRobot](https://uptimerobot.com).** Він уміє все потрібне нижче, включно з
перевіркою ключового слова. Безкоштовний тариф — 50 моніторів, перевірка раз на 5 хвилин,
сповіщення в пошту й у мобільний застосунок UptimeRobot. **Telegram на безкоштовному тарифі
немає** — він з'являється на найдешевшому платному (Solo). Безкоштовний тариф UptimeRobot
позиціонує для хобі й неприбуткових проєктів; магазин — комерційний, тож Solo — і чесний,
і зручніший вибір (Telegram + перевірка частіше). Ціни й склад тарифів змінюються —
звірте на [сторінці цін](https://uptimerobot.com/pricing/) у момент реєстрації.

> **Альтернатива — [Better Stack](https://betterstack.com/uptime).** Безкоштовно — 10
> моніторів разом із «heartbeat»-перевірками (тобто він може замінити й healthchecks.io з
> §1.3–1.4), перевірка раз на 3 хвилини, сповіщення в пошту й Slack. Годиться, якщо ви вже
> там. Двох сервісів для одного й того самого не тримайте — оберіть один.

#### Крок 1. Куди слати сповіщення

1. Зареєструйтесь на UptimeRobot, увімкніть 2FA
   ([01-accounts-access.md](01-accounts-access.md)).
2. Встановіть на телефон застосунок **UptimeRobot** і увійдіть — це безкоштовні push-сповіщення.
3. **Telegram** (платний тариф): My Settings → **Alert Contacts / Integrations** → **Add** →
   **Telegram** → відкриється бот UptimeRobot у Telegram → натисніть **Start** → поверніться
   в UptimeRobot, контакт з'явиться в списку.
4. Пошта — додається автоматично (адреса реєстрації).

#### Крок 2. Чотири монітори

Для кожного: **+ New monitor**, інтервал — найменший доступний, у **Alert contacts** —
позначте телефон, пошту і (якщо є) Telegram.

| #   | Назва                  | Тип         | Адреса                       | Що налаштувати окремо                                                                           |
| --- | ---------------------- | ----------- | ---------------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | `API — живий`          | **HTTP(s)** | `https://api.<домен>/health` | —                                                                                               |
| 2   | `API — без деградації` | **Keyword** | `https://api.<домен>/health` | Keyword: `"degraded":false` (рівно так, з лапками, без пробілів); тривога, коли слова **НЕМАЄ** |
| 3   | `Вітрина`              | **HTTP(s)** | `https://<домен>/`           | —                                                                                               |
| 4   | `Адмінка`              | **HTTP(s)** | `https://admin.<домен>/`     | —                                                                                               |

Адреси `/health`, `/` і `admin.` — ті самі, що перевіряє CI після деплою. Зверніть увагу:
`/health` **без** `/api` на початку.

> **Навіщо два монітори на одну адресу.** `/health` відповідає одним рядком JSON, **без
> пробілів** (саме тому й ключове слово пишеться без пробілу):
>
> ```text
> {"status":"ok","degraded":false,"timestamp":"…","uptime":123.4,"checks":{"database":"up","rateLimitStore":"up"}}
> ```
>
> - **База впала** → відповідь **503** і `"status":"error"`. Це ловить монітор №1.
> - **Redis упав** (у ньому лічильники захисту від перебору паролів і спаму) → відповідь
>   **200**, але `"degraded":true`. Сторінки відкриваються, тому монітор №1 **лишається
>   зеленим** — і саме тому потрібен №2. А поки Redis лежить, **вхід, реєстрація,
>   оформлення замовлення**, відновлення пароля, контактна форма, відгуки й підписка
>   відповідають покупцям помилкою (так задумано: без лічильника ці форми нічим не захищені
>   від перебору й спаму). Тобто сайт «живий», але **не продає** — це така сама тривога, як і
>   падіння.
> - Сам запит монітора теж проходить через лічильник, тож `degraded` показує стан Redis на
>   момент перевірки, а не годину тому.
>
> Що робити, коли спрацював №2: `$COMPOSE ps redis`, `$COMPOSE logs --tail=50 redis`,
> `$COMPOSE up -d redis`. У логах API шукайте `throttler.redis.unreachable` /
> `throttler.redis.recovered`.

#### Крок 3. Переконатись, що тривога справді приходить

Монітор, якого ви жодного разу не бачили червоним, — це надія, а не монітор. Робіть це на
**staging** (або на проді вночі — це кілька хвилин справжнього простою):

```bash
ssh deploy@<сервер>
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"   # на staging: + -f docker-compose.staging.yml

$COMPOSE stop store-client     # → за ≤5 хв має прийти тривога «Вітрина»
$COMPOSE up -d store-client    # → і за ≤5 хв — «знову працює»

$COMPOSE stop redis            # → тривога «API — без деградації», а «API — живий» лишається зеленим
$COMPOSE up -d redis
```

Прийшло на телефон (і в Telegram, якщо налаштовували) — готово. Не прийшло — перевірте
**Alert contacts** у самому моніторі: найчастіше монітор створили, а контакт до нього не
прив'язали.

### 1.3 Місце на диску — щогодинна перевірка

Скрипт `scripts/disk-check.sh` дивиться, наскільки заповнений диск, і при **80 % і більше**
повідомляє. Звітує він у [healthchecks.io](https://healthchecks.io) — безкоштовний сервіс,
який робить дві речі одразу:

- скрипт каже «диск повний» → healthchecks.io пише вам у Telegram / на пошту;
- скрипт **перестав** звітувати взагалі (зник cron, сервер лежить) → healthchecks.io
  помічає тишу й теж пише вам. Це й називається «dead-man switch» — тривога на
  **відсутність** сигналу.

Без адреси healthchecks.io скрипт нічого не надсилає — лише друкує попередження, коли диск
заповнений (у лог cron), — тож його безпечно запускати й без реєстрації.

**Один раз налаштувати healthchecks.io** (той самий акаунт знадобиться в §1.4):

1. Зареєструйтесь на [healthchecks.io](https://healthchecks.io) (безкоштовно — 20 перевірок),
   увімкніть 2FA.
2. **Integrations** → **Telegram** → відкриється бот **HealthchecksBot** → натисніть
   **Start** → він надішле посилання → відкрийте його й натисніть **Connect Telegram**.
   Пошта підключена одразу.
3. **Add Check** → назва `case-store: диск`, **Period: 1 hour**, **Grace: 30 minutes**.
   Скопіюйте адресу для пінгу — вигляду `https://hc-ping.com/<набір символів>`.

**На сервері:**

```bash
crontab -e
```

Додайте рядок (замість `<uuid>` — ваша адреса; не забудьте видалити старий рядок з `df … | mail`,
якщо він у вас був):

```
0 * * * * DISK_PING_URL=https://hc-ping.com/<uuid> /opt/case-store/scripts/disk-check.sh >> /var/log/store-disk-check.log 2>&1
```

Перевірити руками — поріг 1 % спрацює напевно:

```bash
DISK_PING_URL=https://hc-ping.com/<uuid> DISK_THRESHOLD=1 /opt/case-store/scripts/disk-check.sh
# → «disk-check: WARNING — disk / at NN% …», а в healthchecks.io перевірка стала червоною
/opt/case-store/scripts/disk-check.sh   # без порогу → нічого не друкує, перевірка знову зелена після наступного пінгу
```

> Адреса пінгу — не пароль, але хто її знає, той може «відзвітувати» за ваш сервер.
> Тримайте її в менеджері паролів і в `crontab`, **не** в git.

Що робити, коли диск заповнюється, — §2 «Місце на диску».

### 1.4 Бекап — сигнал «нічний бекап не відбувся»

Бекап, який тихо зламався три місяці тому, — найгірший сценарій (§2). `scripts/backup.sh`
уміє звітувати в healthchecks.io сам:

- на старті — «почав» (healthchecks.io бачить, скільки триває бекап, і попередить, якщо він
  завис);
- у кінці — «успіх» **лише** якщо все пройшло, інакше «провал» **разом із причиною**
  (її видно в журналі перевірки на healthchecks.io);
- якщо бекап не запустився взагалі — сигналу немає, і healthchecks.io попереджає про тишу.

Збій самого healthchecks.io (чи мережі) бекап **не зупиняє і не ламає**: пінг — лише спроба,
обмежена в часі; не вийшло — у лозі бекапу з'явиться попередження, а бекап іде далі.

1. healthchecks.io → **Add Check** → назва `case-store: нічний бекап`. Перемкніть розклад на
   **Cron**, вираз `30 3 * * *` (той самий, що в crontab), часовий пояс — як на сервері
   (`timedatectl` покаже; зазвичай UTC), **Grace: 1 hour**. Скопіюйте адресу пінгу.
2. На сервері `crontab -e` — **допишіть змінну в наявний рядок бекапу**
   ([08-backup-restore.md](08-backup-restore.md) §1.3):

   ```
   30 3 * * * cd /opt/case-store && BACKUP_PING_URL=https://hc-ping.com/<uuid> ./scripts/backup.sh >> /var/log/store-backup.log 2>&1
   ```

3. Перевірка — запустіть бекап руками з тією самою змінною й подивіться, що в healthchecks.io
   з'явились події «start» і «success»:

   ```bash
   cd /opt/case-store && BACKUP_PING_URL=https://hc-ping.com/<uuid> ./scripts/backup.sh
   ```

> **Чому в `crontab`, а не в `.env.production`.** Той самий скрипт запускається ще й перед
> кожним деплоєм (`--db-only`). Ці запуски не мають звітувати в перевірку, що стежить за
> **нічним** бекапом: інакше вдалий деплой удень «замаскує» нічний бекап, що не відбувся.
> Тому адреса живе лише в рядку нічного cron.

Щотижневий погляд у лог бекапу (§2) лишається: сигнал «успіх» доводить, що скрипт
відпрацював, але не те, що бекап **відновлюється** — це перевіряє лише репетиція з
[08-backup-restore.md](08-backup-restore.md) §5.

### 1.5 Графіки навантаження — графіки хостера, а не netdata

**Рішення: окремого моніторингового контейнера (netdata, Prometheus/Grafana) не ставимо.**
Для графіків — вкладка **Graphs** сервера в консолі Hetzner.

Чому:

- **Пам'яті немає зайвої.** На CX22 (4 ГБ) ліміти пам'яті контейнерів у
  `docker-compose.prod.yml` уже в сумі ≈ 3,2 ГБ (Postgres, Redis, Meilisearch, API, вітрина,
  адмінка, Umami, Caddy). netdata сам по собі їсть ~100–200 МБ — це третина того запасу, що
  лишився системі, і саме той запас, який рятує від OOM у пікові хвилини.
- **Ще одні двері назовні.** Панель netdata треба або відкрити в інтернет (порт + пароль у
  Caddy + ще один піддомен), або щоразу ходити через ssh-тунель. І це ще один образ, який
  треба оновлювати.
- **Графіки хостера нічого не коштують і живуть поза сервером.** Hetzner збирає CPU, диск
  (операції й швидкість) і мережу на рівні гіпервізора: вони є навіть тоді, коли сервер
  «завис» і ssh не пускає, — саме тоді вони й потрібні.

Чого в графіках Hetzner **немає**, і чим це закрито:

| Немає в графіках хостера | Чим закрито                                                                                                                              |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Заповнення диска         | §1.3 — `disk-check.sh` щогодини                                                                                                          |
| Пам'ять                  | `docker stats --no-stream` (§6); контейнер, убитий через пам'ять, видно в `$COMPOSE ps` — у нього «Up 2 minutes», коли решта «Up 5 days» |
| «Сайт не відповідає»     | §1.2 — UptimeRobot                                                                                                                       |

**Коли переглянути рішення:** якщо повторюються незрозумілі гальма, а графіки хостера й
`docker stats` їх не пояснюють. Тоді netdata ставиться **тимчасово**, за офіційною
інструкцією для Docker, з портом лише на `127.0.0.1`, дивитесь через тунель
`ssh -L 19999:127.0.0.1:19999 deploy@<сервер>` → `http://localhost:19999`, і після
розслідування — видаляєте. Скільки навантаження витримує сервер загалом —
[10-capacity.md](10-capacity.md).

## 2. Щоденні / щотижневі дії

```bash
ssh deploy@<сервер>
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml"   # на staging: + -f docker-compose.staging.yml
```

### Чи все живе

```bash
$COMPOSE ps
```

У колонці `STATUS` має бути `Up ... (healthy)` у всіх. `unhealthy` / `Restarting` → §5.

Самоперевірку (healthcheck) має кожен сервіс, і кожна перевіряє справжню роботу, а не
«процес запущено». У `store-client` і `store-admin` вона вшита в сам образ (Dockerfile —
запит до сторінки засобами node), тому в `docker-compose.prod.yml` їх навмисно не перекрито:
до 2026-09 там стояла перевірка через `wget`, якого в цих образах немає, і обидва сервіси
показували `unhealthy`, хоча сайт працював (TASK-829). Одразу після `up -d` статус кілька
десятків секунд буде `(health: starting)` — це нормально; `unhealthy` означає, що сервіс
тричі поспіль не відповів.

### Логи

```bash
$COMPOSE logs --tail=100 store-api    # останні 100 рядків
$COMPOSE logs -f store-api            # «живі» логи (Ctrl+C — вийти)
```

Найчастіше цікавить `store-api` — там видно помилки замовлень і авторизації.
Інші сервіси: `store-client`, `store-admin`, `postgres`, `redis`, `meilisearch`, `caddy`, `umami`.

> **Шукайте перший ERROR згори, а не знизу.** Знизу зазвичай наслідки, а не причина.

### Перезапустити один сервіс

```bash
$COMPOSE restart store-api
```

> Перезапуск **не розлогінює** користувачів: сесія тримається на JWT + refresh-токені в базі,
> а не в пам'яті контейнера. Клієнти не помітять.

### Перевірити, що нічний бекап відпрацював — **щотижня**

Бекап, який тихо зламався три місяці тому, — найгірший сценарій. Якщо налаштовано §1.4,
про бекап, що не відбувся, вам напише healthchecks.io — але раз на тиждень усе одно гляньте
сюди: сигнал «успіх» каже лише, що скрипт відпрацював, а не що файли й досі лежать у хмарі.

```bash
tail -5 /var/log/store-backup.log        # має закінчуватись "backup: done — <дата>"
ls -lht /opt/case-store/backups/ | head -3 # свіжі файли
rclone ls b2:case-store-backups | tail -3  # і вони доїхали в хмару
```

### Місце на диску

```bash
df -h /                    # загальне
docker system df           # скільки з'їв Docker
docker image prune -f      # прибрати старі образи (безпечно)
```

## 5а. Playbook: «зберіг в адмінці, а на сайті не змінилось»

Цей випадок не схожий на решту: **нічого не падає**. Контейнери здорові, адмінка каже
«збережено», логи чисті, `/health` віддає 200. Просто зміна зʼявляється на сайті не одразу,
а за випадкові 0–60 хвилин. Тому його треба діагностувати окремо — інакше він читається як
«функція не працює».

### Крок 1. Перевірте себе, а не сервер (30 секунд)

Дві найчастіші хибні тривоги:

- **Ви ходили по сайту посиланнями, а не оновлювали сторінку.** Браузер тримає вже відкриті
  сторінки до **5 хвилин**. Перевіряйте через **Ctrl+Shift+R** (жорстке оновлення) або в
  режимі інкогніто.
- **Ви замінили картинку за тією самою адресою.** Тоді нову побачить лише той, у кого
  порожній кеш — до 4 годин. Завантажте файл **заново** замість заміни: кожне завантаження
  отримує власну адресу, і вона підхоплюється одразу.

### Крок 2. Чи долітає сигнал ревалідації

Після кожної правки API просить вітрину скинути кеш. Подивіться, чи ця розмова відбувається:

```bash
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml --env-file .env.production"

# 1. Чи задано секрет — і чи він ОДНАКОВИЙ у двох контейнерах.
#    Команда друкує лише довжину, не саме значення.
docker exec store_prod_api    sh -c 'echo "api:    ${#REVALIDATE_SECRET} символів"'
docker exec store_prod_client sh -c 'echo "client: ${#REVALIDATE_SECRET} символів"'

# 2. Слідкуйте за логом і в цей самий момент змініть щось в адмінці.
docker logs -f store_prod_api 2>&1 | grep -E 'revalidate\.notify'
```

| Що зʼявилось у лозі                          | Що це означає                                    | Що робити                                               |
| -------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------- |
| `revalidate.notify`                          | Сигнал пройшов — річ не в ньому                  | Поверніться до кроку 1                                  |
| `revalidate.notify.failed` + `status: 401`   | Секрети в двох контейнерах різні                 | Крок 3                                                  |
| `revalidate.notify.failed` + `status: 503`   | Секрет не заданий **у вітрині**                  | Крок 3                                                  |
| `revalidate.notify.error`                    | Вітрина недосяжна за `STOREFRONT_REVALIDATE_URL` | Крок 3                                                  |
| `revalidate.notify.disabled` (на старті API) | Змінні порожні **в API**                         | Крок 3                                                  |
| Порожньо, хоча ви щойно зберегли             | Правка не з тих, що ревалідують                  | Норма для деяких сутностей — див. `docs/plans/172-*.md` |

Для повноти той самий бік із вітрини: `docker logs store_prod_client 2>&1 | grep -i revalidate`.

### Крок 3. Лікування

```bash
# Обидва контейнери мають читати ОДНЕ значення. Джерело істини — секрет
# PROD_ENV_FILE у GitHub Environment, а не файл на сервері.
grep -c '^REVALIDATE_SECRET=' /opt/case-store/.env.production   # має бути рівно 1

$COMPOSE up -d store-api store-client
```

> 🚨 **`restart` тут не працює.** `docker compose restart` перезапускає процес зі **старими**
> змінними — env-файл перечитує лише `up -d`. Половина випадків «секрет правильний, а 401
> лишається» — саме це.

Якщо після цього в лозі зʼявився `revalidate.notify`, а на сайті все одно старе — річ у
кроці 1, а не в сервері.

## 6. Аварійні команди — шпаргалка

```bash
# --- ДОСТУП ---
ssh deploy@<сервер>
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml"

# --- ДІАГНОСТИКА ---
$COMPOSE ps                          # хто живий
$COMPOSE logs --tail=100 store-api   # що сталось
curl -i https://api.<домен>/health   # чи жива база
df -h /                              # чи є місце
./scripts/disk-check.sh; echo $?     # те саме, що щогодини робить cron (0 = нормально)
docker stats --no-stream             # хто їсть пам'ять

# --- ЛІКУВАННЯ ---
$COMPOSE restart store-api           # перезапустити один сервіс (СТАРІ змінні!)
$COMPOSE up -d                       # підняти те, що впало / підхопити нові змінні
docker image prune -f                # звільнити місце

# --- ЗМІНИ В АДМІНЦІ НЕ ВИДНО НА САЙТІ ---
docker logs -f store_prod_api 2>&1 | grep -E 'revalidate\.notify'   # → розділ 5а

# --- КАТАСТРОФА ---
./scripts/backup.sh                  # зробити бекап ПРЯМО ЗАРАЗ
# відкат образу      → 07-rollback.md
# відновлення бази   → 08-backup-restore.md

# --- ВТРАТИЛИ ДОСТУП ДО АДМІНКИ ---
$COMPOSE exec store-api node dist/scripts/create-admin.js --email ваша@пошта.com

# --- ВТРАТИЛИ ДОСТУП ДО СЕРВЕРА ---
# → 03-server.md, розділ 5 (консоль хостера)
```
