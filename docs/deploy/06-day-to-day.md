# Щоденна робота — щоб магазин не падав

> **Для кого:** для того, хто ніколи не адміністрував сервер. Це не довідник — це те, що
> треба знати, щоб магазин працював, а ви спали.
>
> Розділ 5 (playbook аварії) — **роздрукуйте**. Під час інциденту ви не будете думати ясно,
> і це нормально.

---

## 0. Головне за одну хвилину

Дешевий VPS падає майже завжди з однієї з двох причин. **Обидві повністю передбачувані, і
обидві вже закриті в конфігурації** — але ви маєте знати, що вони існують:

1. **Закінчилось місце на диску.** Docker за замовчуванням зберігає логи **вічно**. Нічого
   не ламається, ніхто не попереджає — просто через кілька місяців Postgres не може
   записати байт, і все зупиняється одночасно. → Закрито ротацією логів (≈240 МБ стеля).
2. **Закінчилась пам'ять.** Один застосунок «тече», росте, і ядро Linux вбиває **найбільший
   процес** — а це зазвичай Postgres. Тобто витік у вітрині кладе базу. → Закрито лімітами
   пам'яті: тепер помирає той, хто винен, і `restart: unless-stopped` його одразу піднімає.

Третя причина — **ви самі**, під час деплою. Про це [05-first-deploy.md](05-first-deploy.md) §5.

## 1. Щоб ви дізнались про поломку раніше за клієнта

Найважливіший розділ, який усі відкладають. Без нього ви дізнаєтесь про падіння магазину з
листа розлюченого покупця — через 6 годин.

### 1.1 Sentry — помилки в коді

DSN **уже вшитий у код**, лишилось заповнити.

1. Зареєструйтесь на [sentry.io](https://sentry.io) (безкоштовного тарифу вистачає).
2. Створіть проєкт → скопіюйте DSN.
3. У `.env.production` на сервері: `SENTRY_DSN=https://...`
4. GitHub → Environments → `production` → Variables: `NEXT_PUBLIC_SENTRY_DSN`.

Тепер кожна 500-та помилка прилітає вам із повним стеком і контекстом запиту.

### 1.2 Uptime-моніторинг — «сайт лежить»

Sentry не побачить, якщо сервер **зовсім** не відповідає. Потрібна перевірка ззовні.

1. [UptimeRobot](https://uptimerobot.com) — безкоштовно.
2. Три монітори (ті самі URL, що перевіряє CI):
   - `https://api.<домен>/health` ← **найважливіший**
   - `https://<домен>/`
   - `https://admin.<домен>/`
3. Сповіщення → на телефон і на пошту.

> **Чому `/health` найважливіший.** Він **справді перевіряє базу** — пінгує її й віддає 503,
> якщо вона не відповідає. Це реальний датчик, а не «сервер відповідає щось».

### 1.3 Місце на диску

```bash
# crontab на сервері, перевірка щогодини
0 * * * * df -h / | awk 'NR==2 && int($5) > 80 {print "УВАГА: диск заповнений на "$5}' | mail -s "case-store: диск" ваша@пошта.com
```

Якщо `mail` не налаштований — перевіряйте руками раз на тиждень: `df -h`.

## 2. Щоденні / щотижневі дії

```bash
ssh deploy@<сервер>
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml"   # на staging: + -f docker-compose.staging.yml
```

### Чи все живе

```bash
$COMPOSE ps
```

У колонці `STATUS` має бути `Up ... (healthy)` у всіх. `unhealthy` / `Restarting` → §5.

### Логи

```bash
$COMPOSE logs --tail=100 store-api    # останні 100 рядків
$COMPOSE logs -f store-api            # «живі» логи (Ctrl+C — вийти)
```

Найчастіше цікавить `store-api` — там видно помилки замовлень і авторизації.
Інші сервіси: `store-client`, `store-admin`, `postgres`, `redis`, `meilisearch`, `caddy`, `umami`.

> **Шукайте перший ERROR згори, а не знизу.** Знизу зазвичай наслідки, а не причина.

### Перезапустити один сервіс

```bash
$COMPOSE restart store-api
```

> Перезапуск **не розлогінює** користувачів: сесія тримається на JWT + refresh-токені в базі,
> а не в пам'яті контейнера. Клієнти не помітять.

### Перевірити, що нічний бекап відпрацював — **щотижня**

Бекап, який тихо зламався три місяці тому, — найгірший сценарій.

```bash
tail -5 /var/log/store-backup.log        # має закінчуватись "backup: done — <дата>"
ls -lht /opt/case-store/backups/ | head -3 # свіжі файли
rclone ls b2:case-store-backups | tail -3  # і вони доїхали в хмару
```

### Місце на диску

```bash
df -h /                    # загальне
docker system df           # скільки з'їв Docker
docker image prune -f      # прибрати старі образи (безпечно)
```

## 5. Playbook інциденту — сайт лежить

**Роздрукуйте.**

```
┌─ САЙТ НЕ ВІДКРИВАЄТЬСЯ ────────────────────────────────────────┐
│                                                                │
│ 1. Це сталося одразу після деплою?                             │
│      ТАК → ВІДКАТ ОБРАЗУ. 07-rollback.md, розділ 1.            │
│            Не розслідуйте зараз. Спершу підніміть магазин.     │
│      НІ  → далі                                                │
│                                                                │
│ 2. ssh deploy@<сервер> && cd /opt/case-store                      │
│    docker compose -f docker-compose.prod.yml ps                 │
│                                                                │
│    Хтось "Exited" / "Restarting"?                              │
│      → docker compose ... logs --tail=100 <сервіс>             │
│      → шукайте перший ERROR згори, не знизу                    │
│                                                                │
│ 3. curl -i https://api.<домен>/health                           │
│                                                                │
│    HTTP 503 + "database":"down"  → база впала (крок 4)         │
│    Взагалі не відповідає         → сервер/Caddy (крок 5)       │
│    HTTP 200                      → API живий, проблема у вітрині│
│                                                                │
│ 4. БАЗА ВПАЛА                                                   │
│    df -h /              ← диск заповнений? найчастіша причина   │
│    docker compose ... logs postgres --tail=50                   │
│    docker compose ... restart postgres                          │
│                                                                │
│ 5. СЕРВЕР НЕ ВІДПОВІДАЄ ВЗАГАЛІ                                │
│    Пінгується? Заходить по ssh?                                 │
│      НІ → консоль хостера → reboot                             │
│      ТАК → docker compose -f docker-compose.prod.yml up -d     │
│                                                                │
│ 6. НІЩО НЕ ДОПОМАГАЄ                                           │
│    → 08-backup-restore.md, розділ 4.4                          │
│      (підняти магазин з нуля на новому сервері з бекапів)      │
└────────────────────────────────────────────────────────────────┘
```

### Перше правило інциденту

**Спершу відновіть роботу, потім шукайте причину.** Відкат образу займає хвилину і нічого не
руйнує. Розслідування може зачекати годину — ваші клієнти не можуть.

## 6. Аварійні команди — шпаргалка

```bash
# --- ДОСТУП ---
ssh deploy@<сервер>
cd /opt/case-store
COMPOSE="docker compose -f docker-compose.prod.yml"

# --- ДІАГНОСТИКА ---
$COMPOSE ps                          # хто живий
$COMPOSE logs --tail=100 store-api   # що сталось
curl -i https://api.<домен>/health   # чи жива база
df -h /                              # чи є місце
docker stats --no-stream             # хто їсть пам'ять

# --- ЛІКУВАННЯ ---
$COMPOSE restart store-api           # перезапустити один сервіс
$COMPOSE up -d                       # підняти те, що впало
docker image prune -f                # звільнити місце

# --- КАТАСТРОФА ---
./scripts/backup.sh                  # зробити бекап ПРЯМО ЗАРАЗ
# відкат образу      → 07-rollback.md
# відновлення бази   → 08-backup-restore.md

# --- ВТРАТИЛИ ДОСТУП ДО АДМІНКИ ---
$COMPOSE exec store-api node dist/scripts/create-admin.js --email ваша@пошта.com

# --- ВТРАТИЛИ ДОСТУП ДО СЕРВЕРА ---
# → 03-server.md, розділ 5 (консоль хостера)
```
