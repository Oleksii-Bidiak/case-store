# Відкат (rollback) — що робити, коли деплой зламав прод

> **Головне правило: спершу відкотіть образ, потім розбирайтеся.**
>
> Дев'ять із десяти зламаних деплоїв — це баг у коді, а не в схемі бази. Відкат образу
> займає ~1 хвилину, нічого не руйнує і повністю оборотний. Розслідування зачекає — ваші
> клієнти ні.
>
> **Ніколи не «спробую задеплоїти ще раз»** у надії, що воно саме минеться. Якщо
> smoke-check червоний — відкочуйтесь.

---

## 0. Дві різні поломки, які легко переплутати

| Що зламалось              | Симптом                                                    | Що робити |
| ------------------------- | ---------------------------------------------------------- | --------- |
| **Код** (новий образ)     | 500-ки, біла сторінка, кнопка не працює. Дані в базі цілі. | Розділ 1  |
| **Схема бази** (міграція) | API не стартує; помилки типу «column does not exist»       | Розділ 2  |

Відрізнити просто: подивіться логи `store-api`. Якщо він **взагалі не стартує** і скаржиться
на структуру таблиць — винна міграція. Якщо стартує, але поводиться дивно — винен код.

---

## 1. Відкат образу (майже завжди — це те, що вам потрібно)

Образи не видаляються: кожна збірка лежить у GHCR під тегом `prod-<sha>`. Відкат — це
просто «запустити попередній тег». **Нічого перезбирати не треба.**

### Крок 1. Знайти, який тег працював

GitHub → **Actions** → попередній зелений **Deploy to Production** → у **Summary** написані
всі три теги:

```
- store-api: `prod-a1b2c3d...` (built: true)
- store-client: `prod-e4f5g6h...` (built: false)
- store-admin: `prod-e4f5g6h...` (built: false)
```

> `built: false` означає, що цей застосунок не змінювався і його контейнер навіть не
> перезапускався. Відкочувати треба тільки ті, де `built: true`.

### Крок 2. Один раз залогінитись у GHCR

Поза CI сервер не має доступу до сховища образів — треба залогінитись руками. **Зробіть це
заздалегідь, не в момент аварії.**

Потрібен персональний токен GitHub із правом **`read:packages`** (GitHub → Settings →
Developer settings → Personal access tokens → classic-токен із галочкою `read:packages`).
Покладіть його в менеджер паролів ([01-accounts-access.md](01-accounts-access.md) §2).

```bash
echo '<ваш-GHCR-токен>' | docker login ghcr.io -u <ваш-github-логін> --password-stdin
```

### Крок 3. Запустити попередні образи

На сервері:

```bash
cd /opt/case-store

# впишіть теги з попереднього успішного деплою
cat > docker-compose.images.yml <<'YAML'
services:
  store-api:
    image: ghcr.io/oleksii-bidiak/store-api:prod-<ПОПЕРЕДНІЙ-SHA>
  store-client:
    image: ghcr.io/oleksii-bidiak/store-client:prod-<ПОПЕРЕДНІЙ-SHA>
  store-admin:
    image: ghcr.io/oleksii-bidiak/store-admin:prod-<ПОПЕРЕДНІЙ-SHA>
YAML

COMPOSE="docker compose -f docker-compose.prod.yml -f docker-compose.images.yml --env-file .env.production"
$COMPOSE pull
$COMPOSE up -d
```

**Перевірити, який образ зараз запущений** (щоб не переплутати збірки):

```bash
$COMPOSE images
```

### Крок 4. Перевірити

```bash
curl -i https://api.<домен>/health    # має бути HTTP 200 і "database":"up"
curl -i https://<домен>/              # вітрина
```

Якщо `/health` віддає **503** — база недоступна. Це вже не про код: дивіться розділ 2.

### Те саме на staging — простіше

На staging усі три образи мають **спільний** тег, тож окремий файл не потрібен:

```bash
cd /opt/case-store
export IMAGE_TAG=staging-<попередній-SHA>
COMPOSE="docker compose -f docker-compose.prod.yml -f docker-compose.staging.yml --env-file .env.production"
$COMPOSE pull
$COMPOSE up -d
```

> **На staging схему бази відкочувати не треба** — дані там одноразові. Якщо стан
> заплутався, простіше перезалити з нуля
> ([05-first-deploy.md](05-first-deploy.md) §6). **На проді так не можна.**

## 2. Відкат поганої міграції

Тут немає простої кнопки, і це треба чесно розуміти: **Prisma не вміє автоматично
відкочувати міграції назад**. «Down»-міграцій не існує.

Але у вас є те, що це рятує: **бекап знімається автоматично перед кожним прод-деплоєм**
(і деплой не почнеться, якщо бекап не вдався).

### Крок 1. Все одно спершу відкотіть образ

Старий код + нова схема — часто працює краще, ніж новий код + нова схема, і дає вам час
подумати без клієнтів на лінії.

### Крок 2. Відновіть базу з передеплойного бекапу

Повна процедура — [08-backup-restore.md](08-backup-restore.md), розділ 4.3. Коротко:

```bash
cd /opt/case-store
docker compose -f docker-compose.prod.yml stop store-api store-client store-admin

# бекап, знятий автоматично ПЕРЕД цим деплоєм
age -d -i backup-key.txt -o db.dump backups/db-<дата-деплою>.dump.age
cat db.dump | docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner

docker compose -f docker-compose.prod.yml start store-api store-client store-admin
```

### Крок 3. Переіндексуйте пошук

Індекс Meilisearch похідний від бази. Після відновлення він «пам'ятає» стан, якого вже
немає, і пошук показуватиме товари-привиди. Кнопка є в адмінці, або:

```bash
curl -X POST https://api.<домен>/api/admin/search/reindex \
  -H "Authorization: Bearer <ваш-адмін-токен>"
```

## 3. ⚠ Момент, коли «відновити бекап» стає НЕПРАВИЛЬНОЮ відповіддю

Це найважливіше в цьому документі, і його легко пропустити.

Поки магазин новий і замовлень мало, відновлення бекапу — безпечний хід: ви втрачаєте
хвилини даних.

**Але щойно у вас з'являться реальні замовлення, зроблені ПІСЛЯ поганої міграції —
відновлення бекапу їх зітре.** Клієнт заплатив, замовлення зникло. Це гірше за початкову
поломку.

З цього моменту правильний шлях інший:

1. Відкотіть **образ** (це безпечно завжди — дані не чіпаються).
2. Напишіть **нову міграцію, яка виправляє проблему вперед** — не повертає базу назад, а
   доводить її до правильного стану, зберігаючи все, що встигли записати.
3. Задеплойте її як звичайний фікс.

**Правило великого пальця:** якщо після поганого деплою минуло більше кількох хвилин і в
магазині є трафік — **не відновлюйте базу**. Фіксьте вперед.

## 4. Репетиція (зробіть один раз на staging)

Під час справжньої аварії ви будете нервувати. Тому пройдіть відкат **спокійно, заздалегідь**,
на staging — щоб це не було вперше.

1. Задеплойте щось на staging.
2. Подивіться в Summary теги.
3. Задеплойте ще раз (будь-яку зміну).
4. **Відкотіться на попередні теги** за розділом 1.
5. Переконайтесь, що сайт живий: `curl -i https://api.staging.<домен>/health`.

Займає 10 хвилин. Один раз — і ви більше не боїтесь деплоїти.

---

## 5. Пам'ятка

```
Smoke-check червоний?
   → Відкотити образ (розділ 1). Не думати. Не деплоїти повторно.

Відкотили образ, /health досі 503?
   → Проблема в базі (розділ 2).

Магазин уже має реальні замовлення після поганого деплою?
   → НЕ відновлювати базу. Фіксити вперед (розділ 3).
```
