# Домен і DNS — коли домен належить замовнику (TASK-316)

> **Ситуація:** домен уже є, і він **не ваш**. Можливо, на ньому вже живе сайт. Майже
> напевно — пошта.
>
> ## ⚠ Правило цього документа
>
> **Ви тільки ДОДАЄТЕ записи для своїх піддоменів. Нічого не видаляєте, нічого не
> редагуєте, нейм-сервери не чіпаєте.**
>
> Один зайвий рух з поштовими записами — і в замовника перестає ходити пошта. Не «магазин
> не працює», а **бізнес не отримує листів**. Це той випадок, коли зламати чуже легше, ніж
> здається, і помітять не одразу.

---

## 0. Що ми робимо в одному абзаці

Магазин живе на **піддомені**: `shop.<домен-замовника>`. Корінь домену, сайт замовника і
його пошта лишаються **недоторканими** — ми їх навіть не бачимо. Усе, що нам потрібно, —
кілька нових записів, які нічого існуючого не перекривають.

---

## 1. Три адреси, і це не обговорюється

Магазин — це три застосунки на трьох адресах:

| Адреса           | Що це                             |
| ---------------- | --------------------------------- |
| `{DOMAIN}`       | вітрина — те, що бачить покупець  |
| `admin.{DOMAIN}` | адмін-панель                      |
| `api.{DOMAIN}`   | бекенд + завантажені фото товарів |

Це задано в `Caddyfile` (три site-блоки). Зауважте: блоку `www.` **немає**.

### Плюс четверта — аналітика (TASK-378)

| Адреса               | Що це                                    |
| -------------------- | ---------------------------------------- |
| `analytics.{DOMAIN}` | Umami: лічильник відвідувань + її панель |

Формально не обов'язкова — магазин без неї працює. Але **без неї аналітики не існує
взагалі**, і це не очевидно: лічильник вантажить браузер відвідувача, тож поки в Umami
немає публічної адреси, скрипт нізвідки взяти. Контейнер при цьому «здоровий», в адмінці
порожньо, і жодної помилки ніде. Якщо аналітика потрібна — робіть A-запис одразу з рештою,
а далі йдіть за [05a-analytics.md](05a-analytics.md).

На відміну від трьох адрес вище, ця може жити й на іншому домені: у неї немає ні наших кук,
ні CSRF. Лишаємо поруч лише заради зручності сертифікатів і однієї згадки в DNS.

### Чому всі три мусять бути піддоменами ОДНОГО домену

Це не стиль і не економія — це властивість коду:

- бекенд ставить куки з `sameSite: 'strict'` (`apps/store-api/src/auth/auth.controller.ts`);
- CSRF-кука має префікс `__Host-` (`apps/store-api/src/csrf/csrf.constants.ts`), який
  **забороняє** атрибут `Domain`.

Якщо рознести вітрину й API по різних доменах, браузер просто викидатиме куку — логін
злітатиме при кожному перезавантаженні. **Обійти конфігом неможливо**, лише переписуванням
авторизації та CSRF. Тому: один домен, три піддомени.

---

## 2. Схема адрес

`DOMAIN` — просто рядок у конфізі, тож глибина піддоменів значення не має.

| Середовище  | `DOMAIN`               | Три адреси                                                                           |
| ----------- | ---------------------- | ------------------------------------------------------------------------------------ |
| **Прод**    | `shop.<домен>`         | `shop.<домен>`<br>`admin.shop.<домен>`<br>`api.shop.<домен>`                         |
| **Staging** | `staging.shop.<домен>` | `staging.shop.<домен>`<br>`admin.staging.shop.<домен>`<br>`api.staging.shop.<домен>` |

Разом — **6 A-записів** на два різні IP (staging і прод — різні сервери, див. `03-server.md`).

---

## 3. Що спитати в замовника

Він, найімовірніше, не знає цих слів. Питайте по суті, не термінами:

1. **Чи відкривається зараз щось на самому домені?** (сайт, візитівка, «заглушка»)
2. **Чи є пошта на домені?** — тобто адреси виду `щось@<домен>`. **Це найважливіше
   питання.** Якщо так — до поштових записів не торкаємось без окремої розмови (§5).
3. **Хто йому налаштовував домен?** Реєстратор (де купували), хостер, чи хтось третій?
   Cloudflare?
4. **Він дасть доступ до панелі DNS — чи внесе записи сам?** Обидва варіанти робочі; від
   цього залежить лише, кому надсилати §4.

> Якщо відповідь на будь-що — «не знаю», попросіть **скриншот сторінки з DNS-записами**.
> З нього видно все.

## 5. ⚠⚠ Пошта — тут можна зламати замовнику бізнес

Магазин надсилає листи: **підтвердження замовлення**, **скидання пароля**, **сповіщення про
заблокований акаунт**. Без робочої пошти покупець не отримує підтвердження замовлення —
тобто магазин виглядає зламаним.

Але налаштування пошти чіпає DNS **глибше**, ніж A-записи. Тут — головна пастка.

### Чому шлемо з піддомену, а не з кореня

Всі приклади в конфігах показують `no-reply@example.com` — **кореневий домен**. Для нас це
було б помилкою:

> **SPF-запис може бути тільки ОДИН на домен.** Якщо в замовника вже є пошта, у нього вже
> **є** SPF-запис на корені. Додасте другий — обидва стануть недійсними, і **в замовника
> зламається пошта**. Не «погіршиться» — перестане доставлятись.

Тому:

```
MAIL_FROM="Назва магазину <no-reply@shop.<домен>>"
```

Піддомен `shop.<домен>` має **власні, незалежні** поштові записи. Корінь замовника не
торкаємось узагалі — навіть якщо там уже все є. Це та сама логіка, що й з A-записами.

### Записи для пошти (їх дасть SMTP-провайдер)

Провайдер після додавання домену `shop.<домен>` покаже точні значення. Форма така:

| Тип | Ім'я                         | Навіщо                                                    |
| --- | ---------------------------- | --------------------------------------------------------- |
| TXT | `shop`                       | **SPF** — хто має право слати від імені цього піддомену   |
| TXT | `<селектор>._domainkey.shop` | **DKIM** — підпис, що лист не підробили                   |
| TXT | `_dmarc.shop`                | **DMARC** — що робити з листами, які не пройшли перевірку |

Усі три — **на піддомені**. Власний `_dmarc.shop` перекриває політику кореня саме для
нашого піддомену, тож ми не залежимо від того, що там налаштував замовник.

> **MX не потрібен:** магазин лише **надсилає** листи, не приймає. Побічний наслідок: відповідь
> на `no-reply@shop.…` нікуди не дійде. Для «no-reply» це нормально й очікувано, але якщо
> замовник хоче отримувати відповіді — це окрема задача (потрібна справжня скринька).

### Провайдер SMTP

У проєкті він **не обраний** — жоден док його не називає. Обирає замовник (акаунт має бути
на ньому — `01-accounts-access.md` §1).

Робочі варіанти: **Brevo**, **Mailgun**, **SendGrid**, **Postmark**, **Resend**. Умови
безкоштовних тарифів змінюються — звіряйте актуальні на сайті провайдера, не за цим
документом.

На що дивитись при виборі: чи дозволяє **власний домен-відправник** (обов'язково — без цього
DKIM не налаштувати) і чи дає готові DNS-записи для копіювання.

> **Gmail/ukr.net як SMTP для магазину — погана ідея.** Ліміти, блокування за «розсилку»,
> і в полі «Від» стоятиме чужа адреса. Транзакційна пошта — окремий інструмент.

### Поки SMTP не налаштований

Система **не робить вигляд**, що надіслала. Листи лишаються в черзі зі статусом `PENDING`,
у логи щохвилини пишеться помилка. Коли SMTP з'явиться — **ці самі листи підуть**, нічого не
загубиться. Але це не заміна робочій пошті: покупець свого підтвердження так і не бачить.

## 6. Cloudflare — сіра хмарка, не помаранчева

Якщо DNS замовника на Cloudflare, у кожного A-запису є перемикач **Proxy status**:

|                                     |                                      |
| ----------------------------------- | ------------------------------------ |
| 🟠 **Proxied** (помаранчева хмарка) | **зламає сертифікат** — так не можна |
| ⚪ **DNS only** (сіра хмарка)       | ✅ так треба                         |

**Чому.** Caddy отримує HTTPS-сертифікати Let's Encrypt автоматично, і для перевірки
«я справді власник цієї адреси» він має **бачити з'єднання напряму**. Проксі Cloudflare
стає посередині — перевірка не проходить, сертифікат не видається, сайт не відкривається.
(Обхід існує — перевірка через DNS — але він **не налаштований** у цьому проєкті.)

Якщо замовник наполягає на проксі — це окрема задача, а не «щось придумаємо на місці».

**Порти 80 і 443** на сервері мають бути відкриті — інакше та сама перевірка не пройде.

## 7. Перевірте ДО деплою

Не деплойте, поки записи не розійшлись. Інакше Caddy зробить кілька невдалих спроб отримати
сертифікат і **впреться в ліміти Let's Encrypt** — далі доведеться чекати годинами.

```bash
# кожна з шести адрес має віддати IP потрібного сервера
nslookup shop.<домен>
nslookup admin.shop.<домен>
nslookup api.shop.<домен>
nslookup staging.shop.<домен>
nslookup admin.staging.shop.<домен>
nslookup api.staging.shop.<домен>
```

Зміни DNS розходяться від хвилин до кількох годин. Якщо адреса не резолвиться — **чекайте**,
не «спробуйте задеплоїти й подивіться».

Перевірити, що не зачепили чуже:

```bash
nslookup <домен>              # сайт замовника — має відповідати як раніше
nslookup -type=MX <домен>     # його пошта — має лишитись незмінною
nslookup -type=TXT <домен>    # його SPF — має бути РІВНО ОДИН запис
```

## 8. ⚠ Домен обирається ДО першої збірки

Адреси **запікаються всередину** застосунків на етапі збірки образу (`NEXT_PUBLIC_*` — це
build-time, не runtime). Образ назавжди прив'язаний до одного середовища: staging-образ
**неможливо** промоутнути в прод.

**Наслідок:** передумали щодо домену → **повна перезбірка всіх образів**. Тому домен
узгоджується із замовником **до** першого деплою, а не «потім поміняємо».

## 9. Куди вписати значення

Коли адреси узгоджені (з `04-secrets-ci.md`):

| Де                           | Змінна            | Значення                                          |
| ---------------------------- | ----------------- | ------------------------------------------------- |
| GitHub → Variables           | `STAGING_DOMAIN`  | `staging.shop.<домен>`                            |
| GitHub → Variables           | `PROD_DOMAIN`     | `shop.<домен>`                                    |
| `.env.production` на сервері | `DOMAIN`          | те саме для цього сервера                         |
| `.env.production`            | `CORS_ORIGINS`    | `https://shop.<домен>,https://admin.shop.<домен>` |
| `.env.production`            | `PUBLIC_BASE_URL` | `https://api.shop.<домен>`                        |
| `.env.production`            | `MAIL_FROM`       | `"Магазин <no-reply@shop.<домен>>"`               |

`STAGING_DOMAIN` / `PROD_DOMAIN` — це **один** рядок кожен; `admin.` і `api.` пайплайн
додає сам.
