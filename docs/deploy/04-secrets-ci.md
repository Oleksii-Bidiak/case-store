# Секрети й CI — щоб деплой запрацював

> Тут ви заповнюєте GitHub так, щоб він міг сам заходити на ваші сервери й оновлювати
> магазин. Ніяких паролів у коді немає й бути не може.
>
> **Перед цим:** [03-server.md](03-server.md) — потрібні IP обох серверів.

---

## 0. ⚠ Спершу прочитайте це

Усе, що ви зараз впишете в GitHub, — **write-only**. Записати можна, **прочитати назад —
ніколи**, навіть вам як власнику репозиторію.

**Тому: оригінал кожного значення спершу кладіть у менеджер паролів, і тільки потім — у
GitHub.** Інакше через пів року ви не знатимете пароля до власної бази, а бекап без нього
не відновити.

Деталі — [01-accounts-access.md](01-accounts-access.md) §3.

---

## 1. Згенерувати секрети

`.env.production.example` — список усього, що треба заповнити. Скопіюйте його й заповніть
**реальними** значеннями.

Надійний секрет:

```bash
openssl rand -hex 32
```

> **На сервері працює лише перша команда.** Деплой-сервер має Docker, але **не має Node**, тож
> `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` там впаде з
> `command not found` — вона для ноута. Hex зручний ще й тим, що не містить символів, які
> довелося б URL-кодувати всередині `DATABASE_URL`.

Вимоги, які реально перевіряються при старті (інакше застосунок не підніметься):

| Змінна                                | Вимога                                                |
| ------------------------------------- | ----------------------------------------------------- |
| `JWT_SECRET`, `JWT_REFRESH_SECRET`    | ≥32 символи і **мусять відрізнятися** один від одного |
| `CSRF_SECRET`                         | ≥32 символи                                           |
| `REVALIDATE_SECRET`                   | ≥32 символи, **однакове значення** для API й вітрини  |
| `MEILI_MASTER_KEY`                    | ≥16 символів                                          |
| `UMAMI_APP_SECRET`                    | ≥32 символи                                           |
| `POSTGRES_PASSWORD`, `REDIS_PASSWORD` | обов'язкові; спецсимволи URL-екранувати               |
| `CORS_ORIGINS`                        | обов'язковий у проді, перевіряється формат            |
| `NEXT_PUBLIC_APP_URL`                 | обов'язковий; без слеша в кінці (див. нижче)          |

> Кожен рядок із `.env.production.example` має бути заповнений. Пропустите один обов'язковий
> — `docker compose up` впаде з «… must be set». Це навмисно: краще впасти на старті, ніж
> працювати наполовину.

**Що буде, якщо не задати конкретну змінну** — окрема сторінка:
**[04a-env-matrix.md](04a-env-matrix.md)**. Туди ж винесено налаштування, яких у
`.env.production.example` навмисно немає (ліміти пам'яті, крони). Ідіть туди, якщо
питання звучить як «а це взагалі обов'язкове?».

Два рядки з неї, які легко пропустити саме при **оновленні вже розгорнутого** стека:

- `REVALIDATE_SECRET` — **новий обов'язковий**. Без нього стек не підніметься. Це той
  ключ, завдяки якому правки в адмінці одразу з'являються на сайті.
- `NEXT_PUBLIC_APP_URL` — має другу роботу: те саме значення йде в API як
  `STORE_CLIENT_URL`, тобто на нього ведуть посилання «відновити пароль» у листах і
  повернення після входу через Google.

## 2. Пароль на staging

Staging закритий Basic Auth — щоб його не проіндексував Google і не побачили сторонні.

```bash
# згенерувати хеш пароля
docker run --rm caddy caddy hash-password --plaintext 'ваш-пароль'
```

Пароль потрапляє у **два різні місця, у двох різних формах**:

| Куди                                             | Змінна                        | Формат                                      |
| ------------------------------------------------ | ----------------------------- | ------------------------------------------- |
| у `.env.production` (тобто в `STAGING_ENV_FILE`) | `STAGING_BASIC_AUTH`          | **хеш** `$2a$...` — як є, `$` не подвоювати |
| у Secrets середовища `staging`                   | `STAGING_BASIC_AUTH_PASSWORD` | **відкритий пароль**                        |

Другий потрібен лише для того, щоб smoke-check у CI міг достукатись до сайту. Без нього
деплой впаде з 401 і скаже вам про це прямо.

Логін: `staging`. Адреса `/health` навмисно **не** під паролем — щоб працювали smoke-check
і uptime-моніторинг. Вона не віддає нічого, крім «живий/мертвий + чи відповідає база».

## 3. Заповнити середовище `staging`

GitHub → репозиторій → **Settings → Environments → `staging`**.

**Secrets:**

| Ім'я                          | Що це                                                     |
| ----------------------------- | --------------------------------------------------------- |
| `SSH_HOST`                    | IP staging-сервера                                        |
| `SSH_USER`                    | `deploy`                                                  |
| `SSH_PRIVATE_KEY`             | приватний SSH-ключ (публічний уже на сервері)             |
| `STAGING_ENV_FILE`            | **весь вміст** заповненого `.env.production` одним блоком |
| `STAGING_BASIC_AUTH_PASSWORD` | пароль staging відкритим текстом (§2)                     |

**Variables** (публічні, не секрет):

| Ім'я                                                     | Приклад                  |
| -------------------------------------------------------- | ------------------------ |
| `STAGING_DOMAIN`                                         | `staging.shop.<домен>`   |
| `NEXT_PUBLIC_CURRENCY`                                   | `UAH` _(необов'язково)_  |
| `NEXT_PUBLIC_PAYMENT_METHODS`                            | `ON_DELIVERY,ONLINE`     |
| `NEXT_PUBLIC_GOOGLE_AUTH_ENABLED`                        | `true` _(необов'язково)_ |
| `NEXT_PUBLIC_IMAGE_HOSTS`                                | _(необов'язково)_        |
| `NEXT_PUBLIC_SENTRY_DSN`                                 | _(необов'язково)_        |
| `NEXT_PUBLIC_UMAMI_SRC` / `NEXT_PUBLIC_UMAMI_WEBSITE_ID` | _(необов'язково)_        |
| `NEXT_PUBLIC_UMAMI_DASHBOARD_URL`                        | _(необов'язково)_        |

> `STAGING_DOMAIN` — **один** рядок. Адреси `admin.` й `api.` пайплайн збирає сам.

> ⚠ `NEXT_PUBLIC_*` **запікаються в образ** тим самим пайплайном, тому їх задають
> тут, у Variables середовища, а не в `.env.production` на сервері. Найважливіша —
> `NEXT_PUBLIC_PAYMENT_METHODS`: поки вона порожня, чекаут пропонує **лише оплату
> при отриманні**, які б ключі LiqPay не лежали в `.env.production`. Змінили
> будь-яку з них — потрібне **перезбирання**, а не перезапуск (TASK-348).

## 4. Заповнити середовище `production`

Те саме, але:

| Тип      | Ім'я                                        | Що це                                             |
| -------- | ------------------------------------------- | ------------------------------------------------- |
| Secret   | `SSH_HOST` / `SSH_USER` / `SSH_PRIVATE_KEY` | доступ до **прод**-сервера                        |
| Secret   | `PROD_ENV_FILE`                             | увесь `.env.production` прод-сервера одним блоком |
| Variable | `PROD_DOMAIN`                               | `shop.<домен>` (**без** `staging.`)               |

Решта `NEXT_PUBLIC_*` Variables — ті самі, що й у таблиці staging вище, з
прод-значеннями. Їх треба завести **окремо**: середовища не успадковують змінних одне
від одного, а порожня `NEXT_PUBLIC_PAYMENT_METHODS` у `production` мовчки вимкне
онлайн-оплату на бойовому сайті.

### ⚠⚠ Ручне затвердження — увімкніть зараз

**Settings → Environments → `production` → Required reviewers → додайте себе.**

**Це єдиний запобіжник.** У самому workflow його немає й **бути не може** — жоден рядок коду
не здатен його замінити. З ним прод-деплой зупиниться й чекатиме, поки ви натиснете
«Approve» в GitHub Actions. Без нього будь-який злитий PR поїде в прод сам.

## 5. Захист гілки `main`

Зараз коміти в `main` блокує лише локальний хук на **вашому комп'ютері**. На GitHub
**нічого не заважає** запушити напряму в `main` — і це одразу запустить прод-деплой в обхід
усіх тестів.

**Settings → Branches → Add rule** для `main`:

- ✅ Require a pull request before merging
- ✅ Require status checks to pass → `Type Check`, `Lint`, `Unit Tests`, `E2E Tests`
- ✅ Do not allow bypassing the above settings

## 6. Ротація секретів — і що кожен ламає

Знадобиться не сьогодні, але хай буде поруч із рештою.

| Секрет                              | Що станеться при зміні                                       | Коли робити                 |
| ----------------------------------- | ------------------------------------------------------------ | --------------------------- |
| `JWT_SECRET` / `JWT_REFRESH_SECRET` | **Розлогінить УСІХ** — і клієнтів, і вас                     | вікно низького трафіку      |
| `POSTGRES_PASSWORD`                 | Змінити в базі **і** в `.env` + рестарт стека                | планове вікно               |
| `CSRF_SECRET`                       | Зламає відкриті форми у клієнтів (вони перезавантажать)      | будь-коли, майже безболісно |
| `AGE_PUBLIC_KEY`                    | Старі бекапи читаються **старим** ключем — не втрачайте його | обережно                    |

**Загальне правило: не міняйте секрети «про всяк випадок».** Кожна ротація — це ризик і
простій. Міняйте, коли є підозра на витік.

## 7. Поміняти ключ Нової Пошти або LiqPay

Найчастіша операція після запуску — і вона проста, якщо тримати в голові **один
поділ**: змінна або читається під час **роботи** (тоді досить перезапустити), або
**запікається в образ** під час збірки (тоді потрібне перезбирання). Плутанина між
цими двома класами дає симптом «ключ правильний, а не працює».

### Рантайм — перезапуск, без перезбирання

Сюди належать **усі серверні ключі**: `NP_API_KEY`, `NP_SENDER_CITY_REF`,
`LIQPAY_PUBLIC_KEY`, `LIQPAY_PRIVATE_KEY`, `LIQPAY_SANDBOX`, `LIQPAY_PAYTYPES`,
SMTP, `SENTRY_DSN`, `REVALIDATE_SECRET`.

1. GitHub → репозиторій → **Settings → Environments → `production` → Secrets**.
2. Відкрийте **`PROD_ENV_FILE`**, змініть потрібний рядок, збережіть.
   (Секрет write-only: побачити поточний вміст не можна, тому тримайте копію в
   менеджері паролів — див. [01-accounts-access.md](01-accounts-access.md).)
3. **Actions → CI → Run workflow → гілка `main`** → затвердіть у `production`.
4. Пайплайн перезапише `.env.production` на сервері й зробить `up -d`. Образи
   **не перезбираються** — у лозі джоби буде видно `manifest inspect` і пропуск збірки.

Для staging усе те саме, але секрет називається `STAGING_ENV_FILE`, а деплой
запускається пушем у `develop`.

### Три речі, на яких спотикаються

- Змінна називається **`NP_API_KEY`**, а не `NOVA_POSHTA_API_KEY`.
- **Порожній `NP_API_KEY` у проді = доставка рахується як 0 ₴**, а не помилка на
  екрані (див. [09-pre-launch.md](09-pre-launch.md)). Тобто «ключ забули» виглядає
  як «безкоштовна доставка», і покупець цим скористається.
- `LIQPAY_PRIVATE_KEY` ніколи не залишає сервер і замальовується в логах. Змінної
  `NEXT_PUBLIC_LIQPAY_*` не існує — і не має існувати: усе з префіксом
  `NEXT_PUBLIC_` потрапляє в браузер відвідувача.

### 🪤 Пастка, яка вкусить саме на LiqPay

**Увімкнути онлайн-оплату — це ДВІ дії, а не одна:**

1. ключі `LIQPAY_*` у `PROD_ENV_FILE` (рантайм, перезапуск), **і**
2. **`NEXT_PUBLIC_PAYMENT_METHODS`** у **Variables** того самого середовища
   (білд-тайм, **перезбирання**).

Порожній `NEXT_PUBLIC_PAYMENT_METHODS` мовчки лишає на чекауті **лише післяплату**,
скільки б правильних ключів не тримав API. Виглядає це як «LiqPay не працює», а
причина — вітрина, зібрана без цього прапорця. Після зміни Variables деплой має
**перезібрати** образи вітрини й адмінки.

> 🪤 **І ще одна, для розробника.** Образи будує список `build-args:` у
> **`ci.yml`**, а не `build.args` у `docker-compose.prod.yml`. Змінна, додана лише
> в compose, у задеплоєний контейнер **не потрапить**.

### 🪤 Та сама пастка на вході через Google

**Кнопка «Увійти через Google» — теж ДВІ дії:**

1. `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_CALLBACK_URL` у
   `PROD_ENV_FILE` (рантайм, перезапуск), **і**
2. **`NEXT_PUBLIC_GOOGLE_AUTH_ENABLED=true`** у **Variables** того самого
   середовища (білд-тайм, **перезбирання**).

Без другої кнопки на сторінці входу немає взагалі — вітрина зібрана без прапорця.
Без першої кнопка є, але веде в помилку. До TASK-495 друга дія була **неможлива**:
прапорець з'явився в коді з TASK-402, але ні `ci.yml`, ні Dockerfile вітрини, ні
compose його не передавали, тож у жодному контейнерному розгортанні кнопку не можна
було ввімкнути. Тепер можна — але саме значення все одно задає оператор, і жодна
перевірка в CI цього за нього не зробить.
