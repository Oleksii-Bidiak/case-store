# Вимоги до проєкту: Інтернет-магазин мобільних аксесуарів (MVP)

## 1. Загальний опис (Project Overview)
Сучасний інтернет-магазин мобільних аксесуарів (B2C) з панеллю адміністратора для управління контентом та замовленнями. Проєкт розробляється ітеративно з фокусом на масштабованість, безпеку та надійність.

## 2. Стек технологій (Tech Stack)
* **Архітектура репозиторію:** Monorepo (npm workspaces).
* **Backend:** Nest.js, TypeScript.
* **Database:** PostgreSQL (контейнеризація через Docker).
* **ORM:** Prisma.
* **Frontend (Storefront):** Next.js (App Router), React, TypeScript.
* **Frontend (Admin Panel):** Next.js (App Router), React, TypeScript.
* **State Management & Data Fetching:** TanStack Query (React Query).
* **Styling:** Tailwind CSS (з архітектурною готовністю до міграції на SCSS Modules), shadcn/ui (для Admin Panel).
* **API Контракт:** OpenAPI (Swagger) + Orval (автогенерація типів та хуків).

---

## 3. Архітектура додатків (Architecture)

### 3.1. Структура Монорепозиторію
Проєкт розділений на незалежні робочі простори (workspaces) для забезпечення ізоляції та перевикористання коду:
* `apps/store-api` — бекенд.
* `apps/store-client` — клієнтська вітрина.
* `apps/store-admin` — панель адміністратора.
* `packages/eslint-config` — спільні налаштування лінтера.

### 3.2. Backend (Clean Architecture / Layered)
Nest.js додаток будується за принципами багатошарової архітектури:
* **Controllers:** Тільки маршрутизація, валідація DTO та відповіді. Жодної бізнес-логіки.
* **Services:** Інкапсуляція бізнес-логіки.
* **Repositories (через Prisma):** Ізольована робота з базою даних.

### 3.3. Frontend (Feature-Sliced Design - FSD)
Для організації коду в Next.js додатках використовується методологія FSD для чіткого розділення зон відповідальності:
* `app/` — ініціалізація додатку, глобальні провайдери, роутинг (App Router).
* `widgets/` — самостійні блоки інтерфейсу (напр., `Header`, `ProductCard`).
* `features/` — бізнес-взаємодії (напр., `AddToCart`, `CheckoutForm`).
* `entities/` — бізнес-сутності (напр., `User`, `Product`).
* `shared/` — перевикористовуваний UI-кіт, утиліти, згенеровані API клієнти.

## 4. Контроль якості та Тестування (Testing & QA)

### 4.1. Test-Driven Development (TDD)
Для критичних модулів (наприклад, розрахунок вартості кошика, застосування знижок, управління запасами) застосовується підхід TDD (Red -> Green -> Refactor):
1. Написання тесту, який падає, для нової вимоги.
2. Написання мінімального коду для проходження тесту.
3. Рефакторинг з гарантією працездатності.

### 4.2. Рівні тестування
* **Unit Тести (Jest):** Покриття складних сервісів бекенду та ізольованих утиліт/хуків фронтенду.
* **E2E Тести (NestJS / Supertest):** Тестування API ендпоінтів від запиту до бази даних (на ізольованій тестовій БД).
* **Linting & Formatting:** ESLint + Prettier (обов'язковий запуск на pre-commit хуках через Husky).

---

## 5. Безпека (Security)
* **Аутентифікація:** JWT (JSON Web Tokens) з коротким часом життя (Access Token) та механізмом Refresh Token (зберігається в HttpOnly cookie).
* **Валідація:** Сувора валідація вхідних даних через `class-validator` (Backend) та `zod` (Frontend).
* **Захист від атак:** Налаштування CORS, Rate Limiting (захист від DDoS/Brute-force) та Helmet (безпечні HTTP заголовки) в Nest.js.
* **Секрети:** Всі чутливі дані (ключі API, паролі до БД) зберігаються виключно в `.env` файлах, які ігноруються Git.

---

## 6. Логування та Моніторинг (Logging & Observability)
Для забезпечення стабільності на продакшені впроваджується багаторівневий контроль:
* **Backend Логування:** Використання `Pino` або `Winston` для структурованого JSON-логування.
    * Логування всіх помилок (Error).
    * Логування критичних бізнес-подій (Info: створення замовлення, реєстрація).
* **Frontend Error Tracking:** Інтеграція `Sentry` для відстеження помилок у браузері користувача та незароблених виключень (Unhandled Rejections).
* **Логування запитів:** Middleware для логування тривалості обробки HTTP запитів до API.

## 7. CI/CD та Інфраструктура (DevOps)

### 7.1. Безперервна інтеграція (CI)
Налаштований пайплайн через **GitHub Actions**. При кожному Push/Pull Request у гілку `main` або `develop` автоматично:
1. Встановлюються залежності (`npm ci`).
2. Запускається перевірка типів (`tsc --noEmit`).
3. Запускається Linter.
4. Проганяються Unit та e2e тести.

### 7.2. Стратегія розгалуження (GitFlow / GitHub Flow)
* `main` — стабільна версія (продакшен).
* `develop` — гілка активної розробки.
* `feature/*` — гілки для розробки окремих фіч (зливаються в develop через Pull Request).

### 7.3. Контейнеризація
Проєкт має бути повністю описаний через `docker-compose.yml` для легкого розгортання:
* База даних PostgreSQL.
* За необхідності: Redis (для кешування або черг).


Розумний пошук (Full-Text Search): Звичайний пошук по базі даних працює повільно і не розуміє помилок (наприклад, "афйон" замість "айфон"). Топові магазини використовують окремі рушії: Elasticsearch, Meilisearch або Algolia.

Складна система кешування та CDN: Картинки товарів мають роздаватися через глобальну мережу (Cloudflare або AWS CloudFront). Результати частих запитів (меню, популярні товари) мають кешуватися в Redis, щоб бекенд не "впав" під час Чорної П'ятниці.

SEO на стероїдах: Динамічна генерація sitemap.xml, впровадження мікророзмітки (Schema.org) для товарів, відгуків та хлібних крихт, щоб у Google з'являлися красиві сніпети з ціною та рейтингом.

Маркетингова автоматизація: Відстеження "кинутих кошиків" (автоматичні листи на пошту, якщо людина не завершила покупку), інтеграція з Google Analytics 4 (e-commerce події) та Facebook Pixel.

🎨 Опис UI Системи (Дизайн-архітектура)
Щоб наш фронтенд не перетворився на хаос із сотень незрозумілих класів Tailwind, ми будуємо UI систему за принципом "від меншого до більшого" (Atomic Design), адаптованим під FSD.

1. Design Tokens (Фундамент у tailwind.config.ts)
Ми не будемо писати text-[#0f172a]. У конфігу Tailwind ми задамо семантичні змінні:

primary: головний акцентний колір (кнопка "Купити").

background, foreground: кольори фону та тексту.

muted: для другорядного тексту.

Перевага: Якщо замовник захоче змінити фірмовий колір із синього на червоний, ми змінимо рівно один рядок у конфігу, і весь сайт перефарбується.

2. UI Kit (Базові компоненти - shared/ui)
Тут живуть "тупі" компоненти, які нічого не знають про бізнес-логіку. Для адмінки (і, за бажанням, для вітрини) ми використаємо shadcn/ui.

Це не звичайна бібліотека, яку ти встановлюєш через npm. Ти копіюєш вихідний код компонента (наприклад, <Button /> або <Input />) у свій проєкт.

Це дає повний контроль. Якщо тобі треба змінити логіку роботи кнопки, ти просто правиш її код, а не воюєш із чужими стилями.

3. Бізнес-компоненти (features/ та widgets/)
Це "розумні" компоненти, які збираються з UI Kit та підключаються до бекенду.

Feature: <AddToCartButton variantId="123" />. Вона містить кнопку з UI Kit, але всередині використовує згенерований через Orval хук useMutation, щоб відправити запит на додавання в кошик.

Widget: <ProductCard />. Вона містить фото, ціну, та AddToCartButton.

4. Доступність (a11y) та Взаємодія
Сучасний магазин має бути зручним для всіх. Основа shadcn — це Radix UI, який гарантує, що:

Усі модальні вікна можна закрити кнопкою Esc.

По формах можна пересуватися клавішею Tab.

Екранні диктори правильно зачитують інформацію для людей з вадами зору.
